# FR12 纵向审查：SessionController 智能助手会话控制流

> 审查日期：2026-08-18  
> 审查方式：独立纵向审查（requirements → ADR → plan/story → changelog → code → tests）  
> 审查范围：FR12；同时检查其与 FR13 会话切换、FR14 TaskManager 通知、ExecutionEngine/GraphExecutor 和智能助手 UI 的必要交界  
> 变更边界：本次只新增本报告，不修改需求、架构、方案、业务代码或测试

## 1. 结论先行

FR12 不能继续按“已实现/全部完成”理解。它完成了**文件和方法层面的控制流搬迁**，也建立了一个可单测的五状态对象，但没有完成真正的运行时控制权收口。当前更准确的状态是：

**部分实现，存在 P0 级会话控制闭环缺陷；结构迁移基本完成，异步任务、失败、取消、关联和生命周期仍未闭环。**

最关键的事实如下：

1. `SessionController` 已存在且无 PyQt6 import，ChatWidget 也确实接入了它；Orchestrator 的 Plan/Tool/Reply 分发已迁出。
2. `AWAITING_TASK` 只在单元测试中被手工调用，生产代码没有任何 `handle_task_started()` 调用。后台工具返回 `task_id` 后，Controller 会立即从 `EXECUTING` 进入下一轮 `THINKING`；任务稍后完成时，UI 又调用 `handle_task_completed()`，从而命中错误状态断言。
3. Plan 的实际创建、执行、取消和关闭仍由 `ChatWidget` 驱动；`SessionController._execute_plan()` 是空实现。因此 ADR-008 D8 所称“会话级顶层调度者”尚未落地，Controller 更接近一个夹在回调链中的状态跟踪器。
4. LLM 未配置、LLM 请求失败、用户取消 Plan、任务属于其他会话、任务完成发生在 abort 之后等真实事件没有完整状态转换，Controller 会停留在错误状态或收到不属于它的全局完成事件。
5. 46 个 FR12 定向测试全部通过，但“集成测试”主要是纯 Controller + MagicMock 的手工状态推进，没有走真实 ChatWidget、ToolExecutionHandler、TaskManager 和异步工具链，因而没有覆盖上述缺陷。
6. `plans/session-controller/plan.md` 标为“全部完成”，但所有验收框仍为未勾选，引用的两个 Story 文件实际不存在；当前文档无法作为可靠的完成证据。

建议优先采用“**事件驱动的 Session Runtime + 类型化执行结果 + 关联 ID + 可释放订阅**”方案，以增量替换方式迭代，而不是继续向当前五状态类增加条件分支。

## 2. 审查证据链

### 2.1 需求原文

FR12 位于 `docs/requirements.md:913-956`，核心目标是：

- 从 ChatWidget、ConversationOrchestrator、ToolExecutionHandler 提取会话主循环；
- 以 `IDLE / THINKING / AWAITING_CONFIRM / EXECUTING / AWAITING_TASK` 显式表达状态；
- 由 Controller 统一决定 LLM 响应分发、确认、执行完成、后台任务完成和终止；
- ChatWidget 只保留 UI 渲染、用户输入、文件上传和记忆检索；
- Orchestrator 只负责 LLM 轮次生命周期、流式处理和解析；
- ToolHandler 只报告步骤执行完成，不再决定是否继续 ReAct；
- 外部行为不变，原有 smart_assistant 测试零回归。

### 2.2 架构决策

FR12 对应 `docs/adr/008-smart-assistant-code-layering.md:394-502` 的 D8-D12：

- D8：SessionController 是 Orchestrator、ToolHandler、ExecutionEngine 之上的顶层调度者；
- D9：使用 enum + `assert` + `_transition_to()`；
- D10：会话级状态与 GraphExecutor 执行级状态分层；
- D11：规定输入事件和输出回调；其中 ToolHandler 应报告 `on_step_completed(step, result)`；
- D12：先影子并行，再清理旧路径。

架构意图正确，但 D9 的 `assert` 选择、D11 的结果契约、D10 对后台任务与 Graph 子任务的边界定义不足，是当前运行时缺陷的直接来源。

### 2.3 Plan、Story 与 Changelog

- `plans/session-controller/plan.md` 声明 2/2 完成，但第 34-62 行的验收项全部为 `[ ]`。
- Plan 引用：
  - `plans/session-controller/stories/story-01-core-and-parallel.md`
  - `plans/session-controller/stories/story-02-cleanup.md`
  两个文件均不存在，`plans/session-controller/stories/` 目录也不存在。
- Changelog 完整存在于 `docs/changelogs/session-controller/story-01-session-controller/`，记录了需求、ADR、Plan、Story 01 和 Story 02 的编码过程。
- Story 02 changelog 声称 ChatWidget 从约 1108 行降至 1047 行并成为 UI-only；当前 `chat_widget.py` 已增长至 1239 行，并继续拥有计划执行、TaskManager 订阅、任务完成路由、会话持久化和控制器错误兜底等控制职责。

因此，changelog 能证明“发生过修改”，不能证明“验收闭环完成”。

## 4. 关键问题清单

### P0-1：后台任务状态在生产路径不可达，完成回调必然可能撞错状态

证据：

- `session_controller.py:199-203` 定义了 `handle_task_started()`；
- 全仓库生产代码没有调用该方法，只有 `tests/smart_assistant/test_session_controller*.py` 手工调用；
- `_execute_react()` 在 `session_controller.py:254-261` 调用工具，但完全丢弃返回的 `ToolResult`；
- `ToolSpec.is_long_running` 已存在，异步工具的 `ToolResult.data` 也返回 `task_id`，但 Controller 和 Handler 都未把它转换成 `AWAITING_TASK`；
- ChatWidget 在单工具、批量工具和自动模式下都在工具函数返回后立即调用 `handle_execution_complete()`，把状态转成 `THINKING`；
- 稍后 `chat_widget.py:774-800` 的 TaskManager 回调无条件调用 `handle_task_completed()`，而该方法只允许 `AWAITING_TASK`。

最小复现结果：异步工具返回 `task_id=t1` 后状态为 `thinking`，随后完成通知抛出：

```text
after_start thinking
AssertionError: handle_task_completed 仅允许在 AWAITING_TASK 状态调用，当前: State.THINKING
```

影响：

- 后台翻译/润色完成后，观察消息可能已经写入，但 Controller 无法可靠继续 ReAct；
- 回调异常被 TaskManager `_safe_callback()` 捕获并降为 warning，用户得到“看似完成、会话不继续”的隐蔽失败；
- Plan 中启动后台任务时同样会把“启动命令完成”误判为“业务任务完成”。

### P0-2：TaskManager 监听器无法正确释放，且完成事件没有会话归属

证据：

- `TaskManager.on_completed()` / `on_failed()` 会把传入回调包装为内部 `_wrapper` 后存进 `finished` 列表；
- `ChatWidget.shutdown()` 使用原始 bound method 调用 `remove_listener()`；原始方法与 `_wrapper` 不是同一个对象，无法移除；
- 实测注册两个监听器后调用当前 shutdown 同等的 remove 操作，`finished` 监听器数量从 2 仍为 2；
- ChatWidget 还注册了一个匿名 `on_finished(lambda ...)`，没有保存引用，也无法释放；
- TaskManager 是进程级单例，事件只带 `task_id`，SessionController 没有维护自己拥有的 task_id 集合。

影响：

- 已关闭或已切换的 ChatWidget 仍可能被回调，形成引用泄漏和跨会话事件串扰；
- 任意后台任务完成都会通知所有曾注册的 ChatWidget；
- 多会话、多个窗口或未来 MCP/Agent 同时使用 TaskManager 时，状态污染会快速放大。

### P0-3：LLM 启动失败和请求错误没有状态事件，Controller 会停在 THINKING

证据：

- `handle_user_message()` 先转 `THINKING`，再调用 Orchestrator；
- `conversation_orchestrator.py:221-224` 在没有 API key 时只显示消息后 return；
- `_on_error()` 在 `conversation_orchestrator.py:339-373` 只清 UI/worker 和显示错误，不通知 Controller；
- Controller 没有 `handle_round_failed()` / `handle_round_cancelled()`。

影响：状态展示、输入互斥、重试、会话切换和后续可观测性无法依赖 Controller 的状态；当前靠下一次发送前先 `handle_abort()` 自愈，不是真正的状态闭环。

### P0-4：Plan 取消没有通知 Controller

`chat_widget.py:681-685` 的 `_on_plan_cancelled()` 只取消现有 Engine、隐藏思考提示并显示消息，没有调用 `controller.handle_user_cancelled()`。用户在 Plan Card 点击取消时，Controller 仍为 `AWAITING_CONFIRM`。

这是 FR12 明确要求的转换遗漏，也是现有测试没有走真实 ChatWidget 的直接后果。

### P1-1：Controller 不是架构定义的顶层调度者

- `_execute_plan()` 是 no-op；
- Engine 创建、回调注册、提交、取消、shutdown 都在 ChatWidget；
- Controller 不持有 Engine，`handle_abort()` 只取消 Orchestrator，不取消 Plan Engine 或已归属后台任务；
- `conversation` 和 `on_check_permission` 被注入但未使用；`handle_user_message(text)`、`handle_execution_complete(results)`、`handle_task_completed(task_id, result)` 的核心参数也未用于决策或关联。

这说明当前类主要记录“调用方告诉我的状态”，而不是拥有控制流。

### P1-2：同步/异步工具契约缺失，不能只靠 `is_long_running`

仓库已有 `ToolSpec.is_long_running`，但其语义并不等同于“返回后台 TaskRef”：

- `start_translation`、`start_polish`、`run_postprocess` 会真正创建后台线程并返回 `task_id`；
- ParaTranz upload/download/export 和 writer 的部分工具标记为 long-running，却仍同步执行并直接返回最终结果；
- export 甚至在调用线程阻塞轮询最长 30 秒。

因此简单补一行“若 `is_long_running` 则进入 AWAITING_TASK”会制造新的永久等待。需要以**实际执行结果类型**作为生命周期事实来源，而不是用展示元数据猜测。

### P1-3：状态合法性依赖 `assert`，优化模式会静默破坏状态机

当前 D9 使用 assert 保护转换。实测：

```text
python -O ... handle_execution_complete([])
=> idle 状态直接变为 thinking，react_depth=1
```

`assert` 是开发期断言，不是运行时协议校验。发布、打包或测试一旦启用优化，非法事件会被接受。即便不开优化，真实世界的延迟/重复/乱序事件也不应通过 AssertionError 处理。

### P1-4：缺少 turn/execution/task 关联，迟到事件可污染新一轮

状态只有 enum，没有 `session_id / turn_id / round_id / execution_id / task_id`。用户 abort 后旧 worker 或旧任务的迟到回调，无法被识别为 stale；切换会话后完成的旧任务也无法归属原会话。

### P1-5：ReAct 深度有双份状态和边界不一致

- Controller 在完成一次执行后累加深度；
- Orchestrator 在每次 `start_round()` 时另行累加深度；
- ADR 示例使用 `>= MAX`，实现使用 `> MAX` 后再累加，实质允许多一轮；
- Orchestrator 的旧回调和 property 仍保留，形成无效的第二事实源。

### P1-6：ToolHandler 的回调契约没有按 ADR 实现

ADR 规定 `on_step_completed(step, result)`；代码实现为 `Callable[[], None]`，丢失工具名、结果、失败、task_id、执行 ID。并且 `_handle_result()` 仍根据 `skip_react_continue` 和 `mode` 决定是否通知，这意味着“下一步控制策略”仍有一部分留在 Handler。

### P2-1：无步骤响应会重复结束会话

Controller 在无步骤时调用 `on_conversation_end()`，Orchestrator 随后也在 `conversation_orchestrator.py:326-328` 调用自己的 end 回调。当前 ObservabilityCollector 可能容忍重复 end，但所有权不唯一，未来增加持久化/计费/审计后容易重复提交。

### P2-2：Plan/Story 状态和链接失真

- Plan 标“全部完成”，验收项全部未勾；
- 两个 Story 链接是悬空链接；
- Plan 写“6 个输入接口”但需求和代码实际为 7/8 个（又加入了 `handle_task_started`）；
- Changelog 的“唯一驱动者”结论与当前代码不一致；
- `docs/requirements.md`、`docs/INDEX.md`、`plans/INDEX.md` 均把 FR12 标为已完成。

### P2-3：测试命名为集成，实际没有覆盖生产接线

`test_session_controller_integration.py` 主要直接调用 Controller；所谓 Orchestrator 集成测试只用 `inspect.signature()` 验证构造参数存在。没有创建真实 ChatWidget，也没有验证：

- Plan Card cancel；
- 无 API key / LLM error；
- ToolHandler 返回同步结果、失败结果、Deferred task；
- TaskManager 主线程分发与监听释放；
- 多会话任务隔离；
- abort 后迟到回调；
- 自动模式和批量模式中混合同步/异步结果。

## 6. 可选改进方案比较

### 方案 A：在当前 Controller 上做最小补丁

做法：

- ToolHandler 返回后检查 `result.data.task_id`；
- 有 task_id 就调用 `handle_task_started()`；
- Plan cancel、LLM error、no API key 补 Controller 回调；
- TaskManager 改为保存 wrapper 并正确 remove；
- 用显式异常替代 assert。

优点：改动小，可快速解除 P0。

缺点：

- 批量步骤中多个后台任务、同步和异步混合、Plan 中嵌套后台任务仍难表达；
- UI 仍是实际控制器；
- 继续增加 `handle_*` 和 if/else 会让状态组合快速膨胀；
- `task_id` 字段约定仍是隐式的。

结论：适合作为紧急修复，不适合作为最终架构。

### 方案 B：事件驱动 Session Runtime（推荐）

核心模型：

```text
外部事件 -> 纯 reducer/state machine -> Effects/Commands -> EffectRunner
                                  ^              |
                                  |              v
                      typed completion events <- adapters
```

建议类型：

- `SessionEvent`：`UserSubmitted`、`RoundSucceeded`、`RoundFailed`、`ConfirmationAccepted`、`ConfirmationRejected`、`ExecutionFinished`、`TaskStarted`、`TaskFinished`、`TaskFailed`、`AbortRequested`、`SessionSwitched`；
- `SessionState`：不只保存 enum，还保存 `session_id / turn_id / round_id / execution_id / pending_confirmation / owned_task_ids / react_budget`；
- `SessionEffect`：`StartRound`、`PresentConfirmation`、`ExecuteSteps`、`SubscribeTask`、`CancelRound`、`CancelExecution`、`PublishMessage`、`EndTurn`；
- `ToolExecutionOutcome`：
  - `Completed(ToolResult)`；
  - `Deferred(TaskRef)`；
  - 可选 `Rejected/Cancelled`；
- `TaskRef`：至少含 `task_id / owner_session_id / owner_turn_id / kind / cancellation_policy`。

关键原则：

1. Reducer 只做确定性的状态转换和 Effect 生成，不直接调用 Qt、Orchestrator 私有方法或工具。
2. ToolHandler 必须返回类型化 outcome；`is_long_running` 只用于 UI 提示和调度建议，不作为是否等待的事实来源。
3. 所有回调必须带关联 ID；迟到、重复和其他会话的事件可明确忽略并记录。
4. TaskManager 的 `subscribe()` 返回 subscription token/disposable，ChatWidget shutdown 时按 token 释放。
5. Plan Engine 和 React ToolRunner 都作为 `ExecutionPort` 适配器，Controller 不需要知道 BFS/HITL 细节，但必须拥有 submit/cancel/result 生命周期。
6. 状态转换失败使用显式 `InvalidTransition` 或“stale event ignored”结果，不能依赖 assert。
7. 影子迁移时只比较 reducer 输出，旧/新路径绝不能同时执行副作用。

优点：真正实现 FR12 的单一控制权；能自然支持多会话、多后台任务、MCP/Agent 接入、重试和可观测性。

成本：需要新增契约类型、执行适配层和实际 UI 集成测试，改动大于最小补丁。

### 方案 C：直接合并 SessionController 与 GraphExecutor

不推荐。会话状态和 DAG 节点状态的生命周期不同；强行合并会把 UI 确认、LLM 轮次、后台任务和图节点重试耦合到同一个巨型状态机。ADR-008/011 的双层状态方向应保留，只需把两层之间的 submit/result/cancel 协议补完整。

## 7. 推荐目标架构

```text
ChatWidget / MCP / future Agent UI
        |
        v
SessionRuntime (state + reducer + correlation)
        |
        +-- RoundPort ----------> ConversationOrchestrator adapter
        +-- ExecutionPort -----> ReactToolRunner / PlanEngine adapter
        +-- TaskPort ----------> TaskManager subscription adapter
        +-- PresentationPort --> Qt presentation adapter
        +-- SessionStorePort ---> FR13 SessionManager adapter
```

边界说明：

- ChatWidget：收集输入、渲染 `PresentationEffect`、转发按钮事件；不创建或提交 ExecutionEngine，不判断 ReAct 下一步。
- ConversationOrchestrator：执行一个带 `round_id` 的 LLM round，产生 succeeded/failed/cancelled 事件；不结束会话。
- ToolRunner：执行步骤并返回 `Completed/Deferred`；不触发下一轮。
- PlanEngineAdapter：屏蔽 GraphExecutor 细节，只暴露 submit/cancel/completed/failed。
- TaskManagerAdapter：按 owner 订阅任务事件，返回可释放订阅；不向所有会话无差别广播业务事件。
- SessionRuntime：唯一决定等待确认、等待执行、等待哪些 task、何时继续下一轮、何时结束或终止。

## 8. ADR 修订建议

建议在 ADR-008 追加 D13-D18，而不是覆盖 D8-D12 的历史：

### D13：从“回调方法集合”升级为“类型化事件 + Effect”

明确事件、状态数据和副作用的边界。Controller 不直接执行下层对象的私有方法。

### D14：定义工具执行完成契约

规定 `ToolExecutionOutcome = Completed | Deferred | Rejected`。后台任务必须返回 `TaskRef`，禁止仅靠 `is_long_running` 或任意 dict 中的 `task_id` 推断。

### D15：规定全链路关联 ID

每个事件携带 session/turn/round/execution/task 关联；定义 stale、duplicate、foreign event 的处理策略。

### D16：规定取消与失败语义

区分：

- 取消当前 LLM round；
- 取消等待确认；
- 取消 Plan 执行；
- detach 或 cancel 后台任务；
- 会话切换时后台任务的归属和通知策略。

所有路径必须到达稳定状态，不得停留在 THINKING/EXECUTING。

### D17：TaskManager 订阅生命周期

`subscribe(owner, callback) -> Subscription`，订阅可释放；不得用无法反注册的匿名 wrapper/lambda；完成事件按 owner 路由。

### D18：生产状态校验

禁止使用 `assert` 实现业务协议；使用显式错误/忽略策略，并在可观测性中记录非法或迟到事件。

ADR-011 只需补充与 SessionRuntime 的接口，不必改变 GraphExecutor 内部算法。

## 10. 建议验收标准

### 状态正确性

- 任意公开事件在普通 Python 与 `python -O` 下行为一致；
- ReAct 最大轮数边界明确，恰好在约定轮数停止，无 off-by-one；
- no API key、网络失败、认证失败、用户取消、Engine 失败均到达稳定状态；
- 无步骤回复只触发一次 end-turn/end-conversation；
- 每次状态变化包含非空关联上下文。

### 同步/异步执行

- 同步工具完成后恰好继续一次 LLM round；
- Deferred 工具返回 TaskRef 后进入 waiting，完成前不继续；
- 后台任务成功、失败、取消各只继续/终止一次；
- 多个 Deferred task 的等待策略有测试；
- 混合同步 + Deferred 批量执行有测试；
- Plan 中产生 Deferred task 的语义有测试。

### 关联和生命周期

- 两个会话的 task 完成事件不会串扰；
- abort、会话切换或 ChatWidget shutdown 后，旧事件不会改变新状态；
- subscription dispose 后监听器数量回到注册前；
- 不保留已销毁 ChatWidget 的强引用；
- cancel 可按策略传递到 round、plan execution 和 owned tasks。

### 分层

- SessionRuntime 不 import PyQt6；
- ChatWidget 不创建 ExecutionEngine、不判断是否继续 ReAct；
- ToolHandler 不含 `skip_react_continue` 之类的上层控制参数；
- Orchestrator 不保留 ReAct depth、Plan/Tool 卡分发或会话终止所有权；
- Agent/UI/MCP 如需要同一会话循环，应通过同一 SessionRuntime facade，而不是复制回调链。

### 测试与文档门禁

- FR12 单元测试覆盖完整转换矩阵；
- 至少一组真实 Qt 接线 E2E 覆盖 ChatWidget → Orchestrator/ToolHandler → SessionRuntime → TaskManager；
- smart_assistant 全套测试全绿；
- Story 文件真实存在、Plan 验收项逐项勾选、索引状态一致；
- changelog 记录 v2 迁移和 QA 结果。

## 11. 推荐迁移顺序

### Phase 0：冻结现状并补特征测试

先把当前真实行为写成测试，包括本报告的四个 P0。此阶段不重构，确保后续修复能区分“有意改变”和“意外回归”。

### Phase 1：紧急修复生命周期

- Plan cancel / round failed / no API key 回到稳定状态；
- TaskManager 订阅可释放；
- Controller 只处理自己拥有的 task；
- 用显式转换错误替代 assert。

### Phase 2：引入 Outcome/TaskRef 和关联 ID

保持旧 UI 不变，先让 Handler/TaskManager 产生类型化结果。用适配器兼容旧 ToolResult，逐个迁移后台工具。

### Phase 3：影子运行纯 reducer

把生产事件同时送入旧控制器和新 reducer，但新 reducer 的 Effect 全部抑制，只比较状态轨迹和命令，不允许两条路径重复执行工具或 LLM。

### Phase 4：切换 React，再切换 Plan

先迁移单工具/批量 React；稳定后迁移 ExecutionEngine 端口。每次只切一个入口，并保留可回退适配器。

### Phase 5：清理与文档收口

删除旧回调、双份 react depth、ChatWidget 中的 Engine/Task 控制代码；补齐 Story、勾选验收、更新状态。只有真实接线 E2E 和全套测试通过后，FR12 才恢复“已实现”。

## 12. 最终建议

短期先完成 Phase 0-1，解除异步任务、取消、错误和监听泄漏四个 P0；中期选择方案 B，围绕 `SessionEvent / SessionState / SessionEffect / ToolExecutionOutcome / TaskRef` 建立 v2。不要继续把 `handle_*`、boolean 和 task_id 特判堆进当前类，也不要把 SessionController 与 GraphExecutor 合并。

FR12 的正确迭代目标不是“再把 ChatWidget 减少几百行”，而是建立一个可证明的控制权原则：

> 对于任意用户输入、LLM 响应、工具结果、后台任务、取消、失败和会话切换，只有 SessionRuntime 能决定下一步；所有异步事件都可关联、可去重、可取消、可释放、可测试。
