## 1. 结论先行

FR9 不能按当前文档所写认定为“26/26 Story 全部完成且可交付”。更准确的状态是：

> **工具目录和大部分数据操作骨架已经存在，但关键成功链没有闭合；FR9 属于“部分实现、尚未达到端到端可用门槛”。**

当前仓库确实形成了 7 个 FR9 namespace、42 个 FR9 活跃工具（另有 FR16 新增的 7 个工具，总注册数为 49），并实现了 ToolResult、ExecutionContext、TaskManager、Guard、Controller、AgentRegistry 等基础设施。但“注册成功”与“真实业务链成功”之间仍有明显落差：

1. Parser 的 ESP/EET/XT/SST 四条真实成功链均不可用；FR9 要求的 `import_strings` 已从代码删除，但需求和 Story 仍要求存在。
2. Writer 的 EET/XT 构造调用与真实 Writer API 不匹配；Parser 创建的 Slot 又没有保存 plugin/parser/source_path，因此 Parser → Editor → Writer 闭环无法成立。
3. Agent 的筛选和标签状态写入 AppContext，但 Step2 仍维护另一套私有状态，且没有订阅 `filter_changed` / `label_data_changed`；Agent 看到和修改的状态不是用户界面正在使用的状态。
4. 应用启动时先初始化 AgentRegistry、后注册工具，导致 `namespace:*` 在启动时展开为空；代码中也没有生产路径创建 `AgentInstance`，7 个 Agent 更接近静态元数据，而非实际隔离/调度单元。
5. ParaTranz 的三个 `is_long_running` 工具实际同步阻塞执行，没有 TaskManager、task_id、进度、暂停或取消；`download_entries` 不合并本地集合，且返回数据与 description 不一致。
6. MCP 启动路径存在未导入 `ToolRegistry`、未注入 AppContext、配置未传给 Server 等问题；MCP Schema 类型映射无效，工具结果又丢弃 `data`，无法构成可用的外部工具通道。
7. 现有 242 个定向测试中 241 个通过、1 个失败，但大量测试只验证注册、权限、错误路径和 mock，不验证真实 parser/writer/GUI/MCP 成功链。因此通过数不能替代 FR9 验收。

基于需求重要性和真实链路权重，本次给出以下估算：

- 工具注册与目录完成度：约 85%。
- 公共类型/基础设施完成度：约 65%。
- GUI 与 Agent 状态一致性：约 30%。
- Parser/Writer 端到端完成度：约 10%。
- Translator/Proofreader 端到端完成度：约 60%。
- ParaTranz 任务化完成度：约 35%。
- Agent 隔离/调度完成度：约 20%。
- MCP 可用性：约 10%。
- **FR9 综合功能完成度：约 45%，不建议继续标记为“全部完成”。**

上述百分比是用于排迭代优先级的工程估算，不是测试覆盖率。

### 3.3 FR9.2 Editor 与标签

当前 editor 的 7 个 FR9 工具均已注册，数据级的搜索、分页、编辑、stage 和标签方法大部分存在，但与 GUI 的状态契约没有实现：

- `AppContext` 定义 `_filter_state`、`_label_library`、`_entry_labels` 和信号。
- Step2 仍定义自己的 `_label_library`、`_entry_labels`、筛选控件和 `get_filter_state()/apply_filter_state()`。
- 全仓没有 Step2 对 `AppContext.filter_changed` 或 `label_data_changed` 的订阅。
- VariantStore 的 label_library 没有加载到 AppContext。
- Agent 标签以 `entry.key` 作为键；Step2 多处仍以 `entry.id` 查询标签。

因此：

- `set_filters` 修改的是 Agent 侧状态，不会改变 Step2 当前显示。
- `get_visible_entries` 读取的是 Agent 侧筛选，不一定等于用户当前界面筛选。
- Agent 创建/分配的标签不会出现在 Step2 标签 UI，也不会进入现有持久化路径。
- 用户在 Step2 创建的标签，Agent 的 `list_labels` 看不到。

此外还有两个明确实现问题：

1. `edit_translation` 在校验 `new_stage` 之前先写入 `entry.translation`。若 stage 非法，工具返回失败但译文已改变，违反失败原子性。
2. `select_entries` schema 把 `entry_ids` 标为必填，但 description 声称 `action=clear` 时无需提供，条件参数契约不一致。

### 3.4 FR9.3 Translator

已实现：

- 后台启动翻译和润色；翻译/后处理使用 TaskManager。
- stop/pause/resume/get_status。
- 配置查询、scope、术语配置。
- key 主索引语义基本已迁移。

主要偏差：

1. `set_translation_config(profile=...)` 把 profile URL 写入局部 `args['base_url']`，但真正保存字段循环不包含 `base_url`，所以只切 profile 会返回“未做任何修改”，端点没有改变。
2. translator 的 schema 没有套用 `@validate_params`；错误类型可能在方法内部造成异常或被静默忽略。
3. scope 的 `action=exclude/only` 没有参与 `resolve_scope_to_entry_ids()` 和 preview 计算；当前只是保存字段，实际筛选始终按 include 处理。
4. `mode=polish/mixed` 的 `start_translation` 仍走 AutoTranslator；description 甚至写明 mixed 同 translate，与 FR9 的翻译/润色/混合语义不一致。
5. Controller 构造器声明注入 AppContext/TaskManager，但方法实际重新获取 TaskManager，`self._ctx` / `self._task_mgr` 从未使用；模块级全局 Controller 又在首次调用时创建一个新的 AppContext。该“依赖注入”是装饰性的，没有形成真实 composition root。
6. TaskManager 为进程级单例，`stop_task` 不传 task_id 会停止所有 session/project 的任务，不符合 ADR-008 中 AgentInstance 可绑定多个项目的隔离意图。

### 3.5 FR9.4 Proofreader

Story 25 将早期 5 个不可运行工具统一为 `run_postprocess`，方向正确。当前后处理主链比 Parser/Writer 更完整：

- 使用真实 `PostProcessor.process_entries()`。
- 创建 LLMClient、TermDatabase、默认 checker。
- 支持阶段、entry_ids、max_workers。
- TaskManager、暂停/恢复、checkpoint、报告均已接线。

仍需修订：

1. proofreader 工具没有统一参数装饰器；`phases` 若不是 list，错误行为依赖 Python 迭代语义。
2. stop_event 触发时，PostProcessor 正常返回 partial result；外层仍删除 checkpoint、生成报告并把任务标为 `completed`，而不是 `cancelled`。
3. `_last_report` 是进程级模块变量，不按 session/project/task 隔离；多个并发项目的“最近报告”会互相覆盖。
4. checkpoint 路径依赖 ESP；EET/XT/JSON 来源无法获得相同的断点能力。
5. `list_quality_reports` 返回目录路径，与其他状态工具强调不泄露完整路径的安全策略不一致。

### 3.6 FR9.5 ParaTranz

9 个工具已注册，mock API 测试基本覆盖错误路径和简单返回。但核心任务契约没有满足：

- `upload_entries`、`download_entries`、`export_artifact` 标记 `is_long_running=True`，却在调用线程同步执行。
- 没有 TaskManager 注册、task_id、进度、停止、暂停、状态更新。
- upload 逐条调用 API，数量大时会长时间阻塞且缺少统一限流/批处理。
- export 在当前调用线程中每 2 秒 sleep，最长 30 秒。
- download 不合并到 AppContext 集合；返回只含 count/diff_summary，description 却声称返回 `entries`。
- FR9.5.4 要求返回合并结果（新增/更新/未变），当前没有执行合并。
- schema 中大多数 `project_id` 声明为 `str`，需求和 switch 工具使用 `int`。
- `download_entries` 的确认不是“先比较、再带摘要确认”；当前只是通用 permission confirmation，确认时还没有 diff 摘要。
- 401/403、超时重试等需求没有抽象为统一错误策略。

### 3.7 FR9.6 Writer

当前已按 Story 19 合并为一个 `write_back(target=...)`，但真实实现仍不闭合：

1. `EETWriter` 的真实构造器要求 `EET_XmlParser`，代码却调用 `EETWriter()`。
2. `XTWriter` 的真实构造器要求 `XT_XmlParser`，代码却调用 `XTWriter()`。
3. 两个实现直接调用 `writer.write(collection, path)`；真实 API 是先 `apply_collection(collection)`，再 `write(path)`。
4. ESP/strings 依赖 `slot.plugin` 和 `slot.strings_lookup`；Parser 的 `_create_slot()` 没有保存它们。
5. EET/XT 依赖 `ctx.eet_path/xt_path`；Parser 创建的 Slot 没有保存这些路径。
6. Writer 标记 `is_long_running=True`，但实际同步执行，也不返回 task_id。
7. Writer 使用与 Parser 相同的 `_validate_path()`，会拒绝所有绝对路径；桌面 GUI 的 QFileDialog 返回绝对路径，这使“共享同一真实路径”不可能成立。
8. 错误消息直接包含异常文本，可能泄露完整路径；Parser 有 `_sanitize_error`，Writer 没有统一策略。

### 3.8 FR9.7/9.8 状态查询

工具存在，但状态准确性受双状态源影响：

- `get_current_filters/get_app_state` 返回 AppContext.filter_state，不是 Step2 实际控件状态。
- `get_statistics` 不含需求所写的标签分布。
- `list_local_projects` 只返回目录名，缺版本数和最后打开时间。
- `get_current_project` 只返回 name/variant/collection，缺路径、版本列表、源文件列表和集合摘要。

这些工具不是完全不可用，但返回结构明显低于需求。

### 3.9 FR9.9 Agent 与 namespace

这是文档完成度和运行时完成度差距最大的部分之一。

#### 启动顺序缺陷

`ui/app.py` 当前顺序：

1. `AgentRegistry.init_presets()`。
2. `register_all_tools()`。

而 `AgentRegistry.register()` 会在注册时立即把 `namespace:*` 展开为当前 ToolRegistry 的工具名。工具尚未注册时，translator/editor/parser/paratranz/writer/proofreader 的 wildcard 会展开为空。后续注册工具不会刷新 AgentSpec。

测试没有发现该问题，因为测试导入工具模块后才调用 `AgentRegistry.init_presets()`。

#### Agent 运行时未接入

- 生产代码没有创建 `AgentInstance`。
- ConversationOrchestrator 构建的是无 namespace 的 system prompt。
- GraphExecutor 只有在 step 带 `_instance` 时才按 Agent namespace 查工具，但生产路径没有注入 `_instance`。
- AgentSpec.tools 基本没有被执行路径用作授权集合。
- proofreader Agent 写入的 `translator:get_task_status` 是带 namespace 前缀的字符串，但 ToolRegistry 的实际工具名是 `get_task_status`；GraphExecutor 又按 proofreader namespace 查找，跨 namespace 引用没有统一解析协议。
- Orchestrator 所谓 7 个“元工具”只出现在 system_prompt 文本中，没有对应 ToolSpec 或真实 dispatcher。

因此当前 7 个 Agent 是“注册表中存在的角色定义”，不是“可执行的专业 Agent”。

### 3.10 FR9.10 异常、边界与安全

已实现部分：ToolResult、Guard、100KB 输出限制、部分分页、路径遍历检测、敏感字段脱敏。

偏差：

- `validate_params` 并未覆盖所有工具。
- GraphExecutor 直接调用 `spec.execute()`，ToolExecutionHandler 走 `execute_with_guardrails()`，两条 GUI 路径不同。
- InputValidationGuard 使用参数名启发式判断路径，且禁止所有绝对路径；这是“字符串模式检查”，不是“授权路径检查”。
- Unix 绝对路径测试在 Windows 失败。
- 相对路径可以逃逸的判定依赖字符串形式，不能替代 canonical resolve + allowed roots。
- 大多数 write 方法缺少事务/回滚；典型例子是 edit_translation 失败后留下部分修改。
- long_running 只是一项元数据，没有被基础设施强制验证。

### 3.11 FR9.11/9.12

- 搜索 6 字段基本已实现，旧 `text` 兼容仍在 filter_entries 中。
- ParaTranz project query/switch 已存在，但 project_id 类型不一致。
- Parser action 已存在，但 6 工具变成 5 工具；同名覆盖 HITL、文件选择 HITL、成功解析与源信息保存均未完成。

## 4. ADR、Plan、Story、Changelog 一致性审查

### 4.1 ADR 中的关键冲突

#### ADR-002：单一数据中枢没有落实到 GUI

ADR-002 宣称 TranslationEntryCollection/AppContext 是数据中枢，工具层也已改用 key。但 Step2 的筛选/标签仍为自身私有状态，且仍以 id 存标签，造成第二数据源。ADR 需要补充“视图状态、标签状态、选择状态的唯一所有者”和迁移规则。

#### ADR-004：异步模型与现实不一致

ADR-004 以 QThread/Qt 信号为主；FR9 又引入 threading.Thread + TaskManager。当前 Translator/Proofreader 用线程，ParaTranz/Writer 同步，GraphExecutor 用线程池，形成四套生命周期。ADR 应升级为“纯 Python JobRuntime + Qt Adapter”，而不是继续按工具单独决定线程模型。

#### ADR-008：Controller 重构没有形成真正分层

Controller 构造注入的依赖未使用，模块级 wrapper 创建新的 AppContext，GUI/Agent/MCP 仍各自直接组装业务组件。ADR 需要明确：

- Controller/Tool 模块只能做通道适配，不拥有业务流程。
- 业务流程进入 application use case。
- 全部依赖从 composition root 注入。
- 禁止模块级 AppContext/Controller 单例。

#### ADR-012：MCP 设计与实现偏离

当前 MCP 问题：

- `ui/app.py` 使用未导入的 `ToolRegistry`。
- MCPAdapter 未传 AppContext，之后也未调用 set_context。
- MCPServer 未收到 mcp config/auth token。
- adapter 的 JSON Schema 直接输出 `str/int/list/dict`，不是 JSON Schema 的 `string/integer/array/object`。
- adapter 只把 ToolResult.message 返回给 MCP，data/failed_items/pagination 全丢失。
- admin whitelist 即使可见，PermissionGuard 仍永久阻断；write policy allow 也无法执行 `require_confirmation=True` 的 write 工具。
- `select.select([sys.stdin])` 在 Windows stdio 上存在兼容风险。

ADR-012 应重新定义 MCP 的生命周期、认证、批准令牌、结果序列化和跨平台 stdio。

### 4.2 Plan/Story 状态漂移

- Plan 顶部写“26 Story 全部完成”，但 Story 01–15 多数头部仍是“已确认”，Story 16–25 多数仍是“已方案”，只有 Story 26 明确写“已实现”。
- 所有 Story 验收 checkbox 基本仍是 `[ ]`，没有形成逐项验收证据。
- requirements FR9 概述写“S22 待编码”，Plan/INDEX/changelog 又写 S22 已完成。
- Story 24 仍要求 6 个 Parser 和 import_strings，代码和后续 changelog 已删除 import_strings。
- FR9.9.5 要求 v1 工具保持兼容，后续 changelog 直接删除 v1 工具，需求未更新为 superseded。
- Story 12 说 Parser read，Story 24 改成 write；最终代码是 write，但 Plan 前部保留了旧描述。
- Story 12 说 4 个 Writer + deprecated write_back，Story 19 又反向合并成 1 个 write_back；原 Story 没有标记被 supersede。

Changelog 本身较完整，能够追踪多轮修复和合并；问题是没有“当前有效版本”索引，导致历史方案和现行方案并存且互相矛盾。

### 4.3 建议的文档治理规则

1. Requirement 每个子条目增加 `status`、`superseded_by`、`acceptance_evidence`。

## 5. 问题优先级

### P0：阻断主成功链或造成文档“完成”与产品不可用

#### P0-1 Parser 四种核心格式成功链不可运行

**证据**：`tool_parser.py:126-189` 与真实 parser API 不匹配。  
**影响**：Parser Agent 的 ESP/EET/XT/SST 工具注册存在但实际失败。  
**修复门槛**：四种真实最小夹具均能创建带完整 source metadata 的 Slot。

#### P0-2 Parser → Writer 闭环断裂

**证据**：Parser Slot 不保存 plugin/parser/source_path；Writer EET/XT 构造和调用 API 错误。  
**影响**：即使修好解析，Agent 写回仍失败。  
**修复门槛**：每种可写格式完成 parse → edit → write → reparse roundtrip。

#### P0-3 AppContext 与 Step2 双状态源

**证据**：Step2 仍有 `_label_library/_entry_labels`，无 filter/label signal 订阅。  
**影响**：Agent 的筛选/标签操作和用户界面互相不可见，持久化也不一致。  
**修复门槛**：GUI 和 Agent 对同一 state store 读写；双向契约测试通过。

#### P0-4 AgentRegistry 初始化顺序使 wildcard 工具集为空

**证据**：`ui/app.py` 先 init_presets，后 register_all。  
**影响**：专业 Agent 注册后可能没有任何 namespace 工具。  
**修复门槛**：先构建 ToolCatalog，再构建 AgentCatalog；启动校验所有 ToolRef 可解析。

#### P0-5 MCP 启动和执行通道不可用

**证据**：未导入 ToolRegistry、无 ctx、Server config 丢失、Schema 类型无效、结果 data 丢失。  
**影响**：启用 MCP 时启动失败或全部工具不可实际使用。  
**修复门槛**：Windows stdio 进程级 smoke：initialize/list/call read/write-deny/auth 全通过。

### P1：核心语义错误、任务生命周期或安全契约不完整

#### P1-1 ParaTranz 伪 long-running

同步执行且无 task_id/cancel/progress；download 不合并。应迁移到统一 JobRuntime。

#### P1-2 `set_translation_config(profile)` 实际不切换端点

profile URL 未写入 LLMConfig.base_url。需增加配置持久化正向测试。

#### P1-3 参数 Schema 不统一执行

除 editor 外，多数域只“注册 schema”但不“执行 schema”；MCP JSON Schema 又映射错误。应统一 ToolInvoker。

#### P1-4 HITL 只有通用权限确认，没有业务预览

Parser 同名覆盖、下载 diff、force overwrite、批量标签都需要 prepare/preview/confirm/execute，而非执行前通用弹窗。

#### P1-5 失败非原子

edit_translation 可返回失败却已改译文；批量写操作缺事务或 MutationResult。需要 command 层先校验后提交。

#### P1-6 Agent 角色没有实际运行时

AgentInstance 未在生产创建，tool access 未被强制。需要实现轻量 AgentDispatcher，或正式修改需求为“namespace 路由而非多 Agent”。

### P2：维护性、扩展性和跨项目隔离问题

- TaskManager 进程级单例，不按 session/project 隔离。
- 模块级 Controller 和 `_last_report` 形成隐藏全局状态。
- `get_handle()` 返回可变句柄后在锁外修改，线程安全边界不清晰。
- filter_entries 每次分页全量扫描；多页为 O(N×pages)。
- 工具 description、返回结构、代码行为没有机器校验。
- `is_long_running` 只是标记，基础设施不验证“必须立即返回 task_id”。
- Path guard 禁绝对路径与桌面应用实际文件选择冲突。
- GraphExecutor 和 ToolExecutionHandler 有两套 Guard/HITL 调用方式。
- proofreader 最近报告/TaskManager/AgentRegistry 均为进程全局，破坏多项目并行设想。

### P3：文档、命名和体验债务

- requirements/Plan/Story/INDEX 的工具数、Story 状态不一致。
- Story checkbox 未回填。
- `entry_id` 参数实际含义是 key，命名仍误导；建议统一为 `entry_key(s)`，旧名只做兼容别名。
- scope 的 include/exclude/only 描述与实际语义不一致。
- `list_quality_reports` 暴露 directory，而其他工具强调路径脱敏。
- tool_v1 文档写的替代工具名与当前注册目录部分不一致。

## 6. 三种迭代方案

### 方案 A：就地修补当前工具层

**做法**：直接修 Parser dispatch、Writer 构造、AppContext/Step2 信号桥、启动顺序、MCP ctx；为缺失成功链补测试。

**优点**：

- 迭代最短。
- 对当前文件结构侵入小。
- 可以快速解除 P0。

**缺点**：

- GUI、Agent、MCP 仍各自拼装 parser/writer/translator。
- Controller/TaskManager/Guard/HITL 分叉继续存在。
- 下一次新增格式或通道时会再次复制逻辑。

**适用**：只为短期发版止血。  
**建议**：可以作为 Phase 0，但不应成为最终架构。

### 方案 B：Application Use Case + Ports/Adapters（推荐）

**做法**：把解析、编辑、翻译、后处理、ParaTranz、写回定义为 channel-neutral application use cases；GUI、Agent Tool、MCP 只做适配。引入统一 ToolInvoker、PathAccessPort、ConfirmationPort、JobRuntime、SessionStateStore。

**优点**：

- GUI/Agent/MCP 共享同一真实成功链。
- 参数、HITL、权限、任务、错误、返回 schema 只实现一次。
- 易于逐工具迁移，不要求大爆炸重写。
- 最符合 ADR-008 的分层目标。

**缺点**：

- 需要 3–5 个迭代完成核心迁移。
- 迁移期存在旧路径和新路径并行，需要 contract tests 防漂移。

**适用**：作为后续版本的主架构。  
**结论**：推荐。

### 方案 C：全量 Command Bus / Actor / Event Sourcing

**做法**：全部工具变成命令，通过 command bus/actor 按 session 执行，状态变更记录为事件，GUI 和 Agent 订阅投影。

**优点**：

- 天然支持审计、撤销、并发项目、远程控制。
- HITL 和长任务状态机表达力最强。

**缺点**：

- 对当前桌面应用明显过重。
- 迁移范围覆盖持久化、UI、工具、任务、测试。
- 容易把“修通 FR9”扩大成全项目重写。

**适用**：未来确实要做多用户/远程服务/协同编辑时再考虑。  
**结论**：当前不推荐。

## 7. 推荐目标架构

```text
GUI Actions / Agent Tools / MCP
              │
              ▼
        Channel Adapters
              │
              ▼
          ToolInvoker
  ┌───────────┼────────────┐
  │ Schema    │ Permission │ Result serialization
  │ Validation│ + HITL     │ + Observability
  └───────────┼────────────┘
              │
              ▼
      Application Use Cases
  Parse / Edit / Translate / PostProcess
  ParaTranz / Write / Query / Project
              │
     ┌────────┼─────────┬──────────┐
     ▼        ▼         ▼          ▼
SessionState Format   JobRuntime PathAccess
Store        Adapters            + Grants
     │        │         │          │
     ▼        ▼         ▼          ▼
Collection  ESP/EET   worker     filesystem
+ labels    XT/SST    + events   authorized roots
```

### 7.1 SessionStateStore：消除双状态源

建议引入 `WorkspaceSession` 或把 AppContext 明确升级为唯一状态仓库，至少包含：

- active_collection / slots。
- filter_state。
- label_library / entry_labels（统一以 entry.key 为主键）。
- selected_keys。
- translation_scope。
- active_project / paratranz_project。

Step2 不再拥有独立业务状态，只通过 Presenter/ViewModel 展示和派发 command。VariantStore 只做 SessionStateStore 的持久化 adapter。

### 7.2 FormatAdapterRegistry：统一 Parser/Writer

定义：

```text
FormatAdapter
  probe(path) -> FormatInfo
  parse(ParseRequest) -> ParsedDocument
  write(WriteRequest, ParsedDocument, Collection) -> WriteResult
```

`ParsedDocument` 必须保存：

- source_type。
- canonical source_path。
- collection。
- parser/document model。
- plugin / strings_lookup / language。
- write capabilities。

GUI Step1、Parser Agent、FOMOD 如需解析，都调用同一个 adapter registry，不能自己拼类名和方法名。

### 7.3 ToolInvoker：单一工具执行入口

ToolInvoker 负责：

1. ToolRef 解析（namespace + name）。
2. 请求 DTO/Schema 校验。
3. session 和 capability 检查。
4. prepare/preview。
5. HITL approval token 校验。
6. use case 调用。
7. ToolResult 标准化、脱敏、截断和 observability。

GraphExecutor、ReAct、MCP 都必须调用 ToolInvoker，不能再直接 `spec.execute()`。

参数层建议使用 typed request DTO（dataclass + 显式 validator）；若接受新依赖，可评估 Pydantic v2 自动生成 JSON Schema。不要继续维护 `str/int/list` 的半 JSON Schema 方言。

### 7.4 两阶段 HITL

高风险工具改为：

```text
prepare(request)
  -> Preview(summary, affected_count, diff, cost_estimate, approval_hash)

execute(request, approval_token)
  -> Result
```

适用：Parser 覆盖 Slot、批量标签、翻译费用、ParaTranz upload/download、Writer。

MCP 没有 UI 时：

- 默认 deny；或
- 只接受用户预先签发、绑定 request hash/expiry/tool/session 的一次性 approval token。

这样可以避免“admin whitelist 可见但永远无法执行”和确认时没有业务摘要的问题。

### 7.5 PathAccessPort：用授权替代禁绝对路径

不要再把绝对路径视为攻击。桌面文件选择必然产生绝对路径。正确模型：

1. canonical resolve。
2. GUI/HITL 选择文件时生成 `FileAccessGrant`。
3. MCP 使用显式 allowed roots 或 grant token。
4. 校验 resolved path 是否在 grant scope 内。
5. 写入使用 staging + atomic replace，避免破坏源文件。

### 7.6 JobRuntime：统一长任务

所有 `is_long_running=True` 工具必须满足：

- 调用在 200ms 级返回 `JobAccepted(task_id)`。
- JobRuntime 维护 state、progress、result、error、cancel、pause capability。
- Qt adapter 把 JobEvent 转成 signal。
- Agent/MCP 通过 get_task_status/subscribe 查询。
- task 绑定 session_id/project_id，stop all 只影响当前 session。

优先迁移 ParaTranz export/upload/download、Writer、Translator、Proofreader。

### 7.7 轻量 AgentDispatcher

如果保留 FR9 的 7 个专业 Agent，推荐实现轻量 dispatcher，而不是恢复独立 QThread AgentWorker：

- AgentDefinition 持有 `allowed_tool_refs: set[ToolRef]`。
- Graph step 指定 agent_id。
- Dispatcher 构建 AgentRunContext(session_id, agent_id, allowed_tools)。
- ToolInvoker 强制校验 ToolRef 属于 allowed set。
- 并行仍由 GraphExecutor/JobRuntime 负责，不为每个 Agent 再创建一套线程模型。

如果产品并不需要真正专业 Agent，则应修改 FR9 为“namespace 路由”，删除 AgentRegistry 假抽象。两者必须明确选择，不能继续保留仅注册不执行的中间状态。

## 10. 推荐迁移顺序

### Phase 0：立即止血

1. 将 FR9 状态从“全部完成”改为“部分实现/整改中”。

### Phase 1：建立共享业务入口

2. 引入 FormatAdapterRegistry。
3. 让 GUI 先调用 Parse/Write use case，证明共享入口覆盖现有功能。
4. Agent Parser/Writer 迁移到同一 use case。

### Phase 2：统一执行协议

1. ToolInvoker + typed DTO + ToolRef。
2. prepare/preview/approval HITL。
3. Graph/ReAct 路径迁移到 ToolInvoker。

### Phase 3：统一异步与外部通道

1. JobRuntime。
2. ParaTranz 迁移。

## 11. 建议的质量门禁

### Gate A：Catalog

- 所有 ToolRef 唯一。
- 所有 Agent ToolRef 可解析。
- 所有 ToolSpec schema 可生成合法 JSON Schema。
- 所有 description 的返回字段都能由 result contract 验证。

### Gate B：State parity

- GUI 操作后 Agent 查询一致。
- Agent 操作后 GUI 和持久化一致。
- id/key 迁移无双写分叉。

### Gate C：Format roundtrip

- ESP/EET/XT/strings：parse → mutate → write → parse。
- SST/JSON：parse/import 正向夹具。
- 失败时原文件 hash 不变。

### Gate D：Long-running

- 每个 long-running 工具 200ms 内返回 task_id。
- cancel/pause capability 与工具描述一致。
- completed/cancelled/failed 状态不混淆。
- session 隔离。

### Gate E：Channels

- GUI/ReAct/Graph/MCP 通过相同 ToolInvoker。
- MCP Windows 子进程 smoke。
- MCP 返回完整 data，而不只是 message。

### Gate F：Traceability

- 每条 SHALL 有测试/人工验收证据。
- 未通过的 SHALL 不允许需求状态变成“已实现”。

## 12. 最终建议

FR9 当前最应该做的不是继续增加工具数量，也不是继续重写 description，而是把已有 42 个工具从“注册表能力”升级为“共享真实业务能力”。推荐采用方案 B：

1. 以 SessionStateStore 消灭 AppContext/Step2 双状态。
2. 以 FormatAdapterRegistry 修通 Parser/Writer。
3. 以 ToolInvoker 统一 schema、权限、HITL、错误和结果。
4. 以 JobRuntime 修通 Translator/Proofreader/ParaTranz/Writer 的任务生命周期。
5. 以轻量 AgentDispatcher 让 7 个 Agent 真正形成执行边界。
6. 最后再开放 MCP，并用进程级测试验收。

短期可以先就地修复 P0，但中期必须把 GUI、Agent、MCP 收敛到同一 application use case，否则每次新增格式、平台或工具都会再次产生“GUI 能用、Agent 注册了但不能用、MCP 又是另一套”的分叉。

本审查建议将 FR9 的发布门槛从“工具数量/测试通过数”改为以下一句话：

> **每个工具必须至少有一条从真实输入，经统一 use case，到真实状态变化或输出工件的成功链；GUI、Agent、MCP 只允许成为同一成功链的不同适配器。**

## 13. ParaTranz JSON 工具调整

用户的主要使用场景要求显式导入/导出 ParaTranz JSON，现有通用 `import_json` 不应继续承担格式猜测和双 ID 映射。

FR9 V2 应增加：

- `import_paratranz_json(path, conflict_policy)`；
- `export_paratranz_json(path, include_external_ids)`；
- 参数和结果使用 typed schema，报告 total/imported/duplicate_key/missing_key/invalid_stage/external_id_count；
- 工具内部调用同一个 `ParaTranzJsonAdapter`，不得自行映射字段；
- `key` 是本地 EntryKey，ParaTranz `id` 只作为 external ref；
- GUI、Agent、MCP 对同一 fixture 输出一致 digest；
- write/export 工具仍遵循 PathAccessPort、HITL 和原子文件输出。

该 Story 应排在继续增加其他 JSON 工具之前，并成为 Tool Catalog/FormatAdapter contract 的验收样例。详见 [专项调整](paratranz-json-compatibility-adjustment.md)。
