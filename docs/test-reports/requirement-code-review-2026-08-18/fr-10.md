# FR10 智能助手超重文件拆分——纵向实现与迭代设计审查

> 审查日期：2026-08-18  
> 审查方式：独立纵向审查（requirements → ADR → Plan → 全部 Story → changelog → 当前源码 → tests）  
> 审查范围：FR10 及其在当前代码中的后续演化；未修改业务代码、需求、ADR、Plan 或 Story  
> 结论等级：**部分实现，结构搬迁已完成，但“降低耦合、消除全局状态、形成清晰边界”的核心目标没有完成**

## 1. 执行摘要

FR10 确实完成了一批可验证的机械性拆分：`ExecutionEngine` 变成 83 行门面，条件求值和 checkpoint 被提取，`tools/base.py` 的类型被搬到 `types.py`，三个工具模块出现了 Controller 类，`MemoryWriterThread` 也被独立成文件。这些改动降低了若干单文件的局部认知负担，并保留了旧 import 路径。

但从当前代码的依赖、状态所有权和运行契约看，FR10 的真实完成度不能判为“已完整实现”：

1. **Controller 封装主要是函数搬入类，没有建立真正的依赖注入。** 三个 Controller 都保存了构造器参数，但 `TranslationController` 和 `ProofreaderController` 在业务方法里仍重新调用 `TaskManager()`；三个模块又各自通过模块级全局变量惰性创建 Controller，并直接从后端导入 `ui.context.AppContext`。这与 ADR-008 所宣称的“消除全局单例、构造器显式注入、后端不依赖 UI”相反。
2. **上帝类被转移到了 `GraphExecutor`，没有真正拆解执行职责。** 当前 `graph_executor.py` 为 606 行、22 个方法，同时承担节点调度、并发、护栏、重试、HITL 等待、生命周期、回调、DAG 转换和 checkpoint 编排。原需求的“最大文件 <400 行”已被 Plan/ADR 事后放宽并绕过。
3. **图执行存在未被现有测试覆盖的状态机/语义风险。** pause 的 `Event` 用法不会阻塞；checkpoint 被读取但未恢复结果或恢复位置；Condition 节点递归执行选中分支后，BFS 又可能沿其所有出边调度，条件分支存在重复/双分支执行风险。
4. **后续 FR12–FR14 的演化再次暴露边界不稳。** `ConversationOrchestrator`、`SessionController`、`ChatWidget` 同时保留 `react_depth`/`auto_mode`；Orchestrator 仍持有大量 UI 形态回调，ChatWidget 当前达到 1239 行/68 方法。FR10 为后续扩展“扫清基础”的目标只部分成立。
5. **文档状态不可信。** Requirements、Plan、Story 都标注“已实现”，但所有验收复选框仍为未勾选；原 requirements 与后来的 ADR/Plan 在行数、TaskManager API、注册方式上互相冲突；当前测试也不是全绿。

推荐下一轮不要继续以“按行数切文件”为主，而采用**应用服务 + 端口适配器 + 单一 composition root** 的渐进式方案：工具模块只保留协议适配，业务用例进入可注入服务；每个 App/Session/Task 的状态生命周期明确；GraphExecutor 拆成 Scheduler、NodeHandler、CheckpointStore、ExecutionLifecycle；Qt 只存在于 UI adapter。该方案能同时服务 GUI、Agent 和 MCP，且可逐工具迁移，不需要大爆炸重写。

## 3. 需求—ADR—Plan—Story—代码—测试映射

### 3.1 FR10.1 ExecutionEngine 上帝类拆分

**实现证据**

- `execution_engine.py:12-83` 已成为对 `GraphExecutor` 的委托门面。
- `condition_evaluator.py` 和 `checkpoint_manager.py` 已存在。
- `StepResult` 已迁移到 `graph_executor.py:18` 并由旧路径重导出。
- changelog 完整记录了 888 → 610 → 84 行的迁移过程。

**偏差**

- FR10 原文要求 `ExecutionEngine` 保留图执行、生命周期、护栏/重试，目标约 350 行；最终 Plan 改为把这些职责整体搬入 606 行的 `GraphExecutor`。这是方案变更，不是原需求的原样实现。
- Requirements 的全局目标是“最大文件 <400、最大类方法数 <20”，ADR 后来改为 ≤450/≤22，但 `GraphExecutor` 仍为 606 行。Plan 甚至把“606 行”写成验收标准，导致验收标准为实现现状让路。
- `ExecutionEngine.__getattr__` 代理私有属性，使测试和 UI 继续穿透门面访问 `GraphExecutor._executor._executor`（例如 `chat_widget.py:677-679`）。门面没有建立稳定抽象，反而固化了内部结构。

**运行契约问题**

- `graph_executor.py:473-476`：当 `_paused` 已 set 时调用 `_paused.wait()` 会立即返回；`threading.Event.wait()` 是“等待变为 set”，不是“等待 clear”。当前 pause 不会暂停执行。
- `graph_executor.py:466-470`：加载 checkpoint 后只取 `completed_results.keys()`，没有把结果恢复到 `results`，也没有用 `current_node_id` 设置 pending/visited。
- `graph_executor.py:483-485`：每层保存时始终把 `graph.entry_node` 当作 `current_node_id`，无法表示真实恢复点。
- `checkpoint_manager.py:29-40` 将 `StepResult` 序列化为 dict；`Checkpoint.from_dict()` 不重建 `StepResult`，即使未来恢复到 `results` 也会存在类型不一致。
- `graph_executor.py:364-370` 的 ConditionNode 会递归执行选中分支；随后 `graph_executor.py:445-452` 又按“from_node 已 visited”收集所有非 loop_back 出边，不看条件选择，存在双分支/重复执行风险。
- 当前 `test_execution_engine.py` 只验证线性图、单节点、结果顺序、取消上界、Event 是否为实例字段等；没有覆盖上述核心语义。

**完成度**：**55%（结构拆分完成，核心图状态契约未闭环）**。

### 3.2 FR10.2 base.py 类型与逻辑分离

**实现证据**

- `tools/types.py` 包含要求的 5 个类型；`tools/base.py:26-28` 保留重导出。
- `base.py` 当前 273 行，低于 Plan 的 300 行目标。
- 旧 `from tools.base import ToolResult, ExecutionContext` 路径仍可用。

**偏差与设计债**

- `types.py` 并非“纯类型定义”。`ExecutionContext.safe_mutate()`、`notify_collection_modified()`、`__getattr__()`、`__setattr__()` 包含 UI 主线程调度、Qt signal 发射和动态 AppContext 代理行为（`types.py:216-322`）。这只是把复杂逻辑从 `base.py` 移到了名为 `types.py` 的文件。
- `ExecutionContext.app_context/task_manager` 均为 `Any`，动态代理允许工具访问任意 AppContext 属性。依赖没有被类型系统或协议显式表达，工具的真实能力边界仍不可见。
- `_FORWARDED_ATTRS` 是手工维护的白名单，新增共享状态时容易遗漏；直接修改 entry 对象后还要调用 `notify_collection_modified()`，领域变更和 UI 刷新耦合。

**完成度**：**80%（文件级拆分完成，类型层/应用层边界未形成）**。

### 3.3 FR10.3 工具模块 Controller 封装

这是 FR10 当前最严重的“形式完成、目标未完成”部分。

**实现证据**

- 三个 Controller 类都已创建，原工具函数主体大多迁为实例方法。
- `_common.load_llm_config()` 已存在。
- 兼容 `_tool_*` wrapper 保留，现有大量私有函数测试没有 import 断裂。

**与 ADR/Story 的直接冲突**

- ADR-008:329 要求 `_register_*_tools()` 创建 Controller 后将实例方法注册到 `ToolSpec.execute`；当前注册的仍是模块级 wrapper。
- ADR-008:331 声称通过 Controller 消除 AppContext/TaskManager 全局单例；当前存在：
  - `tool_translator.py:576-585` 的 `_translator_ctrl`；
  - `tool_proofreader.py:414-423` 的 `_proofreader_ctrl`；
  - `tool_editor.py:376-385` 的 `_editor_ctrl`；
  - 三个 getter 均直接构造 `AppContext()` 和全局 `TaskManager()`，且后端反向 import `src.transbridge.ui.context`。
- `TranslationController.__init__` 保存 `self._task_mgr`，但 `start_translation`、`start_polish`、`stop_task`、`get_task_status` 都重新调用 `TaskManager()`（`tool_translator.py:90,204,303,350`）。注入的 TaskManager 实际未被使用。
- `ProofreaderController.run_postprocess` 同样在 `tool_proofreader.py:135` 重新调用 `TaskManager()`。
- 三个 Controller 中 `self._ctx` 目前基本是冗余字段；运行时又依赖动态 `ctx`。形成“两套上下文”，而不是清晰依赖。
- `tool_proofreader.py:27-41` 保留模块级 `_last_report`；`tool_translator.py:261-263` 跨模块写它。报告状态是整个进程共享，而不是 App/Project/Session/Task 作用域。
- 三个源文件当前为 715/461/451 行，只有类名变化，没有把配置、后台任务、查询、报告、注册 metadata 等不同职责分离。
- `_common.py` 只有 6 行，仅把 `LLMConfig.load_from_file()` 再包一层，未形成可替换的 ConfigProvider，也没有消除 start_translation 中的直接配置加载。

**为什么这是文件搬迁而非有效封装**

真正的封装至少应满足：依赖只能从构造器进入；实例有明确生命周期；全局状态被移除或集中到显式 store；注册层不穿透到 UI；单测可注入 fake 并观测调用。当前四点均未满足。Controller 只是 wrapper 后面的另一个调用层。

**完成度**：**35%（代码形状完成，架构意图大部分未完成）**。

### 3.6 FR10.6 TaskManager 精简

**实现证据**

- `on_finished/notify_finished` 已增加；旧完成/失败方法保留为兼容 wrapper。

**需求—Plan 冲突**

- Requirements 要移除 `set_main_thread_dispatcher/reset_dispatcher`、内联 `get_handle`，同时又要求“所有公开 API 签名不变”，两者逻辑上冲突。
- Plan/ADR 后来根据活跃调用方决定保留这些方法，但没有回写 requirements。因此“FR10 已实现”没有单一可判定基线。

**当前设计债**

- `TaskManager` 仍通过 `__new__` 实现进程级单例，`_dispatcher` 也是类级全局状态。
- Controller 和 `ToolExecutionHandler` 随处直接 `TaskManager()`，任务归属无法表达为 App、Session、Project 或 Execution。
- 旧 listener wrapper 每次注册都会创建匿名闭包；`remove_listener(callback)` 很难用原 callback 移除 wrapper，存在监听器泄漏/重复通知风险。
- `TaskManager` 当前 348 行、25 方法，仍同时负责注册表、线程创建、进度、暂停、取消、回调、dispatcher 和清理。

**完成度**：**60%（API 合并完成，生命周期和状态边界未改善）**。

## 4. 优先级问题清单

### P0：应先修复或建立阻断门禁

1. **Graph pause 语义错误**：`Event.set()` 后 `wait()` 立即返回，暂停无效。
2. **Checkpoint 恢复不生效**：读取结果未回填，恢复位置未使用，保存位置固定为 entry node。
3. **条件分支可能执行双分支/重复执行**：递归 dispatch 与通用 BFS 出边推进并存。
4. **Controller 注入是假的**：方法重新获取全局 `TaskManager()`，测试无法替换；模块还直接创建 UI `AppContext()`。
5. **测试门禁不覆盖关键执行语义**：当前“结构重构零行为变化”没有 characterization/golden tests 支撑。

### P1：下一迭代应完成的架构修正

1. 建立唯一 `AssistantRuntime`/composition root，明确 App、Session、Execution、Task 四种生命周期。
2. 后端包禁止 import `src.transbridge.ui.*` 和 PyQt6；Qt 事件投递进入 adapter。
3. 工具函数改为薄适配器，业务流程下沉到 application services；GUI、Agent、MCP 复用同一用例。
4. 拆分 GraphExecutor：Scheduler、NodeHandlers、CheckpointStore、Lifecycle/Cancellation、ExecutionEventSink。
5. 把 `_last_report` 改为显式 `QualityReportRepository`，按 project/session/task key 存储。
6. 收口 ReAct/auto mode 所有权到 SessionController，删除 Orchestrator/ChatWidget 的重复状态和死回调。

### P2：质量与可维护性

1. `ExecutionContext` 改为显式 capability protocols，不再动态代理整个 AppContext。
2. 注册 metadata 与实现分离，避免 700 行文件同时容纳业务流程、schema、长描述和兼容 wrapper。
3. 建立静态依赖门禁、模块级可变状态门禁、复杂度/扇出门禁；行数只作为提示而非首要验收。
4. 将 Plan/Story 复选框与测试证据、changelog、commit/文件链接同步，避免“状态已实现但验收全未勾选”。
5. 修复可复现开发环境：重建 `.venv`，确保 `uv run` 与声明依赖一致。

### P3：后续优化

1. 删除已过渡完成的兼容重导出和私有属性穿透。
2. 将回调列表替换为具名事件协议，统一观察性和错误模型。
3. 为工具 namespace 生成注册表，减少手写 schema/description 与实现漂移。

## 5. 可选优化方案与取舍

### 方案 A：最小修补，保留当前 Controller + wrapper

做法：修 GraphExecutor 的 pause/checkpoint/condition；把 Controller 内的 `TaskManager()` 全部替换成 `self._task_mgr`；由启动入口显式调用 `configure_controllers(app_context, task_manager)`；将 `_last_report` 放入 TaskManager 或 AppContext。

优点：改动小、兼容成本低、可以快速消除 P0。  
缺点：模块全局 provider、动态 ExecutionContext、GUI/Agent/MCP 多入口耦合仍存在；未来继续增长时会再次变成大文件。  
适用：只作为 1 个短迭代的稳定化，不应作为最终架构。

### 方案 B：应用服务 + 端口适配器 + Composition Root（推荐）

建议结构：

```text
smart_assistant/
  application/
    editing_service.py
    translation_service.py
    quality_service.py
    conversation_service.py
    task_runtime.py
  execution/
    scheduler.py
    node_handlers.py
    checkpoint_store.py
    lifecycle.py
    models.py
  ports/
    app_state.py
    config_provider.py
    report_repository.py
    event_sink.py
    main_thread_dispatcher.py
  adapters/
    tools/               # Agent/MCP ToolResult 适配
    qt/                  # signal/timer/dialog/main-thread adapter
  bootstrap.py           # 唯一 composition root
```

关键原则：

- `bootstrap.py` 创建一次 `AssistantRuntime`，显式注入 `TaskRuntime`、repositories、config provider、event sink。
- ToolRegistry 注册的是绑定好的 adapter 实例，不在工具执行时构造 AppContext/TaskManager。
- `TranslationService` 等只接收明确 DTO/Protocol，不认识 Qt、ToolResult、QWidget。
- GUI、Agent、MCP 只做输入/输出格式转换，共享相同 use case。
- Graph 执行产生 typed events：started/progress/paused/completed/failed/cancelled；Qt adapter 再转 signal。
- 每个 Session 有独立 `SessionRuntime`，每次计划执行有独立 `ExecutionRuntime` 和 cancellation token。

优点：真正解决依赖方向、全局状态、复用与测试；后续迭代成本最低。  
缺点：需要 4–7 个 Story 渐进迁移；短期文件数增加，需要维护兼容适配层。  
风险控制：采用 strangler 方式按 namespace 迁移，不做一次性重写。

### 方案 C：Command/Event Bus 或 Session Actor

做法：所有 UI/Agent/MCP 操作变为 Command，Session Actor 串行处理并发和状态，所有结果写入 Event Bus。

优点：状态隔离、并发顺序、可观察性最强；适合未来多会话并行、多客户端远程控制。  
缺点：对当前桌面应用偏重；调试链路和学习成本高；若没有严格 schema 容易把类型问题变成消息问题。  
建议：暂不采用完整 actor；只吸收 typed command/event 与 per-session runtime 两个思想。

## 6. 推荐目标设计

推荐方案 B，并把“状态所有权”作为核心设计轴：

```text
AppRuntime
├─ ConfigProvider / SecretProvider
├─ TaskRuntime                 # app 级任务目录，但 task handle 有 owner_id
├─ ToolRegistry               # app 级，只存 adapter
└─ SessionRuntime(session_id)  # 每会话一个
   ├─ ConversationService
   ├─ SessionController        # 唯一 ReAct/auto mode 所有者
   ├─ ReportRepository(view scoped by session/project)
   └─ ExecutionRuntime(execution_id)
      ├─ GraphScheduler
      ├─ NodeHandlerRegistry
      ├─ CheckpointStore
      └─ Cancellation/PauseToken
```

依赖方向：

```text
Qt UI / Agent Tool / MCP Adapter
            ↓
      Application Services
            ↓
     Domain Models + Ports
            ↑
 Config/File/Qt/LLM Infrastructure Adapters
```

必须禁止的依赖：

- `smart_assistant.application|execution|ports` → `ui.*`
- application service → `ToolResult`、QMessageBox、QTimer、pyqtSignal
- Controller/service 内部直接调用 `TaskManager()` 或 `AppContext()`
- 通过 `__getattr__` 暴露整个 AppContext 作为能力集合
- 模块级保存当前 controller/report/session/execution 的可变全局变量

## 7. ADR 修订建议

### ADR-008：重写“代码分层”执行约束

建议新增/修订：

1. 定义 composition root 位置与对象生命周期矩阵（app/session/execution/task）。
2. 明确 `tools/` 是 inbound adapter，不是业务 Controller 所在层。
3. 后端到 UI 的 import 设为 CI 阻断项；Qt 仅位于 `ui/` 或 `adapters/qt/`。
4. 兼容 wrapper 必须标注 owner、移除条件和截止版本，不能作为永久主入口。
5. 取消“仅凭文件行数判定完成”，改为：依赖扇出、可变全局数、构造器注入覆盖率、跨层 import、状态所有者数量、关键 contract tests。
6. 明确 `ExecutionContext` 的替代协议，例如 `CollectionPort`、`SelectionPort`、`LabelPort`、`UiEventSink`。

### ADR-011：按真实实现修正图执行契约

建议明确：

- Scheduler 不直接递归执行条件目标；NodeHandler 只返回 `NodeOutcome(next_nodes, result, state_patch)`。
- BFS/拓扑推进只由 Scheduler 一处负责。
- PauseToken 的语义和线程实现；pause 必须在节点边界阻塞，cancel 必须唤醒 pause/HITL 等待。
- Checkpoint schema 版本、StepResult 序列化/反序列化、`current_frontier`、completed/visited/results 的恢复规则。
- 正常完成后 checkpoint 删除或标记 terminal；取消/失败是否保留应显式定义。
- 所有 graph id 使用稳定 UUID/内容 hash，禁止 Python `hash()` 作为跨进程恢复键。

### ADR-004：统一后台任务模型

补充纯 Python `TaskRuntime` 与 Qt bridge 的关系；任务状态、进度、暂停、取消、完成通知只保留一套协议，禁止各 Controller 自行创建线程和回调约定。

### 可新增 ADR：Assistant Runtime 与多入口复用

记录 GUI、Agent、MCP 共用 application services 的决策，避免三个入口继续各自组装解析、翻译、写回和状态逻辑。

## 8. Plan / Story 修订建议

建议不要继续修改原 FR10 的历史 Story 来掩盖偏差，而是新增 `smart-assistant-architecture-v2` Plan，并在原 Plan 增加“后续治理链接”和真实验收结果。

### Story 01：基线与特征测试（P0）

- 为条件分支、循环、DAG join、pause/resume/cancel/HITL/checkpoint 建 characterization tests。
- 为三个 Controller 建“注入 fake TaskRuntime 后必须只调用 fake”的 contract test。
- 建 UI import、模块级可变 runtime、私有属性穿透静态门禁。
- 验收：关键契约测试先能复现当前缺陷，再由后续 Story 逐一变绿。

### Story 02：Graph Runtime 正确性与职责拆分（P0）

- `GraphScheduler`：唯一 frontier/visited/dependency 推进者。
- `NodeHandlerRegistry`：Action/Condition/Loop/HumanConfirm 分别实现 handler。
- `CheckpointStore`：版本化 schema、原子写、精确恢复。
- `ExecutionLifecycle`：pause/cancel/shutdown/HITL wait。
- 验收：条件只执行一个分支；join 等待全部依赖；pause 在节点边界阻塞；cancel 唤醒所有等待；进程重启后从 frontier 恢复且不重复副作用。

### Story 03：Composition Root 与 Controller 真 DI（P0/P1）

- 新建 `AssistantRuntime/bootstrap.py`。
- ToolRegistry 接收 adapter 实例；移除三个 `_get_*_controller()` 的 UI fallback。
- 所有 `TaskManager()` 由注入的 `TaskRuntime` 替代。
- 验收：`smart_assistant/` 非 Qt adapter 下零 `src.transbridge.ui` import；fake dependency 调用可观测；两个 runtime 实例状态完全隔离。

### Story 04：工具应用服务化（P1）

- 先迁 `editor`（同步、风险低），再迁 `proofreader`，最后迁 `translator`。
- 将 schema/description/registration 与 use case 实现分离。
- 将 `_last_report` 改为 `QualityReportRepository`。
- 验收：GUI/Agent/MCP 对同一 use case 的结果一致；工具 adapter 无业务分支和线程创建。

### Story 05：会话与 UI 边界收口（P1）

- SessionController 成为 `react_depth/auto_mode` 唯一所有者。
- Orchestrator 仅负责一次 LLM round；移除卡片、auto、ReAct 深度等死回调。
- ChatWidget 拆为 View + Presenter/QtAdapter；不直接访问 `engine._executor._executor`。
- 验收：每项会话状态只有一个写入者；ChatWidget 不创建后端 service；纯文本/plan/react/long-running task 状态转换 E2E 全覆盖。

### Story 06：TaskRuntime 与事件协议（P1）

- 用实例化 TaskRuntime 替代单例；TaskHandle 带 owner/session/project/execution id。
- 统一 finished 事件并提供可移除 subscription token。
- 验收：创建/销毁会话不会残留 listener；任务不能串到其他会话；pause/cancel 端到端有效。

### Story 07：兼容层清理与文档闭环（P2）

- 移除已无调用方的 `_tool_*` 私有 wrapper、`__getattr__` 私有穿透、旧 callbacks。
- 勾选验收项并附测试命令/结果、代码链接和偏差说明。
- Requirements 中 FR10 状态改为“结构拆分已完成/架构治理由 V2 接续”，避免继续声称全部目标完成。

## 9. 建议验收门禁

### 架构门禁

- `src/transbridge/smart_assistant/application|execution|ports` 中 `PyQt6` 和 `src.transbridge.ui` import 数为 0。
- 工具模块中 Controller/Task/Report/Session 可变全局实例数为 0。
- application service 中直接 `TaskManager()`/`AppContext()` 构造数为 0。
- 业务调用方不访问 `_executor._executor` 等私有实现链。

### 行为门禁

- Condition true/false 各只执行被选分支一次。
- DAG join 仅在全部依赖完成后执行；依赖失败时策略明确。
- pause 至少阻塞一个节点边界；resume 后继续；cancel 能从 paused/HITL wait 中退出。
- checkpoint 恢复不重复已完成的有副作用节点，并恢复 typed result/state/frontier。
- 两个 Session/Execution 并行时，任务、报告、ReAct 深度、选择集互不污染。
- Controller contract test 证明传入 fake TaskRuntime/Repository/ConfigProvider 被实际使用。

### 测试与文档门禁

- `tests/smart_assistant` 全绿；当前基线两项失败必须修复或形成带原因和期限的 waiver。
- 完整套件通过，且至少在项目声明的 Python/Windows 版本执行。
- 每个 Story 的复选框与实际证据同步，不允许“状态已实现 + 全部 AC 未勾选”。
- changelog 记录真实偏差，不再把目标行数或测试数量写成未验证的完成事实。

## 10. 渐进迁移顺序

1. **先建测试，不改入口**：锁定现行为并新增失败用例，优先暴露 graph 和 DI 问题。
2. **修 P0 Graph 契约**：这是用户数据副作用和长流程恢复的风险中心。
3. **引入 composition root 和 ports**：先允许旧 wrapper 调新 service，保持 ToolRegistry/LLM prompt 不变。
4. **按 editor → proofreader → translator 迁移**：从同步低风险到异步高风险；每迁一个 namespace 做 GUI/Agent/MCP parity test。
5. **收口 Session/Orchestrator/UI**：删除重复状态与死回调，拆 ChatWidget。
6. **实例化 TaskRuntime/ReportRepository**：完成多会话隔离和 listener 生命周期治理。
7. **移除兼容层并更新文档状态**：只在全量调用点和测试证明不再需要时删除。

## 11. 最终判定

FR10 的历史实现不是无价值的：ConditionEvaluator、CheckpointManager、MemoryWriterThread 和类型重导出都提供了可继续演化的切入点，ExecutionEngine 门面也能作为未来替换 GraphRuntime 的兼容边界。

但当前不能把它视为一次已经完成的“解耦重构”。更准确的判断是：

- **文件拆分完成度：约 80%**；
- **职责边界完成度：约 50%**；
- **依赖注入/全局状态治理：约 25%**；
- **关键执行契约验证：约 40%**；
- **FR10 综合完成度：约 50–55%，状态应为“结构阶段已完成，架构治理待 V2”**。

下一轮最有价值的投入不是再把 600 行切成若干 300 行文件，而是建立可执行的依赖规则、状态生命周期和行为契约。推荐以方案 B 为目标、方案 A 为首个稳定化迭代，用 6–7 个独立 Story 渐进迁移。
