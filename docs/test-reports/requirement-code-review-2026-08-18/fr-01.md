# FR1 文件解析纵向审查

- 审查 Agent：`fr01_vertical_review`
- 范围：需求 → ADR → `file-parsing` Plan/Story → Changelog → 解析代码 → 测试
- 方式：只读审查；未修改业务文件

## 结论

FR1 形成于早期代码与旧工作台时期，后续代码经过多轮架构和产品流程迭代。旧 Plan/Story 中的模块路径、类接口、Step1 页面和具体实现步骤只用于追溯历史，**不能直接作为要求当前代码恢复旧实现的基线**。

本报告改用“当前产品能力合同”判断是否需要修改：

- 用户已经确认的当前需求：ParaTranz JSON 的显式导入与导出，并在 ParaTranz 重建数值 `id` 后仍通过 `key` 保持本地词条身份；
- 当前仍公开展示或可调用的能力：如果入口存在，就必须能够成功执行，或明确标为实验性/不可用，不能静默失败；
- 未重新确认的历史能力：DSD、SST、完整 NPC/INFO/DIAL 结构化上下文、BSA/Strings 多入口等，不自动进入本轮代码改造；
- 已被替代的实现方式：旧 Step1、旧 parser 类路径和旧调用签名不要求恢复，只需在文档中记录替代关系并清理误导性状态。

建议状态：**历史 FR1 已完成过阶段性交付；当前进入能力重基线。ParaTranz JSON 兼容为已确认增量，其余问题按公开入口和产品取舍分别处理。**

## 当前范围决策

|---|---|---|
| 已确认 | ParaTranz JSON 导入/导出、`key`/平台 `id` 双身份 | 纳入近期迭代并建立自动化验收 |
| 公开即应可用 | 当前 UI/Agent 中仍展示的 ESP/EET/XT/JSON 解析入口 | 修复成功链，或在产品层隐藏/标记实验性 |
| 待产品确认 | DSD JSON、SST 迁移与写回、完整结构化上下文、BSA/Strings 补齐 | 不作为当前 P0；确认保留后再进入 Plan |
| 历史实现细节 | 旧 Step1、旧模块路径、统一 `.parse()` 假设 | 不恢复；更新文档、链接和状态 |

因此，下文的技术发现仍然保留，但“发现代码与旧 Story 不同”本身不再被视为缺陷。只有破坏当前产品合同、造成错误结果或仍由产品公开承诺的问题，才需要修改代码。

## 用户样本约束补充：ParaTranz JSON 不是 DSD JSON

用户的主要兼容目标是 ParaTranz 的数组格式：`id/key/original/translation/stage/context`。其中数值 `id` 由 ParaTranz 生成，`key` 才是用户原始稳定 ID。

因此 FR1 的 JSON 解析建议需补充：

- 新增独立 `ParaTranzJsonAdapter`，不能继续让 `from_json_file()` 同时猜标准 JSON、ParaTranz JSON 与 DSD JSON；
- ParaTranz 导入必须以 `key` 建立本地主索引，把数值 `id` 保存为 namespaced external reference；
- 缺 `key` 默认报错，不能用 ParaTranz `id` 代替用户 ID；
- DSD 仍由 `DsdJsonAdapter` 处理，两者的格式识别、错误信息和 UI 入口必须分开；
- GUI/Agent/MCP 对同一 ParaTranz fixture 必须生成相同 collection digest。

详细合同见 [ParaTranz JSON 双 ID 兼容性调整](paratranz-json-compatibility-adjustment.md)。

## 历史需求映射与当前适用性

- FR1.1 ESP/ESM/ESL：基础解析基本可用；失败会返回空列表，无法区分合法空插件和解析失败；ESL/light FormID 缺专门验证。
- FR1.2 批量解析：主流程存在，但失败会被误计为成功；对话框允许配置的 EET/XT/已译插件/Strings 迁移源在批量执行中被忽略。
- FR1.3 Strings/BSA：松散文件和部分 BSA 规则存在；只要命中任一松散文件就不再用 BSA 补齐其他 Strings 类型。
- FR1.4 NPC/INFO/DIAL 上下文：提取层取得 sex/race/class/speaker/emotion/quest/topic/note 等字段，但转成 `TranslationEntry` 后大多丢失。是否恢复完整字段属于待确认产品能力；若当前 AI 方案只依赖现有 `context`，不因旧 Story 自动重构模型。
- FR1.5 EET：基础解析较完整；格式识别宽松，不相关 XML 可能成为“成功的空文件”。
- FR1.6 XT：解析内核基本可用；主要仍作为迁移源。
- FR1.7 DSD JSON：底层 `from_dsd_json_file()` 存在，但 Workbench 和 Agent 都误调 `from_json_file()`。仅当当前产品仍展示 DSD 导入时视为缺陷，否则应移除入口并将需求标为暂缓/退役。
- FR1.8 Strings 导入：只能基于已有插件集合按 `string_id` 迁移，缺可靠独立导入链。
- FR1.9.1 SST 解析：SSU8/SSU9 代码存在，但当前 pytest 没有 SST 回归测试。
- FR1.9.2 SST 迁移：入口只在已移除的旧 Step1。旧 Step1 已被后续工作台替代，不要求恢复；是否为 SST 建立新入口需另行确认。
- FR1.9.3 SST 容错：魔数检查存在；截断/解码恢复可能使游标失同步；SSU9 有未初始化变量风险。
- FR1.9.5 SST 写回：源码存在，但公共导出明确被屏蔽，等待 xTranslator 兼容验证。当前应标为实验性/未认证，而不是要求立即恢复公开导出。

## 按当前产品合同重新分类

### 已确认近期需求（P0）

1. 缺少明确的 ParaTranz JSON 双向适配器和产品入口。
   - 不能让通用 JSON loader 猜测 TransBridge、DSD 与 ParaTranz 三种语义不同的格式。
   - 导入必须以 `key` 恢复本地稳定身份，数值 `id` 只能作为有作用域的 ParaTranz 外部引用。
   - 导出必须把本地稳定身份写入 `key`；不能依赖平台数值 `id` 保持不变。
   - GUI、Agent 以及未来 MCP 应调用同一应用服务，并返回一致的导入/导出统计和冲突结果。

2. ParaTranz JSON 的大文件导入任务需要可靠持有 Worker 生命周期。当前 Workbench JSON 导入的 `ApiWorker` 只保存在局部变量中，约 12 MB、3.2 万条的真实样本可能触发 QThread 提前销毁风险。

### 当前公开入口的条件性缺陷（P1）

1. Agent 的 ESP/EET/XT/SST 解析工具全部无法走通成功路径。
   - `tool_parser.py` 最终统一调用 `cls().parse(path)`。
   - `PluginParser` 的真实方法是 `parse_plugin()`。
   - EET/XT 指向不存在的模块路径。
   - `SST_Parser` 需要构造参数，正式入口是 `from_file()`。
   - Agent 路径校验又拒绝桌面文件选择器产生的绝对路径。

   处理原则：保留在当前工具清单中的格式必须修复真实成功链；不再支持的格式应从工具能力描述和路由中移除，不能仅为匹配旧 Plan 恢复旧类结构。

2. DSD JSON 产品入口错误（仅在当前仍公开 DSD 导入时成立）。
   - 正确方法为 `TranslationEntryCollection.from_dsd_json_file()`。
   - Workbench 与 Agent 实际调用标准 JSON loader，DSD 的 `{form_id,type,string}` 会被按 `{id,key,original}` 解释。

3. 解析异常伪装为合法空结果。若当前 UI 或批处理仍使用这些入口，损坏文件会被显示为成功的 0 条，属于真实结果契约缺陷。

### 待确认能力，不作为当前缺陷

- FR1.4 完整结构化上下文：确认下游 AI、持久化和报告仍需要这些字段后再恢复；未确认前只记录数据损失事实。
- SST 迁移 GUI：旧 Step1 已退役，不要求恢复；若继续支持 SST，应在当前工作台设计新的入口。
- SST Serializer：保持 feature flag/公共导出关闭，状态改为“实验性、兼容未认证”。
- DSD、BSA/Strings 互补、EET/XT 严格 schema：根据当前支持矩阵决定保留、加固或退役。

## 保留能力时需要处理的技术风险

- ESP 解析异常返回 `[]`，批量 UI 会把损坏插件显示为成功的 0 条。
- 多个迁移入口使用 `except Exception: pass`，最终仍显示解析完成。
- 松散 Strings 与 BSA 不能按文件类型互补。
- `_read_strings()` 未严格校验 header 的 `data_size` 和记录边界。
- SSU8 主文本解码失败后直接继续，游标可能仍在当前记录中部。
- SSU9 的 `chn_len` 在畸形尾记录上可能未赋值即使用。
- SST 单条更新按 `form_id` 只更新首条，批量更新同 FormID 的全部记录，键语义不一致。
- EET/XT 缺格式/schema 验证，错误 XML 可能被视为合法空输入。

## 架构与性能债（P2/P3）

- GUI、Agent、FOMOD 分别认识不同 parser 类和签名，包移动后入口立即漂移。
- 新增格式不只需实现 parser，还要逐一修改 UI、Agent、FOMOD、持久化和测试，NFR 所称扩展点并不存在。
- ESP 上下文解析大量访问第三方库 name-mangled 私有属性，依赖升级风险高。
- EET/XT 整树解析，未设文件大小、节点数、条目数或峰值内存预算。
- 没有统一取消 token 和每文件结构化失败结果。
- Plan/Story 仍引用迁移前的模块路径；SST 测试报告与当前仓库事实不一致。
- `tests/converter/tests_translation_entry_collection.py` 命名不符合默认收集，手动收集又引用已删除的 XT 模块。

## 测试结论

- 现有测试主要证明 EET/XT 小型数据类和 ESP mock 转换。
- 缺失：SST parser/serializer、DSD、Strings/BSA、上下文完整保留、批量解析、MainWindow/Workbench 成功链。
- Agent 测试主要覆盖空路径、错误路径和扩展名，没有真实格式成功 fixture。

## 当前迭代方案比较

### A. 仅实现 ParaTranz JSON 专用适配器

新增明确的 ParaTranz JSON import/export adapter、双 ID 映射、GUI 入口和自动化测试，不重构其他 parser。

- 优点：直接满足已经确认的用户目标，改动范围和风险最小。
- 缺点：其他格式入口和错误结果契约仍然分散。

### B. 先完成 ParaTranz 纵切，再渐进引入统一应用服务（推荐）

新增纯 Python `ParseApplicationService`，格式实现统一 `ParserAdapter`：

```text
ParseRequest(paths, format_hint, language, skip_empty, cancellation_token)
  -> ParseOutcome(status, document, entries, issues, metrics)
```

第一步只让 `ParaTranzJsonAdapter` 通过统一应用服务接入 GUI/Agent；验证成功后，再按当前支持矩阵逐个迁移仍需保留的格式。纯解析、导入集合、Qt 后台执行、Agent 权限和 FOMOD 批处理分开。

- 优点：统一合法空、部分成功、失败、警告和取消；形成真实扩展点；便于入口等价测试。
- 缺点：需要中等规模渐进迁移和暂时兼容层。

### C. 一次性重构全部历史格式

同时恢复或重写 ESP/EET/XT/DSD/SST/Strings/BSA 的所有入口，并加入流式处理、资源预算和插件发现。长期能力最完整，但在产品范围尚未确认时容易为已退役需求投入过多成本，当前不推荐。

## 推荐目标设计

- `ParsedDocument` 保存源格式、源路径、warnings/errors、模板能力与可写性。
- `TranslationEntry` 保留旧字符串 `context`，新增可序列化 `context_detail`，完整保存 NPC/INFO/DIAL 字段。
- 合法空、部分损坏、失败、取消必须是不同结果状态；失败禁止伪装成空列表。
- Registry 注册真实 adapter 对象，不再依赖字符串模块和统一 `.parse()` 约定。
- 路径安全采用“canonical path 位于用户授权根”而不是拒绝全部绝对路径。
- SST 写回保持 feature flag 关闭，直到字节/重解析/xTranslator/重复 FormID 兼容矩阵全部通过。

## ADR / Plan / Story 建议

### ADR

- 优先修订 ADR-002：明确 `key` 是本地稳定身份，ParaTranz 数值 `id` 是有作用域的外部引用；区分内部 JSON、ParaTranz JSON 与 DSD JSON。
- 新增或修订导入导出 ADR：定义 Format Adapter、结构化 Outcome、冲突策略和原子写出。
- 只有确认继续保留多格式统一入口后，再新增完整 Parser Adapter Registry ADR。
- ADR-001 的结构化上下文扩展、ADR-004 的通用批量取消，以及 SST 兼容认证，均进入条件性 Backlog。

### 已确认 Stories

1. ParaTranz JSON Adapter 与 `key`/external `id` 身份契约。
2. ParaTranz JSON 显式导入、显式导出与结构化冲突结果。
3. GUI/Agent 入口接入同一服务，补真实样本、双 ID 往返和性能门禁。
4. 修复导入 Worker 生命周期和取消/失败反馈。

### 条件性 Backlog

5. 对当前仍公开的 parser 工具修复 dispatch 与成功链。
6. 保留 DSD 时建立独立 `DsdJsonAdapter` 和显式入口。
7. 保留结构化上下文时扩展模型及旧数据迁移。
8. 保留 SST 时加固 parser，并按当前工作台重新设计迁移入口。
9. SST 写回通过目标工具兼容认证后再开放。
10. 仅在三种以上格式确认长期保留后，推进通用 Parser Adapter Registry。

## 已确认范围的核心验收标准

- ParaTranz JSON 可通过明确的导入与导出入口处理，不依赖自动猜测格式。
- ParaTranz 数值 `id` 全部改变后重新导入，本地 `key` 集合和译文仍保持一致。
- ParaTranz JSON 缺 key/重复 key 必须产生结构化错误，禁止静默覆盖。
- 导出时稳定身份始终写入 `key`；仅在存在同一 ParaTranz 作用域映射时复用平台 `id`。
- 用户提供的约 3.2 万条、12 MB 样本可完成导入/导出，Worker 不被提前销毁，失败与取消可见。
- GUI 与 Agent 对同一 fixture 产生相同 collection digest 和冲突统计。
- 内部 JSON、ParaTranz JSON、DSD JSON 不发生静默串格式解析。

其他格式的验收标准在确认保留后，从上述条件性 Backlog 单独展开，不作为 ParaTranz JSON 迭代的发布门禁。

## 迁移顺序

1. 把用户提供的 ParaTranz JSON 固化为脱敏 fixture，并冻结 `key`/external `id` 合同。
2. 新建 ParaTranz JSON 专用 adapter，完成导入、导出、冲突与错误结果。
3. 接入当前 GUI，再接入 Agent；修复 Worker 生命周期并补大文件测试。
4. 将旧 FR1 各项标为“当前保留、待确认、已替代、实验性”之一，停止用旧实现步骤判定当前回归。
5. 盘点当前实际公开的 ESP/EET/XT/DSD/SST/Strings/BSA 入口：保留的修成功链，不保留的移除入口与能力描述。
6. 只有支持矩阵稳定后，才为多个长期格式引入通用 Adapter Registry。
7. SST 写回保持关闭；只有重新确认需求并完成目标工具认证后才开放。
8. 删除旧 Step1 死代码、过期链接和与当前支持矩阵冲突的状态描述。
