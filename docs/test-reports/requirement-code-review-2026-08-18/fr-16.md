# FR16 通用文件与词条 Agent 工具：需求—架构—方案—Story—代码纵向审查

> 审查日期：2026-08-18  
> 审查范围：FR16.1～FR16.5（归档、目录差异、过滤、键迁移、词典 Agent 工具）  
> 审查方式：独立纵向审查；未读取或引用本轮其他 Agent 的结论  
> 变更边界：本文件仅记录审查结果，不修改需求、ADR、Plan、Story、业务代码或测试

## 1. 结论摘要

FR16 已经形成了较完整的“文件存在层”实现：`fileops/`、`migrator/`、7 个 Agent 工具注册项和纯 Python 单元测试都已落地，ZIP、基础 diff、规则过滤、键迁移的 happy path 能运行。但是，它还没有形成可信的“用户成功链”。最关键的事实是：

1. `migrate_entries` 虽已注册，却固定返回 `NOT_AVAILABLE`，FR16.4.4 实际为 0% 可用。
2. 所有需要真实 Windows 文件路径的 Agent 工具都经过 `InputValidationGuard`；该 Guard 一律拒绝绝对路径。文件选择器、项目路径和 MCP 客户端实际都会使用绝对路径，因此 `extract_archive`、`pack_archive`、`diff_directories` 以及带 `rules_json` 的 `filter_files` 在正常桌面用法中被安全层自己阻断。
3. MCP 启动链还有三处独立阻断：`ui/app.py` 使用未导入的 `ToolRegistry`；Adapter 在 `MainWindow/AppContext` 创建之前以 `ctx=None` 启动且没有后续注入；`select.select([sys.stdin])` 在 Windows 仅支持 socket，stdio 线程不能按当前方式可靠运行。
4. MCP 暴露的 JSON Schema 把内部类型名 `str/list` 原样输出，而不是合法 JSON Schema 类型 `string/array`。即使启动链修复，严格客户端也可能拒绝这些工具定义。
5. ADR/Plan 承诺 7z、RAR 自包含发布，但 `pyproject.toml`、`uv.lock`、`transbridge.spec` 均未声明/收集 `py7zr`、`rarfile` 或 `unrar.exe`；仓库中也没有 `unrar.exe`。开发机“碰巧安装”不能满足可交付要求。
6. 归档层没有统一的成员路径授权、文件数/总展开大小/单文件大小/压缩比/超时/取消策略。ZIP 的字符串 `startswith` 包含性判断不是可靠的路径证明；7z/RAR 则完全依赖第三方库默认行为。当前缺少压缩炸弹、路径穿越、符号链接/重解析点测试。
7. `normalize_root()` 实际只向输入目录的父级搜索锚点，无法发现解包目录下的单层包装目录；而这正是“消除包裹层级差异”的目标场景。
8. 进度能力只在 ZIP 和 RAR 的逐成员循环中部分实现；7z 解包、7z 打包没有进度，Agent 工具也不传进度回调，且没有标记为长任务。FOMOD UI 虽在线程中运行，但也没有把 archive progress 连接到 UI。
9. 词典工具注册已完成，但 `apply_dictionary` 使用空 `QueryContext`，没有当前 mod 语境；冲突只返回数量，不返回候选摘要；`apply_to_collection()` 写入译文后不更新 stage。实现没有锁定条目状态与来源语义。
10. 文档状态严重陈旧：Requirements 仍标记“待方案”，Plan/Story 验收框全部未勾选，changelog 却声称已编码；其中 `migrate_entries` 的 changelog 与代码事实直接矛盾。

综合判断：FR16 的纯后端算法约完成 **60%～70%**，Agent/MCP/桌面真实成功链约完成 **20%～30%**，按用户可观察验收口径总体建议记为 **约 45%（部分实现，不可发布）**。当前不宜继续只补小函数；推荐升级为“授权文件资源服务 + 格式适配器 + 统一 Job/Progress + 薄 Agent/MCP/UI 适配层”的渐进方案。

## 4. 文档链路审查

### 4.1 Requirements

需求拆分本身是合理的：把通用 fileops/migrator 从 FOMOD 特定逻辑中抽离，也明确区分“键迁移”和“词典兜底”。问题在于非功能合同不足：

1. 没有定义 Agent 如何引用用户本地文件和两个集合。`str path` 与安全层之间没有授权模型。
2. 没有定义归档安全预算：最大成员数、最大展开字节、单文件上限、压缩比、目录深度、符号链接/硬链接/重解析点、覆盖策略。
3. 没有定义冲突、部分成功、警告、跳过、取消后的结果结构。
4. 没有定义 progress 的事件模型、频率、取消令牌和 UI/MCP 如何消费。
5. “跳过大文件哈希仅比较存在性”会把同名但大小已变的文件标成 unchanged，语义应至少升级为“存在性+大小+可选mtime”或单列 `assumed_unchanged`。
6. “原文变化标记需复核”没有说明是只返回 key，还是必须改变条目 stage/label/provenance。
7. Requirements 状态仍为“待方案”，与已有 ADR、Plan、代码不一致。

### 4.2 ADR-015

ADR 对包边界和职责分离的判断正确，但它只解决了“代码放哪里”，没有解决“能力怎样安全地跨 Agent/MCP/UI 调用”。建议保留现有包边界，同时补充以下决策：

- 文件路径不再由 Guard 以“绝对/相对”二元判断；所有路径先转换为 `AuthorizedPath` 或 `FileResourceRef`，基于用户授权根做 canonical containment。
- Archive/Diff/Filter/Migrate 均通过应用服务调用，Agent/MCP/UI 只做参数适配。
- 归档格式实现改为 Adapter Registry；每个适配器声明读/写/进度/取消能力。
- 所有文件任务返回统一 `OperationResult`：`status`、`metrics`、`warnings`、`artifacts`、`errors`、`partial`。
- 归档处理必须接受 `ArchivePolicy` 和 `CancellationToken`。
- 对“需复核”和词典命中建立统一的 TranslationEntry mutation/provenance 合同。

ADR-012 也需要同步更新：MCP 的 context 生命周期、合法 JSON Schema 类型、Windows stdio、write 工具授权与审计不能继续留给实现自行推断。ADR-004 需允许纯 Python JobRuntime + Qt signal adapter，而不是把进度回调散在具体函数里。

### 4.3 Plan 与 Story

Plan 的 5 Story 按模块切分易开发，但缺少最重要的跨层 Story：

- S01～S05 各自只验证函数或注册，没有一条“用户选文件 → Guard授权 → Agent/MCP调用 → 后端执行 → progress/cancel → 结果/产物”的验收链。
- Story 文件中的复选框全部未勾选；Plan 状态却为“已确认”，不能表达已实现/部分实现。
- S01 说 `pycryptodome/texttable` 应显式声明，实际依赖完全没有写入 `pyproject.toml`。
- S01 声称流式/进度，代码没有 7z 进度和取消。
- S02 的“向上查找锚点”设计无法解决输入根内的包裹层。
- S04 没有定义 Agent 的新旧集合资源模型，最终只能注册一个 stub。
- S05 详细 Story 要求把 conflicts 摘要放入结果，代码只保留数量。

### 4.4 Changelog

Changelog 可追溯性较好，但有事实偏差：

- S04 记录“注册 migrate_entries”容易被理解为可用；实际函数固定失败。
- S01 记录“zip 路径穿越防护”，但实现是字符串前缀比较，不能作为可靠 containment 证明；7z/RAR也没有同一政策。
- S03 记录“保留脚本”，而“常规 mod”预设的 keep 集不含 `.pex/.psc`；之所以测试仍保留，是因为未知扩展默认保留。记录表达与真正规则语义不同。
- 测试补全记录只覆盖基础 happy path，不能代表 7z/RAR、Agent/MCP、Windows、恶意归档或发布验收。

## 5. 代码级问题清单

### P0：必须先修，否则 FR16 不能宣称 Agent 可用

#### P0-1 `migrate_entries` 是公开注册的不可用占位符

- 证据：`tool_migrator.py:71-76` 无条件返回 `NOT_AVAILABLE`。
- 影响：FR16.4.4 直接未实现；LLM 能看到工具却永远失败，产生错误能力宣告。
- 修复方向：定义 `old_collection_ref/new_collection_ref` 或 `old_variant/current_variant` 合同，通过 AppContext/ProjectService 解析；支持 `dry_run=true` 返回预览，再以确认后的 mutation commit。

#### P0-2 文件工具与全局绝对路径禁令互相冲突

- 证据：`input_validator.py:66-90` 对参数名含 path/file/dir/output/dest/save 的绝对路径一律拒绝。
- 影响：Windows 文件对话框、项目恢复、MCP 客户端都天然产生绝对路径；FR16.1/16.2 的典型用法无法穿过统一执行链。
- 修复方向：用 `PathAuthorizationService` 验证“是否位于用户授权根/管理工作区”，而不是拒绝绝对路径。必须使用 `Path.resolve(strict=...)` + `Path.is_relative_to()`，并处理目标不存在时的父目录、junction/symlink/reparse point。

#### P0-3 MCP 应用启动链不可运行

- `ui/app.py:60-61` 使用未导入的 `ToolRegistry`，MCP 开启时会 NameError。
- `ui/app.py:53-64` 在 `MainWindow` 创建前启动 Adapter，`ctx=None` 且没有后续 `set_context()`。
- `mcp/server.py:43-50` 在 Windows 对 `sys.stdin` 使用 `select.select`，不是可靠的文件句柄等待方案。
- 影响：FR16 即使工具自身修好，也无法形成 MCP 成功链。
- 修复方向：Composition Root 先构造 AppContext/服务，再构造 MCP；Windows 使用阻塞 reader thread + queue，或标准 asyncio/官方 MCP SDK 的 stdio transport；加入真实进程启动测试。

#### P0-4 7z/RAR 与“自包含发布”不一致

- `pyproject.toml:10-28` 无 `py7zr/rarfile`。
- `uv.lock` 无两者锁定。
- `transbridge.spec:18-45` 无 unrar binary、相关 datas/hiddenimports。
- 仓库无 `unrar.exe`。
- 影响：开发机导入成功不代表 wheel/PyInstaller 包可用；RAR 必然依赖外部环境，与需求明确相反。
- 修复方向：先解决 unrar 的许可证与分发来源，再锁定版本、校验二进制哈希、加入 spec；若不能合法可靠捆绑，应修改需求为“RAR 可选能力”，并在 UI/Agent capability 中明确不可用原因。

#### P0-5 归档缺少统一安全与资源限额

- ZIP 的 `str(target.resolve()).startswith(str(dest.resolve()))` 会受到同前缀目录、大小写和路径语义影响；应使用路径组件关系。
- 7z/RAR没有应用层成员校验。
- 无成员数、总展开量、单文件、压缩比、目录深度、超时、取消、覆盖策略。
- 影响：不可信 mod 包可导致越界写入风险、磁盘耗尽、长时间阻塞或覆盖已有文件。即使某版本库自动清洗路径，也不应把安全合同隐式外包给依赖默认值。
- 修复方向：先列清单/元数据并校验，再写到独立 staging；拒绝绝对成员、`..`、驱动器/UNC、链接类条目；预算超限立即取消并清理；最终原子发布。

### P1：影响正确性和核心体验

#### P1-1 根归一化算法没有实现“剥离包装层”

- 证据：`differ.py:37-42` 只检查 `[p, *p.parents]`。
- 影响：`extracted/ModName/fomod` 对 `extracted/fomod` 会产生大量虚假 added/removed。
- 方向：分别扫描输入根下的有限深度候选根，识别锚点集合；只有唯一候选时自动选择，多候选时返回 ambiguity，让调用方/用户选择。不要无界递归猜测。

#### P1-2 “跳过哈希”把变化文件错误标为 unchanged

- 证据：`differ.py:79-82` 同路径、扩展命中 skip 后直接进入 unchanged。
- 影响：同名 BSA 大小已变化仍被报告为不变。
- 方向：改为 size-first；可选采样哈希；或者新增 `unchecked/assumed_unchanged` 类别，避免伪精确。

#### P1-3 进度和长任务合同不完整

- 7z extract/pack 不发 progress。
- `tool_archive.py` 不传 progress，工具注册也没有 `is_long_running=True`。
- `ToolExecutionHandler.execute_step()` 同步调用工具；大型归档可阻塞智能助手 UI。
- FOMOD pipeline `extract/pack` 也不传进度；Panel 没有取消令牌。
- 方向：统一 JobRuntime，事件至少含 phase/current/total/bytes/message；Agent 返回 task_id，UI订阅，MCP可轮询；cancel 必须传播到每个适配器阶段。

#### P1-4 Agent/MCP 参数与结果合同不合格

- FR16 工具函数未应用 `@validate_params`，缺参常被捕获成 internal error。
- MCP schema 输出 `str/list` 非 JSON Schema 标准类型。
- 大 diff 直接把全部路径塞入 `ToolResult.data`，没有分页/产物文件。
- 所有异常都粗略映射为 `internal`，无法区分 input/not_found/unsupported/corrupt/permission/quota/cancelled。
- 方向：单一 typed schema 源生成 Agent prompt、运行时验证和 MCP JSON Schema；结果使用稳定 error code 和分页/artifact_ref。

#### P1-5 键迁移“需复核”没有形成领域状态

- `key_migrator.py:57-59` 只把 key 放入 `MigrationResult.needs_review`，条目本身无 stage/label/provenance 变化。
- 影响：结果对象丢失后，GUI、Agent、保存/重开无法知道该条目需复核。
- 方向：定义 `TranslationMutation` 和 `TranslationOrigin`；原文变化可设 `STAGE_QUESTIONABLE` 或专用 review flag，并记录来源 old_variant/key/old_original。具体产品语义写入 ADR-001/002 或 ADR-015 更新节。

#### P1-6 词典套用缺少上下文、冲突详情与 stage 策略

- `tool_migrator.py:30-35` 每次新建 manager，并使用空 `QueryContext()`。
- `tool_migrator.py:41-43` 只返回 conflicts 数量，不返回候选摘要。
- `manager.py:350-352` 写入 translation，但不更新 stage。
- 影响：同 mod 优先级失效，LLM无法仲裁冲突，词条可出现“有译文但 stage=未翻译”。
- 方向：由应用服务注入共享 TM manager；要求 mod_file_id/context；返回经过脱敏和限量的候选；所有译文写入走统一 mutation policy。

### P2：可维护性、可复现性和边缘一致性

1. `extract()` 在确认归档存在/格式合法前就创建目标目录（`archive.py:63-74`），失败会留下空目录。
2. `_extract_zip` 对缺失成员静默跳过且不返回 warning；RAR 对缺失成员可能整体失败；7z又是过滤后静默跳过，三格式合同不一致。
3. 7z `extracted_count` 可能包含不同于 ZIP/RAR 的目录/特殊条目语义。
4. `pack()` 的 `fmt` 与输出后缀可以矛盾，例如 fmt=zip 写入 `.7z` 文件名。
5. pack 不保证输出父目录存在，也没有排除输出归档位于源目录内导致自包含/重复风险。
6. `FilterRules.from_json()` 不校验根对象、字段类型、扩展名格式、keep/strip 重叠、dir rule 结构。
7. Windows 路径比较大小写敏感；同一规则 `fomod` 不一定匹配 `FOMOD`。
8. `normalize_root()` 对不存在路径返回该路径，diff 将其当空目录而非 input error。
9. `old_by_key.setdefault` 静默接受重复 key，迁移结果依赖输入顺序。
10. `migrate()` 在新条目已有译文时仍可覆盖，没有 overwrite/preserve policy。
11. `save_dictionary` schema 没有 `entry_ids/tags`，与 manager 能力和 Story 接口描述不完全一致。
12. `apply_dictionary` 命中会改变 hits，但工具没有保存 manager，命中统计是否应持久化没有明确合同。

### P3：文档与开发体验

1. Requirements/Plan/Story 状态没有随编码回写。
2. `story-04` 仍保留编码前 id/key 警告，虽 ADR 更新节和代码已切换 key，Story 没有正式收敛。
3. 测试文件实际放在 `tests/test_fileops.py`，Story 清单写的是 `tests/fileops/test_*.py`。
4. `fileops/__init__.py` 导出私有 `_find_unrar`，公共 API 边界不清晰。
5. 工具描述宣称“不依赖用户环境 7-Zip”，但 7z Python 依赖与 RAR 二进制并未交付，属于能力过度宣告。

## 6. 三种后续方案

### 方案 A：现有模块内修补

做法：保留当前函数与 str path 参数；修复 normalize、添加资源限制、补依赖、对 FR16 工具放宽绝对路径、实现 migrate_entries。

优点：改动小、短期最快。  
缺点：会在 Guard 中出现工具特例；Agent/MCP/UI 仍各自组织上下文、进度和错误；以后每个文件工具都重复安全逻辑。  
适用：仅作为 P0 紧急止血，不应作为最终架构。

### 方案 B：授权路径 + 应用服务 + 格式适配器（推荐）

做法：

1. 新建 `application/file_operations.py`（名称可调整），提供 Archive/Diff/Filter/Migration use case。
2. 新建 `PathAuthorizationService`，把 UI 用户授权目录、项目根、管理 staging 转为 `AuthorizedPath`。
3. `ArchiveAdapter` 按 zip/7z/rar 注册，每个声明 capabilities；服务统一执行 member validation、quota、staging、progress/cancel、错误映射。
4. Agent/MCP/UI 只调用应用服务；短期仍接受路径，但必须先授权和规范化。长期可升级 resource_ref。
5. Collection/Variant 通过 `CollectionRef` 解析，`migrate_entries` 先 dry-run 后 commit。
6. 所有译文写入使用统一 `TranslationMutationPolicy`，设置 stage/provenance/review。

优点：可渐进迁移，能直接修复当前真实阻断，并为 FOMOD/未来批处理复用；测试边界清晰。  
缺点：需新增应用层合同与兼容 facade，改动中等。  
推荐理由：在不推翻 fileops/migrator 纯后端的前提下，把现在缺失的授权、任务、上下文和结果合同补齐。

### 方案 C：完全资源句柄化/沙箱工作区

做法：Agent/MCP 永不接收真实路径，只接收 `resource_id`；所有输入先由用户导入受管工作区，输出也先生成 artifact，再由用户导出。

优点：安全边界最强、MCP 易审计、跨平台路径差异最小。  
缺点：大体积 FOMOD/BSA 复制成本高，桌面 UX 和项目迁移改动大；现有路径型 API 兼容工作多。  
适用：远程 MCP、多用户或不可信 Agent 执行环境的长期目标。

### 推荐组合

采用 **B 为主、C 的 resource_ref 作为 MCP/远程通道长期形态、A 只做阻断修复**。也就是：先让授权绝对路径在本地桌面安全可用；随后把 MCP 改为资源句柄；后端 fileops 仍保持纯 Python 和可直接测试。

## 7. 建议的目标架构

```text
UI 文件选择器 / Agent Tool / MCP Tool
                │
                ▼
        PathAuthorizationService
   (授权根、canonical path、读写能力、审计)
                │
                ▼
       FileOperationsApplicationService
   ┌────────────┼───────────────┬─────────────┐
   ▼            ▼               ▼             ▼
ArchiveService DiffService  FilterService MigrationService
   │                                       │
   ▼                                       ▼
AdapterRegistry                  TranslationMutationPolicy
(zip/7z/rar)                     + CollectionRepository
   │
   ▼
ArchivePolicy + Staging + JobRuntime
(quota/member validation/progress/cancel/atomic publish)
```

建议关键数据类型：

- `AuthorizedPath(path, capability, root_id)`
- `ArchivePolicy(max_members, max_total_bytes, max_single_file_bytes, max_ratio, max_depth, allow_links, overwrite)`
- `OperationResult(status, metrics, warnings, artifacts, errors, partial)`
- `OperationError(code, message, path/member, retryable)`
- `JobEvent(phase, current, total, bytes_done, message)`
- `CollectionRef(project_id, variant_id, slot_id)`
- `MigrationPreview(inherited, needs_review, missed, conflicts, mutations)`
- `TranslationMutation(entry_key, translation, stage, origin, review_reason)`

### 8.3 每个 Story 必须新增的验收

#### S01 Archive

- 三格式 capability 在运行时可查询；不可用必须在调用前返回明确原因。
- 选择性提取在三格式结果一致，缺失成员进入 warnings。
- 拒绝绝对成员、`..`、驱动器/UNC、symlink/hardlink/reparse point（除非显式允许）。
- 达到任一配额后取消并清理 staging，不发布半成品。
- progress 至少每 N 个成员或 M 字节发事件；cancel 后不再写最终产物。
- fmt 与后缀冲突返回 input error；输出不能位于未排除的源目录内。

#### S02 Diff

- 单包装层、双包装层、无锚点、多锚点均有明确行为。
- Windows 大小写和路径分隔统一；输出统一使用 POSIX relative path。
- skip_hash 文件至少比较大小，并明确 `unchecked` 状态。
- 不存在/不可读目录返回 input/permission error，而不是空目录。

#### S03 Filter

- JSON Schema 有版本；扩展名自动 lower 并补点，或严格拒绝。
- keep/strip 冲突和非法 dir rule 有稳定错误码。
- 目录规则按路径段且 Windows casefold；禁止 `..`。
- 提供 dry-run summary，不直接删除文件。

#### S04 Migration

- Agent 能指定旧 variant 与新/current variant，并成功执行。
- dry-run 不修改集合；commit 使用版本/快照校验防止 TOCTOU。
- changed 条目持久化 review 状态与来源；已有译文遵守明确 overwrite policy。
- 重复 key/空 key/旧条目无译文都有单独统计。

#### S05 TM

- QueryContext 自动带当前 mod/project。
- conflicts 返回限量候选摘要及 continuation/artifact，不只数量。
- 命中后的 stage/provenance 与统一 mutation policy 一致。
- scope、entry_ids、tags 全部校验；并发保存和损坏词典有恢复策略。

#### S06/S07/S08 集成

- GUI Agent 使用用户选择的 Windows 绝对路径成功完成 ZIP extract/diff/pack。
- MCP 在 Windows 子进程中启动，tools/list schema 通过 JSON Schema 校验，read/write policy 可控。
- MCP write 工具使用授权 resource/path，不允许越权目录。
- FOMOD UI 能显示 archive phase progress，并能取消且不留下最终包。
- clean environment 安装 wheel 后可导入 7z/rar 依赖；PyInstaller 包包含合法来源的 unrar 或明确禁用 RAR。

## 12. 最终建议

### 与 ParaTranz JSON Adapter 的职责边界

FR16 通用 fileops 只负责授权路径、原子读写、大小限制和 artifact 输出，不应在 `filter_files` 或通用 JSON 工具里实现 ParaTranz 的 `id/key` 业务映射。该映射属于 `ParaTranzJsonAdapter`/应用 Use Case；Agent/MCP 的 `import_paratranz_json` 与 `export_paratranz_json` 可以复用 FR16 的 PathAccess/Artifact 能力，但不能复制格式逻辑。详见 [ParaTranz JSON 双 ID 兼容性调整](paratranz-json-compatibility-adjustment.md)。

FR16 不应推倒重写：现有 `fileops/` 与 `migrator/` 作为纯 Python 核心的方向是正确的，ZIP/diff/filter/migrate 的基础算法也可保留。真正需要重构的是它们上方缺失的应用合同。推荐立即创建“FR16 v2 / File Operations Application Service”迭代，把 P0 集中在授权路径、MCP 启动、归档安全、真实 migrate Agent 和发布依赖；随后再统一任务、进度、取消和 TranslationEntry mutation。

验收标准应从“模块存在/工具已注册”改成“GUI、Agent、MCP 三个入口在 Windows 上都能用授权资源完成同一用例，并得到一致、可审计、可取消的结果”。只有达到这个标准，FR16 才真正完成了它的核心目标：通用能力可复用且 Agent 可调用。
