# FR13 多会话 / SessionManager 纵向审查报告

> 审查日期：2026-08-18  
> 审查路径：需求原文 → ADR → Plan / Story → Changelog → 实际后端 / UI / 任务系统 → Tests  
> 审查原则：以 `docs/requirements.md` 中 FR13 原文为最终需求基线；本报告不读取或合并其他 Agent 的结论。  
> 结论性质：只读审查，不修改业务代码、架构文件或既有方案文件。

## 1. 执行结论

FR13 的基础外观和基本 CRUD 已落地：用户可以创建、切换、删除、重命名会话；会话文件能落到全局 `data/sessions/`；普通的手工切换可保存并恢复消息；后端与 UI 基本遵守 ADR-008 的分层方向。

但是，当前不能继续标记为“完整实现”。审查确认存在 3 类会破坏会话隔离或持久化正确性的 P0 问题：

1. **启动恢复只恢复 UI 气泡，没有恢复 `ConversationManager`**。下一次对话会在空历史上继续，并可能通过自动保存覆盖原会话文件，造成历史对话丢失。
2. **后台任务和计划执行没有 `session_id` 归属**。在会话 A 启动任务后切到 B，A 的完成回调会写入 B 的对话并驱动 B 的 `SessionController`；旧 `ExecutionEngine` 也没有在切换时被取消或隔离。
3. **会话切换不是事务**。Panel 在确认目标会话成功加载前就修改 `_active_session_id`；目标文件加载失败时，UI 仍显示旧会话内容，但活动 ID 已变成目标 ID，后续自动保存可能把旧会话内容写入错误目标。

综合判断：

- 基础功能完成度：约 **75%**。
- 会话隔离、并发和故障恢复完成度：约 **35%**。
- 文档链路完整度：约 **55%**。
- 建议把需求状态由“已实现”暂时修正为 **“部分实现 / 稳定化中”**，完成本报告 P0、P1 验收后再恢复为“已实现”。

## 3. 需求到实现映射

### 3.1 FR13.1 SessionManager 后端

实现情况：**部分完成**。

- CRUD 已存在：`session_manager.py:37-136`。
- 每会话一个 JSON：`session_manager.py:28-33, 140-147`。
- 目录扫描和缓存：`session_manager.py:149-168`。
- 每轮 LLM 响应后自动保存入口：`chat_widget.py:1178-1202`。
- Panel 启动时选择最近活跃会话：`panel.py:111-125`。

主要偏差：

- 需求规定格式为 `{meta: {...}, messages: [...]}`，实际和 ADR 使用扁平结构 `{session_id, name, ..., messages}`，需求、ADR、代码三者不一致。
- 所谓“消息懒加载”只是不把消息存入 `_cache`；`_scan()` 仍对每个文件执行完整 `read_text + json.loads` 并读取 `messages` 长度，启动时仍会读取和解析全部消息。
- `get_session()` 只在内存中更新 `last_active_at`，没有写回文件；“恢复上次活跃会话”不可靠。
- 自动保存只处理有消息的会话，并忽略 `save_session()` 的 `False` 返回值，磁盘失败不会按需求通过 `on_system_message` 提示用户。
- `create_session()` 的写入异常没有捕获，磁盘不足或权限错误会直接穿透 UI 调用链。

### 3.2 FR13.2 ConversationManager 序列化

实现情况：**基本完成，但缺少输入契约**。

- `to_dict()` / `from_dict()` 已实现：`conversation_manager.py:100-114`。
- 正常 round-trip 单元测试存在：`test_session_manager.py:194-257`。

缺口：

- `from_dict()` 不验证 `messages` 是否为列表，也不验证元素的 `role/content` 类型。
- 合法但结构错误的 JSON 会延迟到 UI `load_history()` 或 `ConversationManager.add_system()` 才崩溃。
- 缺少 `schema_version`、迁移器和未知字段策略，未来难以安全演进。
- system prompt 被作为普通历史持久化；跨项目打开旧会话后，`ConversationOrchestrator.start_round()` 看到已有 system 消息就不会重建当前项目上下文，可能持续使用创建会话时的旧项目上下文。

### 3.3 FR13.3 会话列表 UI

实现情况：**基础能力完成，有设计漂移**。

- 左侧可折叠列表、名称、消息数、最后活跃时间、高亮、创建、删除均存在：`session_list_widget.py:31-312`。
- 删除前有确认：`session_list_widget.py:302-312`。
- 代码额外增加了重命名能力。

文档漂移：

- ADR D17 / Plan Story 02 写的是“+ 后弹命名框”和“悬停 × 删除”；代码后来改为“秒建新对话”和“⋯ 菜单含重命名/删除”。Changelog 记录了变化，但需求、ADR、Plan 没有回写。
- Plan 将重命名列为范围外，实际已经实现。
- 没有 SessionListWidget / Panel 的 Qt 集成测试。

### 3.4 FR13.4 ChatWidget 会话切换

实现情况：**普通路径部分完成，并发路径不安全**。

- 手工切换会先保存旧会话，再读目标会话：`panel.py:157-169`。
- `load_session()` 会中断 LLM Controller、清 UI、恢复 ConversationManager 并渲染历史：`chat_widget.py:1140-1150`。
- 普通手工 A→B→A 在没有并发任务、没有加载失败时可以工作。

关键偏差：

- 启动恢复调用的是 `load_history()`，不是 `load_session()`：`panel.py:123-125`。因此只恢复气泡，未恢复 `_conversation`。
- `load_session()` 只调用 `SessionController.handle_abort()`；它只取消当前 LLM round，不取消正在运行的 `ExecutionEngine`。
- `_uploaded_docs`、`_pending_memory_context`、重试按钮状态、观测上下文等仍由唯一的 ChatWidget 实例共享；切换会话不清理或按会话保存。
- 任务监控仅 `reset()` UI；全局 `TaskManager` 中的任务继续存在且没有会话归属。
- Plan 风险说明承诺“历史超过 50 轮折叠”，代码没有折叠组件；实际是消息控件达到 100 后从 UI 头部淘汰。

### 3.5 FR13.5 跨项目访问

实现情况：**元数据层完成，运行上下文没有明确契约**。

- SessionManager 使用全局 `get_data_dir()/sessions`，不绑定项目。
- 创建时记录 `project_name`：`panel.py:129-130, 177-186`。

缺口：

- `project_name` 只是标签，没有记录稳定的项目 ID、variant ID 或创建时上下文版本。
- 跨项目进入旧会话时，持久化的旧 system prompt 可能继续参与 LLM 请求；当前集合工具却使用当前 `AppContext`。这会形成“语言上下文属于旧项目、工具写入当前项目”的混合状态。
- UI 没有对这种上下文漂移给出提示或“重新绑定当前项目”的明确操作。

## 4. 严重问题清单

## P0 — 迭代前必须处理

### P0-1 启动恢复会显示历史，但后端历史为空，随后可能覆盖原文件

证据：

- `panel.py:123-125`：启动时只调用 `self._chat.load_history(data["messages"])`。
- `chat_widget.py:1140-1147`：真正恢复 `_conversation` 的逻辑只在 `load_session()` 中。

影响链：

1. 重启后用户看到历史气泡，以为会话已恢复。
2. `_conversation` 实际为空。
3. 用户发送新消息时，LLM 不会收到旧历史。
4. LLM 响应后 `_auto_save_hook()` 将当前空历史加新一轮写回原会话。
5. 原 JSON 中的旧消息被覆盖。

修复方向：启动恢复必须走与普通切换相同的唯一入口，并增加“重启后首次请求包含旧历史、保存后旧历史仍在”的端到端测试。

### P0-2 后台任务没有会话归属，完成回调污染当前会话

证据：

- `TaskHandle` 没有 `session_id` 字段：`task_manager.py:29-38`。
- 翻译/后处理注册任务的 metadata 只有 mode/type/phases，没有会话 ID。
- ChatWidget 为全局 TaskManager 注册统一回调：`chat_widget.py:739-769`。
- 任务完成时直接向当前 `_conversation` 添加 observation：`chat_widget.py:774-800`。
- 会话切换只清空任务监控 UI，不取消或重新归属任务：`chat_widget.py:1148-1150`。

影响：A 会话启动任务后切到 B，A 的任务结果会写入 B；随后 `handle_task_completed()` 在 B 已被重置为 IDLE 时还可能触发状态断言。任务结果、UI 和控制状态三者失配。

修复方向：所有异步作业创建时必须携带不可变 `owner_session_id`；完成事件按 owner 路由。未激活会话的结果写入其持久化 inbox / event log，不直接操作当前 ChatWidget。

### P0-3 会话切换先提交活动 ID，后验证加载结果，存在错写和状态撕裂

证据：`panel.py:157-169` 在 `get_session()` 前先设置 `_active_session_id = session_id`，且目标加载失败时没有回滚。

影响：目标文件在扫描后被外部删除或损坏时，旧 UI / 旧 ConversationManager 仍保留，但 active ID 已指向目标。后续自动保存可能把旧会话内容写入目标，或静默保存失败。

修复方向：采用两阶段切换：先保存 outgoing → 预加载并验证 incoming → 建立新 runtime snapshot → 最后原子提交 active ID 和 UI；任一步失败都保持原会话不变并提示用户。

## P1 — 稳定性与数据契约

### P1-1 `session_id` 未验证，外部 JSON 可形成目录逃逸

`_scan()` 信任文件内部 `session_id`，而 `_path_for()` 直接拼接该值。最小复现已证明 `../outside` 可读取 `sessions/` 外的 JSON。删除接口同样可能作用于逃逸路径。

应只接受固定格式 ID（建议完整 UUID 或严格 `[0-9a-f]{12}`），并要求内部 ID 与文件 stem 完全一致；不一致文件应隔离到 quarantine，而不是进入缓存。

### P1-2 “损坏文件跳过”只处理语法错误，不处理结构错误

`_scan()` 仅捕获 `JSONDecodeError/OSError`。合法 JSON `[]` 会触发 `AttributeError` 并中断 SessionManager 初始化。`messages` 为字符串、消息项不是 dict 等也没有防护。

应引入显式 DTO 验证和 `LoadReport`，单文件失败不得影响其他会话。

### P1-3 保存失败没有用户提示，创建失败可能直接崩溃

`save_session()` 返回 bool，但 `ChatWidget.save_current_session()` 和 Panel 都忽略返回值；创建会话未捕获 `_atomic_write()` 异常。与 FR13 异常场景直接不符。

应让仓储返回 `Result` / 抛出领域化异常，由应用服务统一转换为 `on_system_message`；切换前保存失败默认中止切换，避免用户误以为已保存。

### P1-4 最近活跃会话没有可靠持久化

`get_session()` 更新 `last_active_at` 只改返回值和缓存，不写磁盘。若用户切到一个空会话后退出或进程异常终止，重启可能恢复到错误会话。

建议单独维护小型 `active-session.json` 指针，或在事务中持久化元数据；不要为了更新活跃时间重写整份大消息文件。

### P1-5 运行态隔离不完整

当前每个会话只隔离 messages。上传文档、pending memory、执行引擎、任务、观测会话和部分 UI 状态仍共享。至少需要明确以下状态的生命周期：

- 属于会话：消息、上传文档引用、工具执行结果、任务归属、观测会话 ID、待确认计划。
- 属于用户全局：Auto 模式偏好、模型配置、通用 Skill。
- 属于当前项目：AppContext、当前集合、长期记忆索引。

### P1-6 TaskManager 监听器无法正确注销

`on_completed(cb)` / `on_failed(cb)` 注册的是内部 wrapper，但 `shutdown()` 使用原始 bound method 调用 `remove_listener()`；最小复现证明监听器数量不会下降。另有匿名 `on_finished(lambda...)` 完全没有保存注销句柄。

Panel 重建后可能保留旧 ChatWidget 引用、重复回调和跨会话写入。应将回调 API 改为返回 `Subscription` / token，并在 shutdown 精确 dispose。

## P2 — 维护性、性能与质量门禁

### P2-1 JSON 方案不是真正的元数据懒加载

启动扫描仍完整解析每个会话的消息数组。短期可增加独立 index/metadata sidecar；中长期如果要支持搜索、归档、任务历史，SQLite WAL 更合适。

### P2-2 Plan 和 Story 产物不完整

- `plans/session-manager/plan.md` 引用了 3 个 `plans/session-manager/stories/story-*.md`，实际目录中不存在这些文件。
- Plan 顶部写“3/3 完成”，但所有验收框仍是 `[ ]`。
- Story 01 验收写“35 个新增测试”，实际 `test_session_manager.py` 为 24 个测试。
- Plan 中函数名 `render_history()` 与实现 `load_history()` 不一致。
- 风险回退写“删除 data/sessions 即回到单会话模式”，实际应用会重新创建目录和默认会话，并不会关闭多会话 UI。

### P2-3 ADR 与最终 UX 不同步

ADR D17 仍描述命名弹窗和“×”删除按钮；实际是秒建会话、AI 自动命名和“⋯”菜单。需要追加 ADR 更新说明，不应改写历史决策正文。

### P2-4 测试结构过于偏向单类单元测试

现有 120 个相关测试全部通过，但没有覆盖真正最危险的跨组件状态交错。既有 QA 报告据此给出“零 Major”结论已经过时。

### P2-5 SessionManager 暴露可变缓存对象

`list_sessions()` 返回 `_cache.values()` 中的原始 dict 引用，调用方可以绕过仓储直接改变缓存。应返回不可变 DTO 或深/浅复制后的快照。

## P3 — 后续体验优化

- 大量会话时增加分页 / 虚拟列表、搜索、归档。

- 增加“运行中任务：继续后台运行 / 取消并切换 / 暂不切换”的明确策略。

## 5. 三种改进方案

### 方案 A：在现有 JSON + Panel 协调架构上做最小加固

内容：

- 修复启动恢复统一调用 `load_session()`。
- Panel 改为两阶段切换。
- SessionManager 增加 schema 校验、ID 校验、active 指针和保存错误返回。
- TaskHandle metadata 增加 `session_id`，回调先过滤 owner。
- 切换时统一取消旧 ExecutionEngine。

优点：改动最小、两三个 Story 可完成、回归面较窄。

缺点：ChatWidget 和 Panel 继续承担应用编排；TaskManager 仍为全局单例；会话状态继续分散，下一次扩展上传文档、任务恢复、观测恢复时会再次堆条件分支。

适用：只想尽快消除 P0，且半年内不扩展会话能力。

### 方案 B：引入 Session Application Service + SessionRuntime（推荐）

核心设计：

```text
SessionListWidget / ChatWidget
          │ UI Intent / Render Model
          ▼
SessionApplicationService
  ├─ SessionRepository (port)
  │    └─ JsonSessionRepository v2 (adapter)
  ├─ ActiveSessionStore
  ├─ SessionRuntimeRegistry
  └─ TaskRouter(owner_session_id)
          │
          ├─ SessionRuntime A: Conversation + ControllerState + Attachments + TaskRefs
          └─ SessionRuntime B: Conversation + ControllerState + Attachments + TaskRefs
```

关键原则：

- UI 不再自行决定保存/加载顺序，只发出 `switch_session(target_id)`。
- Application Service 执行 prepare → checkpoint → load/validate → bind → commit。
- `SessionRuntime` 明确保存会话级运行状态；暂时不需要让所有会话常驻，可只常驻 active + 有运行任务的会话。
- 所有后台事件带 `owner_session_id` 和 `correlation_id`，由 TaskRouter 路由。
- inactive 会话的完成结果先写入持久化事件/inbox，激活时再渲染。
- system prompt 作为可重建的临时上下文，不和用户历史等价持久化；每次激活根据当前项目生成或明确采用“冻结旧上下文”策略。

优点：解决当前根因；适合继续扩展任务、附件、观测、恢复和多 Agent；可逐步迁移，不必重写 UI。

缺点：需要新增应用层契约，并同时调整 FR13、FR14、ADR-008 与任务 Plan。

推荐理由：当前问题不是单个 if 缺失，而是“会话身份没有贯穿异步工作流”。方案 B 能以有限成本建立 identity / ownership / transaction 三个核心约束，明显比继续在 ChatWidget 上打补丁更稳。

### 方案 C：SQLite WAL + 事件化会话存储

内容：

- 用 SQLite 表保存 session、message、attachment、task、event、active pointer。
- 所有消息和任务结果 append-only，使用事务和 WAL。
- UI 查询投影，支持搜索、归档、分页、崩溃恢复。

优点：事务、并发、索引、分页和迁移能力最好；后续会话搜索、任务历史和审计自然落地。

缺点：对当前 FR13 明显偏重；需要数据迁移、存储版本管理和更多测试；若只维持几十个短会话，收益暂时不足。

适用：路线图已确定要做会话搜索、长历史、任务恢复、多窗口或云同步时。

## 6. 推荐目标方案与渐进迁移

推荐采用 **方案 B，底层第一阶段继续使用 JSON Repository**。等会话搜索、任务历史或多窗口成为确定需求后，再把 Repository adapter 从 JSON 替换为 SQLite；应用层和 UI 契约无需重写。

### 阶段 0：立即止血

1. 启动恢复统一走 `load_session()`。
2. 会话切换先加载验证，成功后再提交 active ID。
3. 切换期间取消或隔离 LLM worker / ExecutionEngine。
4. 自动保存失败必须提示，并在切换前默认阻止切换。
5. 暂时禁止活动后台任务期间静默切换，直到 owner routing 完成。

### 阶段 1：建立存储契约

1. 定义 `SessionMeta`、`SessionSnapshot`、`MessageRecord`、`LoadReport`。
2. 引入 `schema_version: 2`，采用 envelope：`{schema_version, meta, messages, runtime_refs}`。
3. 增加 v1 扁平 JSON → v2 的只读迁移器；首次成功保存再升级文件。
4. 强校验文件 stem、session ID、字段类型、消息 role；异常文件 quarantine。
5. active pointer 独立小文件原子写入，避免切换会话时重写全部消息。

### 阶段 2：抽出应用服务

1. 新建 `SessionApplicationService`，Panel 只绑定 UI 信号与 render model。
2. 实现 `switch_session()` 两阶段协议和失败回滚。
3. 新建 `SessionRuntime`，先纳入 conversation、controller、attachments、pending plan、task refs。
4. 删除 ChatWidget 向上遍历 `_find_panel()` 和访问 Panel 私有字段的反向依赖。

### 阶段 3：任务归属与异步路由

1. Task 注册 API 强制要求 `owner_session_id`。
2. TaskEvent 包含 owner、correlation、status、payload。
3. active 会话事件更新 UI；inactive 会话事件写 inbox 并更新列表徽标。
4. 监听器改为 subscription token，生命周期可验证。
5. 切换策略明确为 cancel / detach / block，不能依赖隐式 reset。

### 阶段 4：性能与体验

1. 历史消息分页或虚拟化渲染。
2. 元数据 index/sidecar，避免启动解析全部消息。
3. 跨项目会话显示旧项目标签，进入时提示上下文策略。
4. 若需求增长，再引入 SQLite Repository adapter。

## 7. 建议修改的 ADR

### ADR-008 追加 D18：SessionApplicationService 是唯一切换协调者

禁止 Panel / ChatWidget 直接拼接保存、加载、提交 active ID 的顺序。UI 只能提交 intent，服务返回成功或错误 render model。

### ADR-008 追加 D19：会话运行态与资源归属

定义 SessionRuntime 的边界，并明确消息、附件、计划、任务、观测的 owner；全局配置和项目 AppContext 不得误放入会话快照。

### ADR-008 修订 D16：两阶段切换和失败回滚

新流程：

```text
prepare target
→ checkpoint outgoing
→ validate/load incoming
→ apply switch policy to running work
→ bind incoming runtime
→ commit active pointer
→ render
```

任何失败均保持 outgoing 活跃且不得修改 UI。

### ADR-008 修订 D17：同步最终 UX

记录秒建、自动命名、“⋯”菜单、重命名已经成为正式设计；或若坚持原需求范围，则明确重命名属于后续 FR。

### ADR-004 追加会话切换并发约束

所有 worker、ExecutionEngine 和 TaskManager 事件必须携带 owner / generation token。回调落地前检查 generation，避免过期事件更新新会话。

### 新 ADR：会话持久化版本与迁移

定义 schema version、ID 规则、原子性强度、active pointer、quarantine、兼容期和 JSON→SQLite 的 port/adapter 边界。

## 9. 新验收标准

以下条件全部满足后，FR13 才适合恢复“已实现”：

1. 重启后 UI 历史和 `ConversationManager` 历史一致；下一次 LLM 输入包含旧对话。
2. 重启后追加一轮并保存，不会丢失恢复前消息。
3. 切换到空会话并退出后，重启仍恢复该空会话。
4. outgoing 保存失败时，UI 提示错误且 active 会话不变。
5. 目标文件被外部删除、改坏或 schema 不合法时，切换失败且旧会话、旧 UI、旧 active ID 都保持不变。
6. 合法 JSON 非对象、messages 非列表、消息项缺字段只影响单文件，不阻断其他会话加载。
7. 内部 session ID 与文件名不一致、含路径分隔符或 `..` 时被拒绝 / quarantine。
8. 在 A 启动任务后切到 B，任务完成只更新 A；B 的消息和 Controller 状态不变。
9. 在 A 启动 Plan / LLM streaming 后切到 B，A 的迟到回调不能更新 B。
10. 删除当前会话时，有运行任务必须按明确策略处理；不得产生孤儿回调。
11. 连续创建、切换、删除 100 次，无重复 listener、悬空 ChatWidget、存活 worker 或任务线程泄漏。
12. 关闭 / 重开 Panel 多次后，每个 TaskEvent 只触发一次 UI 回调。
13. v1 扁平 JSON 可无损读取并升级到 v2；未知新版本只读拒绝，不破坏文件。
14. 100 个会话、每个 1 MB 历史时，启动只读取元数据，消息在激活时加载。
15. 跨项目打开旧会话时，UI 明确显示旧项目标签并按已选策略刷新或冻结 system context。

## 12. 最终建议

不要直接把 SessionManager 替换成数据库，也不要继续只在 ChatWidget 增加零散清理逻辑。最优迭代路径是：

1. 先用小补丁止住启动覆盖和切换错写。
2. 紧接着引入 `SessionApplicationService + SessionRuntime + owner_session_id`。
3. 保留 JSON 作为第一版 Repository adapter，同时建立 schema v2 和迁移契约。
4. 通过端到端并发测试确认会话 identity 从 UI、Controller、Engine 到 TaskEvent 全链路一致。
5. 只有在搜索、归档、任务恢复等需求明确后，再切换 SQLite adapter。

这条路线既能快速消除当前数据风险，也能避免为 FR14、附件、观测和多 Agent 继续累积会话隔离债务。
