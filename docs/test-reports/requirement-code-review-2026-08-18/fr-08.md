# FR8 项目持久化与翻译版本管理：纵向实现审查

**审查日期**：2026-08-18  
**审查方式**：独立纵向只读审查  
**需求范围**：`docs/requirements.md` FR8.1–FR8.12  
**追踪链**：需求 → ADR-006 → `plans/project-persistence/plan.md` → Story 01–08 → changelog → 实际代码 → tests  
**结论口径**：以当前仓库代码能否稳定满足验收为准，不以文档中的“已实现”状态为准。

## 1. 执行结论

FR8 已经搭出了项目、版本、工作区、快照、归档、自动保存和分版本写回的完整 UI 表面，但当前实现还不能作为可靠的“项目数据层”。主要问题不是缺少按钮，而是版本隔离、保存时机、恢复语义和数据演进契约不成立。

综合判断：

- **功能入口完成度约 65%**：大部分操作有 UI 和基础文件读写代码。
- **可靠验收完成度约 35%–40%**：12 个 FR 中没有一个具备完整自动化验收证据；FR8.4、FR8.6、FR8.9、FR8.11、FR8.12 存在会导致数据丢失、版本串写或错误输出的关键缺陷。
- **文档状态失真**：需求和 Plan 均标记“已实现”，但 Plan 的 47 个验收勾选仍全部是 `[ ]`，仓库中也没有 FR8 持久化自动化测试文件。`docs/test-reports/project-persistence.md` 是历史人工审查记录，不是可重复运行的测试套件。
- **不建议继续在 `MainWindow` 上追加补丁**。推荐先建立 `ProjectSession + ProjectRepository + PersistenceCoordinator` 的应用层，再渐进迁移 UI、Agent 和写回流程。

## 2. 需求到实现映射

### FR8.1 项目模型 — 部分实现

已有：

- `ProjectHandle` 提供项目名、源文件列表、版本列表和活跃版本。
- `AppContext` 持有 `WorkspaceState`、`ProjectHandle`、活跃版本和 `VariantStore`。
- 项目可登记多个源文件。

偏差：

- 一个 `VariantStore.translations: dict[entry.id, translation]` 覆盖项目全部源文件，没有 `source_id` 维度。不同插件或格式出现相同复合键时会互相覆盖。
- 版本切换只处理当前活跃集合，其他 `CollectionSlot` 保留上一个版本的内存数据。项目的“多源文件集合”与“版本”没有真正形成三层隔离。
- `AppContext`、Step2 和 `VariantStore` 各自保存标签状态，存在三个事实来源。

完成度：**部分，约 45%**。

### FR8.2 工作区文件 — 部分实现

已有：

- `WorkspaceState` 读写 `workspace.json`，记录项目映射、活跃项目、保存配置和最近筛选状态。
- 写入使用临时文件后 `replace`。

偏差：

- `workspace.json.version` 只有常量值，没有 schema 校验和迁移分派。
- 载入损坏 JSON 时静默回到空模板，会把“文件损坏”伪装成“首次启动”。
- 旧 schema 缺字段时不会与默认模板深度合并。
- UI 布局仍由 `QSettings` 保存，并非需求描述中的 workspace 状态。
- workspace 保存的是可变项目名到绝对路径的映射，项目改名需要跨文件同步，且不利于归档迁移。

完成度：**部分，约 60%**。

### FR8.3 源文件存储 — 部分实现

已有：

- `{project}/{variant}/current.json` 存储 translations、labels、label_library。
- `snapshots/` 目录和 JSON 快照已存在。

偏差：

- 持久化键仍使用 `entry.id`，而 ADR-002 后续已把 `entry.key` 定为稳定主键。当前二者多数相同，但存储契约没有跟进后续架构。
- `collect_from()` 只追加非空译文；用户清空译文后，旧译文不会从 JSON 删除，下次恢复会“复活”。
- `apply_to()` 只覆盖命中的译文，不清除目标版本中不存在的译文，空白版本会继承前一版本的屏幕数据。
- `stage` 不持久化，`apply_to()` 也没有按“有译文 → stage 1”推导。重启后可出现“有译文但 stage=0”。有疑问、已检查、已审核、锁定、隐藏等用户状态都会丢失。
- 多源文件没有 source namespace，translation/label 键可能碰撞。

完成度：**部分，约 40%**。

### FR8.4 自动恢复 — 未可靠实现

已有：

- 启动读取活跃项目和版本。
- ESP 通过后台 worker 重解析并套用译文。
- 筛选状态通过延迟定时器恢复。

偏差：

- 只恢复 `type == "esp"` 的源文件；已登记的 EET、XT、SST 不会自动恢复。
- 没有记录或比较源文件哈希，需求要求的“哈希变更后初始化空白并提示”完全缺失。
- 标签和标签库没有从 `VariantStore` 注入 Step2/AppContext；版本恢复实际上只恢复译文。
- 以固定 3 秒定时器恢复筛选，不等待所有异步解析完成，慢磁盘/大插件时存在竞态。
- 打开/导入项目不清空旧项目的 slots，旧集合可残留到新项目中。
- `ProjectHandle.load()` 对损坏文件返回空对象，调用方没有统一的 `missing/corrupt/incompatible` 分支。

完成度：**失败/部分，约 25%**。

### FR8.5 快照操作 — 存在数据破坏缺陷

已有：

- 可保存和选择加载快照。
- `VariantStore` 提供 list/load/delete 方法。

偏差：

- 保存快照前没有从当前运行时集合和标签中 collect，快照可能落后于屏幕上的最新编辑。
- `VariantStore.load_snapshot(path)` 返回的实例把 `_path` 设为快照文件本身。加载后该实例成为当前 `variant_store`，后续手动/自动保存会覆盖历史快照，而不是写回 `current.json`。
- 加载快照只覆盖命中的译文，不清空不存在项，也不恢复标签到 UI。
- 快照删除没有可用 UI；ProjectBar 的“管理快照”仍是 `lambda: None`。
- 快照不是不可变对象，没有 checksum、来源 revision 和恢复审计记录。

完成度：**高风险部分实现，约 35%**。

### FR8.6 自动保存 — 未达到可靠保存语义

已有：

- 5 分钟 QTimer、2 秒防抖、Ctrl+S、关闭事件保存入口。
- `dirty` 字段和 `dirty_changed` 信号存在。

偏差：

- Step2 的译文编辑、标签增删、stage 修改都没有调用 `ctx.mark_dirty()`。因此主要 UI 编辑不会触发 2 秒防抖。
- `_save_current_project()` 只在 dirty 时调用 `variant_store.save()`，但不先 `collect_from()`。关闭程序、新建/打开项目、导出归档时若防抖尚未执行，会把旧缓存写回，最新屏幕编辑丢失。
- Agent 编辑调用 `ctx.notify_collection_modified()`，但真实 `AppContext` 没有这个方法；协议存在、实现缺失。回调会在主线程记录异常，Agent 修改不会可靠刷新/标脏。
- `auto_save_interval_minutes` 和 `auto_save_on_edit` 配置未被启动逻辑使用；`_auto_saver.start()` 固定采用默认 5 分钟。
- 自动保存仍在 UI 线程序列化和写文件。
- 保存过程中没有 revision 比较：若后台化后不增加 revision/快照语义，很容易把保存期间的新编辑误标成 clean。

完成度：**失败，约 25%**。

### FR8.7 项目切换 — 未形成隔离事务

已有：

- 新建项目、打开 project.json、保存当前项目。
- workspace 可登记多个项目。

偏差：

- ProjectBar 没有已登记项目下拉；“打开项目”不是需求中的工作区项目切换体验。
- 新建项目时没有先可靠 collect/save 当前项目。
- 打开新项目时不清理旧 slots、labels、filters 和选中状态。
- 当前项目保存与目标项目加载没有事务边界；中途解析失败会留下混合上下文。
- 本地 Agent 只有只读查询，没有 switch/create/save/snapshot 等统一应用服务。

完成度：**部分，约 35%**。

### FR8.8 `.transbridge` 单体项目文件 — 部分实现

已有：

- 可导出项目目录中的 JSON。
- 导入检查绝对路径/`..`，并限制总解压大小 500MB。

偏差：

- 命令行入口没有解析 `.transbridge` 参数，双击/拖入打开未实现。
- 导出前调用的是不 collect 的 `_save_current_project()`，归档可能缺少最新编辑。
- 覆盖现有项目时直接 `extractall(dest_dir)`，没有 staging、完整验证、原子替换和回滚；失败会把新旧文件混合。
- 未限制成员数量、单文件大小、压缩比、重复路径、特殊文件；没有 manifest/checksum/schema version。
- 归档中的 source path 是原机器绝对路径，又不包含源文件和重定位映射，分享后无法自动恢复。
- 导入后不清空旧 slots，也不完整恢复源文件。

完成度：**部分，约 45%**。

### FR8.9 翻译版本模型 — 关键隔离失败

已有：

- 每个版本有独立目录和 current.json。

关键失败：

- A 版本有译文、B 版本为空时，从 A 切到 B，`apply_to()` 不清空 A 的译文，B 视图仍显示 A。
- 多集合只更新当前集合；切换 slot 后会看到该 slot 上一次所在版本的数据。
- labels/label_library 没有随版本切换注入 UI。
- 版本存储不含 source_id，多个源文件之间不能可靠隔离。

完成度：**失败，约 20%**。

### FR8.10 版本创建与复制 — 表面实现、语义不完整

已有：

- 可创建空版本和复制当前版本。
- `copied_from` 元数据存在。

偏差：

- 新版本切换时不会清空旧译文，因此“空白版本”并不空白。
- 复制前 `_save_current_project()` 不 collect，最近编辑可能未复制。
- 只复制 VariantStore 缓存；UI 与 AppContext 中未同步的标签不会复制。
- 版本名非法时底层会抛 `ValueError`，UI 路径没有统一捕获和错误展示。

完成度：**部分，约 45%**。

### FR8.11 版本切换 — 未满足保存/放弃与标签隔离

已有：

- 下拉可选择版本。
- dirty 时支持 prompt 或自动保存分支。

偏差：

- `active_variant` setter 已发信号，`_switch_to_variant()` 又显式 emit，同一次切换重复通知。
- “放弃修改”后仍调用 `_save_current_project()`；虽然通常保存的是旧缓存，但语义隐晦且容易引入误写。
- 切换只 apply 当前集合，不处理项目所有 slots。
- 标签库不随版本切换。
- `VariantStore.apply_to()` 非 replace 语义，导致版本串写。

完成度：**失败，约 25%**。

### FR8.12 版本写回 — 输出可能串版

已有：

- 多版本时可选择全部版本，每个版本建立输出子目录。
- 当前写回器得到 output override。

偏差：

- 全版本循环复用同一个 live collection，逐个 `apply_to()` 只叠加不清空，后一个版本会携带前一个版本的译文。
- 同一个 plugin/collection 对象在多个版本间复用，写回过程与 UI 状态耦合。
- 只恢复当前 VariantStore 的命中项，不能保证恢复前的精确内存状态。
- 没有真正持久化 `workspace.settings.write_back.mode/last_output_dir`。
- 某些底层写回函数以弹窗/返回而不是异常表达失败，批量汇总可能把失败当成功。

完成度：**失败，约 25%**。

## 3. 关键缺陷分级

### P0：必须先修复，否则会丢数据或产出错误版本

1. **版本 replace 语义缺失**：切换空白/稀疏版本不清空旧译文；多版本写回会串版。
2. **保存生命周期丢数据**：关闭、新建/打开项目、导出、复制版本、保存快照前没有统一 collect 当前事实状态。
3. **快照路径错误**：加载快照后保存会覆盖快照文件，而非 current.json。
4. **标签三套状态分裂**：Step2、AppContext、VariantStore 互不一致；标签无法可靠恢复、切换和由 Agent 修改。
5. **多源文件无命名空间**：不同源文件相同 entry key 会覆盖；切换版本只处理 active slot。
6. **没有 FR8 自动化测试**：当前所有“完成”结论不可回归，尤其缺少数据隔离和故障注入测试。

### P1：进入下一次功能迭代前完成

1. 建立 schema version、验证、迁移、corrupt/quarantine/backup 恢复策略。
2. 恢复所有源类型，增加 source fingerprint 和确定性异步 barrier。
3. 项目打开/切换使用 staging session，成功后一次性替换 AppContext；失败保持旧项目不变。
4. `.transbridge` 使用 staging 解压、manifest/checksum、原子发布和回滚。
5. 全版本写回改为不可变 materialized view，不再修改 live collection。
6. 实现统一 Project Application Service，并让 UI/Agent/MCP 共用。
7. 修复本地 Agent 项目列表：当前代码遍历 workspace.projects 字典键后用 `getattr(p, 'name', '')`，会返回空名称。

### P2：可维护性和体验优化

1. 自动保存移出 UI 线程，使用 immutable snapshot + revision CAS 清理 dirty。
2. 用稳定 `project_id/variant_id/source_id` 做目录和引用，显示名称只做 metadata，降低重命名跨文件风险。
3. 项目选择器、快照管理器、冲突重命名、源文件重定位向导。
4. 持久化 stage、translation provenance、revision、updated_by；明确三态标记是否纳入跨会话。
5. 清理 `MainWindow` 中的持久化业务逻辑，降低上帝类风险。

### P3：后续扩展

1. 增量/差分快照、快照保留策略和空间配额。
2. 可选嵌入源文件的 portable archive。
3. 多实例文件锁、只读打开、冲突检测。
4. 大项目性能指标、增量序列化或 SQLite 后端。

## 4. 三种优化方案及取舍

### 方案 A：继续修补 JSON v1

做法：修 `apply_to/collect_from`、补 dirty 事件、标签注入、snapshot path、恢复全部源类型和测试，目录结构保持不变。

优点：改动最小，1–2 个短迭代可止血；对用户文件兼容最好。

缺点：多源键冲突、跨文件事务、schema 演进、MainWindow 耦合仍在；之后还要二次重构。

适用：仅作为 P0 热修，不宜作为最终架构。

### 方案 B：JSON v2 + ProjectSession/Repository（推荐）

做法：继续保留人类可读 JSON，但引入稳定 ID、source namespace、typed schema、repository、revision、备份/恢复和应用服务。

建议结构：

```text
projects/{project_id}/
  project.json
  variants/{variant_id}/current.json
  variants/{variant_id}/snapshots/*.json
  recovery/commit-manifest.json
```

`current.json` 建议最少包含：

```json
{
  "schema_version": 2,
  "project_id": "...",
  "variant_id": "...",
  "revision": 42,
  "sources": {
    "source_uuid": {
      "fingerprint": {"sha256": "...", "size": 123},
      "entries": {
        "stable_entry_key": {
          "translation": "...",
          "stage": 3,
          "labels": ["label_uuid"]
        }
      }
    }
  },
  "label_library": {}
}
```

优点：保留 JSON 可读性和归档兼容；能解决当前核心一致性问题；迁移风险可控；最符合现有产品规模。

缺点：需要自建 revision、备份和多文件提交协议；非常大项目的全量 JSON 仍有性能上限。

### 方案 C：SQLite 运行库 + JSON 交换格式

做法：每项目一个 SQLite，使用事务/WAL/schema migration；`.transbridge` 和快照导出为 JSON manifest + 数据文件。

优点：事务、迁移、索引、增量更新和崩溃恢复成熟；大项目性能最好。

缺点：迁移面最大，用户无法直接 diff current.json；与 FR8.3 当前文件格式冲突，需要正式改需求和 ADR；打包/备份流程更复杂。

适用：出现 10 万级以上条目、频繁增量保存、多进程访问或历史查询后再采用。

**推荐决策**：以方案 B 为目标，先取方案 A 的 4 个止血改动：精确 replace、统一 collect、快照 current path、标签单一事实源。不要直接进行 SQLite 大迁移。

## 5. 推荐目标设计

### 5.1 ProjectSession 是唯一运行时事实源

- `ProjectSession` 持有 project/variant/sources/entries/labels/filter/dirty_revision。
- Step2 只显示 Session 的 ViewModel，不再拥有独立标签权威数据。
- AppContext 只持有当前 Session 和跨模块服务，不直接拼装持久化流程。
- 每个编辑入口（UI、Agent、翻译器、校对器）调用同一组命令：`EditTranslation`、`SetStage`、`AssignLabel` 等；命令成功后 revision +1。

### 5.2 PersistenceCoordinator 统一生命周期

统一入口：

- `save(session, reason)`
- `switch_project(target_id, save_policy)`
- `switch_variant(target_id, save_policy)`
- `create_snapshot(name)`
- `restore_snapshot(snapshot_id)`
- `export_archive(path)`
- `recover()`

保存时从 Session 创建 immutable snapshot；后台落盘结束后，只有当 `saved_revision == session.revision` 才清 dirty。这样保存期间发生的新编辑不会被误标成已保存。

### 5.3 VariantMaterializer 使用精确替换

`materialize(variant_id, source_id)` 必须得到一个完整、不可变、独立的条目视图：

- 缺失译文明确写为空字符串；
- stage/labels 按目标版本完整替换；
- 不直接修改其他版本或 live UI collection；
- Writer 接收 materialized view，批量写回不触发 UI 版本切换。

### 5.4 加载采用两阶段提交

1. staging：读取 workspace/project/variant，验证 schema，迁移，解析全部源，校验 fingerprint，构建新 Session。
2. commit：全部成功后一次性替换 AppContext 当前 Session；失败保留原 Session。

源文件变更不建议直接“清空一切”。更好的行为是输出 reconcile report：matched/added/removed/orphaned/conflicted，让用户选择迁移已匹配译文或创建空白版本。需要同步修订 FR8.4。

### 5.5 崩溃恢复

- 临时文件必须在目标同目录、使用唯一名称；写入后 flush + fsync，再 replace。
- current.json 保留最近 3 个 checksum 备份，与 Plan 风险表原承诺一致。
- load 返回 `LoadResult(status=ok|missing|corrupt|incompatible|recovered)`，禁止静默空模板。
- 跨 workspace/project/current 的提交写 manifest；恢复时只接受最后一个完整 revision。
- 对写入阶段做故障注入测试：serialize、temp write、fsync、replace、manifest commit 任一步失败均不损坏最后成功版本。

### 5.6 Agent/UI 对等

Agent 不直接操作 `AppContext` 私有状态，应调用 ProjectApplicationService。建议工具：

- read：`list_local_projects`、`get_project_status`、`list_variants`、`list_snapshots`、`get_recovery_status`
- write：`save_project`、`switch_local_project`、`switch_variant`、`create_variant`、`copy_variant`、`create_snapshot`、`restore_snapshot`
- admin：`delete_variant`、`import_project_archive`、`replace_existing_project`

所有 write/admin 工具复用 UI 的 save policy、确认护栏和审计日志。

## 6. ADR 修改建议

### ADR-006 应改为 Superseded 或发布 v2 更新

## 8. 必须加入的验收测试

### 隔离与数据完整性

- A 有译文、B 为空：A→B 后所有 B 缺失项必须为空；B→A 精确恢复。
- 两个 source 存在相同 entry key：保存/切换/写回互不覆盖。
- 清空译文后保存、重启，旧译文不得复活。
- stage 0/2/3/5/9/-1、labels、label library 重启后精确一致。
- 切换非活跃 slot 后仍展示当前 variant 对应的数据。

### 保存与崩溃

- UI 编辑后 2 秒内立即关闭，最新编辑仍保存或明确阻止关闭并提示失败。
- Agent 编辑后 dirty/revision/UI refresh/自动保存均发生。
- 保存期间继续编辑，旧 revision 落盘后 session 仍保持 dirty。
- 在 serialize/temp/fsync/replace/manifest 每一步注入异常，最后成功版本仍可恢复。
- current.json 损坏时从备份恢复并给出可见提示；不允许静默空项目。

### 项目/版本/快照

- 新建、打开、切换失败不得污染旧 Session。
- 项目重命名后所有 repository path 更新，不重新创建旧目录。
- 快照保存包含当前未落盘编辑；加载后保存只写 current.json，快照 checksum 不变。
- delete variant 至少保留一个，取消/失败无副作用。

### 源文件恢复

- ESP/EET/XT/SST 混合项目重启全部恢复。
- 指纹不变时正常恢复；改变时产生 reconcile report。
- 多源并发解析顺序不同，最终 Session 结果一致。

### 归档与写回

- archive 导出前强制保存当前 revision。
- 导入中途失败、schema 不兼容、checksum 错、重复成员、超数量/压缩比均不影响现有项目。
- CLI 传入 `.transbridge` 后可完成导入/打开或明确冲突交互。
- 全版本写回 golden test：每个目录只包含本版本译文，写回后 live Session 完全不变。

### Agent/UI parity

- 同一个 ProjectApplicationService 用 UI adapter 和 Agent adapter 执行，状态和错误码一致。
- `list_local_projects` 返回真实项目名，不为空字符串。
- Agent 的 save/switch/snapshot 操作遵守与 UI 相同的确认和 save policy。

## 9. 渐进迁移路线

### Phase 0：止血（P0）

- 给 VariantStore 增加 exact replace/materialize，并在切换前清空目标字段。
- 所有生命周期操作统一调用 `collect_and_save()`。
- 修正 snapshot restore 的 current path，快照保持不可变。
- 将 Step2 标签迁移到 AppContext/Session 单一事实源。
- 立即补 10–15 个核心回归测试。

### Phase 1：在旧 UI 旁引入服务层

- 新建 ProjectSession、ProjectRepository、ProjectApplicationService。
- MainWindow 先改为调用服务，不改变用户操作界面。
- 使用 adapter 读取旧 JSON v1，写入时可选择 dual-write v1/v2 进行验证。

### Phase 2：schema v2 与全源恢复

- 引入稳定 IDs、source namespace、stage/revision/fingerprint。
- 提供 v1→v2 dry-run、备份、迁移报告和回滚。
- staging 加载通过后再切换 AppContext。

### Phase 3：快照/归档/写回解耦

- 快照与归档都从 immutable SessionSnapshot 生成。
- Writer 从 VariantMaterializer 获取独立视图。
- `.transbridge` v2 使用 manifest + checksum + staging import。

### Phase 4：Agent/MCP 对等与清理

- Agent 工具接入同一应用服务。
- 删除 MainWindow 中重复业务逻辑、AppContext/Step2 标签副本和旧 overlay API。
- 通过全部 FR8 traceability gate 后，才能把 requirements/Plan 状态重新标记为“已实现”。

## 10. 最终建议

FR8 的下一轮不应首先增加更多 UI 功能，而应先把“一个项目在任意保存、切换、崩溃、恢复、Agent 修改和多版本写回情况下都得到同一份确定数据”作为唯一目标。

推荐立项 `project-persistence-v2`，选择 **JSON v2 + ProjectSession/Repository**。先用一个短迭代修 P0 数据串写和丢失，再用两个迭代完成 schema/recovery/全源/无副作用写回，最后接 Agent/MCP。完成这些门禁后，FR8 才适合恢复为“已实现”。

## 11. ParaTranz JSON 身份边界补充

用户提供的 ParaTranz 文件中，数值 `id` 是平台外部 ID，`key` 是用户稳定 ID。FR8 的 JSON v2 不能把外部 `id` 混入 Variant/label/translation 的持久化键。

调整建议：

- VariantState、labels、revision、task results 始终以 EntryKey 存储；
- ParaTranz id 保存为带 `system/project_id/file_id` scope 的 external reference；
- external reference 可以随在线同步刷新，但不得导致 Variant key 重写；
- `.transbridge` 项目归档可以保存 external refs，标准 ParaTranz JSON 导出只输出平台认识的字段；
- 同一 ParaTranz JSON 被导入不同项目时，不得把数值 id 当作跨项目全局唯一值；
- JSON v1→v2 迁移要区分“历史本地 id”与“ParaTranz remote id”，无法判定时生成迁移报告，禁止静默猜测。

专项合同见 [ParaTranz JSON 双 ID 兼容性调整](paratranz-json-compatibility-adjustment.md)。
