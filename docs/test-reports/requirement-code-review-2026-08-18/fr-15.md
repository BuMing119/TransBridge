# FR15 纵向审查：FOMOD 安装包翻译与通用翻译记忆系统

> 审查日期：2026-08-18  
> 审查方式：独立纵向审查（需求 → ADR → Plan/Story → Changelog → 真实代码 → 测试/发布）  
> 审查范围：FR15.1～FR15.9，并核对其对 FR16 通用文件/词条能力的复用  
> 变更边界：本次只新增审查报告，不修改需求、ADR、Plan、Story 或业务代码

## 1. 结论先行

FR15 当前不能按“完整可用于生产的 FOMOD 翻译能力”验收。

翻译记忆的基础数据结构、ZIP 文件操作、键迁移、简单 XML 翻译、过滤组装、GUI 入口等局部能力已经存在，现有 43 个相关测试也全部通过；但端到端主路径仍属于“功能原型/骨架”，存在会生成错误成品、静默掩盖失败、删除 FOMOD 必需图片、选错目标语言译文、取消后仍打包等问题。

核心判断如下：

- **翻译记忆（FR15.1）**：基本模型可用，但项目作用域、目标语言隔离、更新语义、STALE 行为、冲突候选及 Stage 不变量均不完整。适合作为实验性单语言词典，不适合作为多来源、多语言、自动流水线的最终仲裁器。
- **归档/差异/过滤（FR15.2/15.3/15.6）**：ZIP 主路径可用；7z/RAR 的项目依赖和 `unrar.exe` 分发未落地。根目录归一化算法对真实“解压目录下多一层包装目录”的场景无效。默认过滤会删除 `fomod/*.png|jpg`，并默认放行未知扩展名。
- **插件迁移/翻译/写回（FR15.4）**：组件调用顺序存在，但 TM 没有传入当前 mod 上下文，写回和 AI 异常被吞掉，失败后仍会打包并报告“完成”。
- **FOMOD XML（FR15.5）**：UTF-16LE+BOM 基础读写已实现；只翻译叶子文本，不翻译 `installStep/group/plugin` 的 `name` 属性，也没有接入 TM 文本索引；`info.xml` 未进入流水线。
- **GUI/可配置性（FR15.7/15.9）**：输入、输出、格式、目标语言、AI 开关和过滤扩展名已有控件，但不是 Plan 所述四步向导；没有 diff 审核、输出预览、冲突仲裁、真实进度或取消按钮，结果摘要也不满足需求。
- **文档状态**：`requirements.md` 仍标“待方案”，Plan 顶部标“已确认”、验收框全部未勾选，而 INDEX/Changelog 又标“已实现”。这些状态不能同时成立。

推荐不要继续在当前 `FomodPipeline.run()` 上堆条件分支。应采用“**分阶段、可预览、事务式流水线 + 带语言/项目身份的 TM V2 + 统一候选仲裁**”方案，保留现有 parser/writer/AutoTranslator/fileops 作为端口适配器，逐阶段替换，而不是大爆炸重写。

### 2.4 额外最小行为复现

现有测试未覆盖的最小复现得到以下结果：

1. TM 键命中但原文变化时，`apply_to_collection()` 仍将旧译文写入，条目 `stage` 保持 0。
2. 当前 mod 的词典文本命中时，查询直接返回，不收集其它词典的不同译文，`conflicts=[]`。
3. 同一 mod、同一原文再次写入新译文，默认仍保留旧译文，不符合需求中的“已存在原文覆盖新译文”。
4. 默认 `FilterRules()` 把 `fomod/screenshot.png` 判定为剔除。
5. 解压根目录为 `new/Wrapper/fomod/ModuleConfig.xml` 时，`normalize_root(new)` 仍返回 `new`，没有定位到 `new/Wrapper`。

这些结果与后文代码静态证据相互印证。

#### TM 的两个结构性设计缺口

1. **目标语言缺失**：FR15.9.3 允许中文、繁中、英文、日文，但 `.tbdict` 没有 `source_locale/target_locale`。选择日文时仍可能套用中文 TM。
2. **project scope 无所有者**：重构删除 `scope_id` 后，只剩 `scope='project'` 标签，没有 `owner_project_id`。所谓“项目专属”无法执行隔离。

因此，TM V2 的词典身份至少应包含：

```text
DictionaryIdentity = {
  game_id,
  mod_file_id,
  source_locale,
  target_locale,
  visibility: global | project,
  owner_project_id?: str
}
```

仍可保持“一本文件对应一个 mod”的用户心智；语言/项目可通过目录分区或文件内强校验实现，不必回退为旧式混装大库。

归档安全还缺以下策略：

- 最大文件数、总展开大小、单文件大小、压缩比、递归归档/符号链接策略。
- 解包到临时 staging 后再发布，而不是直接在目标目录产生部分文件。
- 7z/RAR 的损坏归档、缺后端、恶意路径和资源炸弹测试。

## 5. 关键缺陷分级

### P0：必须在继续宣称“已实现”前修复

#### P0-1 静默失败后仍发布成品

- `_ai_translate()` 捕获所有异常并返回 0（`pipeline.py:157-168`）。
- `_write_back()` 捕获所有异常并 `pass`（`pipeline.py:170-183`）。
- 流水线随后仍组装、打包并返回 `archive_path`（`pipeline.py:91-100`）。

结果可能是“界面显示翻译完成，但插件根本没有写回”。这不是可降级错误，应至少标为该插件失败，并默认阻止最终发布。

#### P0-2 取消不是终止状态，仍会打包部分结果

`stop_event` 只控制插件循环和 XML 步骤；即使已停止，代码仍无条件执行组装与打包。GUI 又没有提供 stop_event 或取消入口。必须定义 `CANCELLED` 为终态，取消时禁止发布最终归档。

#### P0-3 目标语言跨 TM、插件翻译、XML 三条路径不一致

- GUI 选择 `target_lang`。
- XML 使用该参数。
- 插件 AutoTranslator 仍使用配置文件中的目标语言。
- TM 无目标语言元数据，可能套入历史中文译文。

多语言配置已是 FR15.9 的正式需求，因此这是内容正确性阻断项。

#### P0-4 TM 的 STALE 与 Stage 语义会产生错误状态

`apply_to_collection()` 对 STALE 仍写译文，且对任何成功套用都不设置 stage。它既违反 FR15.4.2 的“不直接套用”，也会留下“有译文但 stage=0”的矛盾对象，随后可能再次被 AI 处理。

#### P0-5 默认输出删除 FOMOD 必需图片

全局 strip 包含 `.png/.jpg`，默认没有 `fomod` 目录特例，违反 FR15.6.3。必须先修规则再允许打包。

#### P0-6 7z/RAR 自包含承诺未进入依赖与发行物

ADR/Changelog 声称新增 `py7zr/rarfile` 与捆绑 `unrar.exe`，但项目声明、lock、PyInstaller spec 和仓库二进制均未落地。ZIP 之外的主输入格式在干净安装包中没有可验证性。

### P1：下一迭代的主体

1. 根目录定位要向下发现唯一 FOMOD 根，并贯穿 diff、插件配对、XML、组装，而不是只在 diff 内局部调用。
2. 用统一 `TranslationCandidateResolver` 表达项目/TM/旧归档/AI 的来源、匹配类型、置信级别、STALE、冲突和 provenance。
3. 修复冲突模型与 GUI：候选组必须包含胜者、全部输家和“保留空/拒绝”，按 entry 分组；流水线必须在预览阶段处理冲突。
4. 结构化解析 FOMOD XML 的文本和属性，保留编码、声明、namespace、注释及不可翻译标记。
5. 实现真正四阶段 GUI：预检 → diff/冲突审核 → 翻译执行 → 输出预览/发布。
6. 将最终包发布改为 staging + 验证 + 原子替换；任何 fatal stage 不产生最终成品。
7. 增加项目来源选择、旧归档来源灌入/临时 overlay、TM 持久化是否发生的明确策略。

### P2：可靠性与规模优化

1. TM 建立按 `(target_locale, normalized_original)` 的合并倒排索引，避免每条词句线性扫描全部词典。
2. 仲裁不能用会随运行变化的 `hits` 作为主要稳定排序依据；定义确定性元组和最后稳定 tie-breaker。
3. `.tbdict` 增加 schema 校验、index 引用完整性校验、语言/项目身份、来源 provenance、可迁移版本。
4. 归档增加路径和资源预算策略，覆盖 ZIP/7z/RAR。
5. 增加逐阶段进度、结构化错误、失败重试和可恢复 manifest。
6. 写回后重新解析插件并核验预期译文数量、localised/inline 模式及 ESL 行为。

### P3：体验与长期维护

1. 输出摘要支持导出 JSON/Markdown，包含每插件/每阶段指标。
2. 词典面板增加 scope/语言/项目身份编辑、批量导入和诊断视图。
3. FOMOD 预设支持版本化、导入/导出和项目级复用。
4. 清理过时 MEMO、Plan 状态和 INDEX 统计，避免后续 Agent 读取错误状态。

## 6. 三种后续方案

### 方案 A：在现有实现上做阻断性补丁

做法：保持 `FomodPipeline.run()` 单体结构，修异常传播、stop 后不打包、TM context/stage、FOMOD 图片、目标语言、依赖声明，并补 E2E 测试。

优点：改动小，最快得到一个可用 ZIP/单语言版本。

缺点：来源仲裁、预览、恢复、错误报告和阶段事务仍会继续挤在一个函数中；后续加入项目来源、多语言、断点续传时很快再次失控。

适用：只作为 1 个短迭代的止血，不应作为最终架构。

### 方案 B：分阶段事务流水线 + TM V2（推荐）

将业务拆为明确阶段，每个阶段返回同一类结果，不直接发布最终文件：

```text
Preflight
  → Extract(new/old)
  → DiscoverLayout + NormalizePaths
  → Diff + PreviewManifest
  → LoadSources(project/TM/old overlay)
  → ResolveCandidates(key/text/stale/conflict)
  → TranslatePlugins(TM/AI) + VerifyWrite
  → TranslateFomodXml + VerifyXml
  → ApplyDistributionPolicy + PreviewOutput
  → PackageToStaging + ValidateArchive
  → AtomicPublish
```

统一契约示例：

```python
StageResult(
    status="ok|warning|failed|cancelled",
    metrics={},
    warnings=[],
    errors=[],
    artifacts={},
)

TranslationCandidate(
    entry_key,
    translation,
    source_kind="project|tm|old_archive|ai",
    source_id,
    matched_via="key|text|generated",
    freshness="exact|stale|unknown",
    target_locale,
    priority,
)
```

优点：

- 取消、失败、预览、重试和统计有清晰边界。
- UI、CLI、Agent 可复用同一用例层。
- 可保留现有 parser/writer/AutoTranslator/fileops，通过 adapter 渐进迁移。
- TM 冲突、Stage 和 provenance 由 resolver 统一处理，不再由各模块直接写字段。

缺点：需要新增应用服务与 V2 schema，工作量中等。

这是当前需求复杂度与代码成熟度之间最合适的方案。

### 方案 C：持久化 DAG/作业引擎 + SQLite 资产库

把每次 FOMOD 翻译建模为持久化 job DAG，阶段状态、候选、冲突、文件 manifest、断点均写 SQLite；TM 也迁到数据库，`.tbdict` 仅作为交换包。

优点：最强的恢复、并发、审计、批量处理和大规模查询能力。

缺点：引入数据库迁移、作业生命周期和更复杂的运维，不适合当前仍未建立端到端契约的阶段。

建议作为方案 B 稳定后的扩展方向，而不是现在直接采用。

## 7. 推荐的架构变更

### 7.1 ADR 处理

不要直接删除 ADR-014/015 的历史。建议：

1. **新增 ADR：FOMOD V2 分阶段事务执行模型**  
   固化 StageResult、取消终态、fatal/warning 策略、staging/atomic publish、预览 manifest、端口适配器。
2. **新增 ADR：Translation Memory V2 身份与候选仲裁**  
   固化 locale/project identity、候选 provenance、STALE 不应用、Stage 转移、确定性排序、冲突组结构、schema migration。
3. **更新 ADR-014**  
   标记旧 `FomodPipeline.run()` 编排和 TM V1 查询契约被新 ADR 部分取代；保留“一文件一 mod”“复用现有 parser/writer/AutoTranslator”的有效决策。
4. **更新 ADR-015**  
   增加 `ArchivePolicy`、`LayoutDiscovery`、资源预算和统一路径校验；明确 fileops 是端口实现，不承担业务事务。

### 7.2 模块边界

建议新增应用层，而非让 GUI 直接构造所有组件：

```text
application/fomod/
  job_spec.py
  stage_result.py
  orchestrator.py
  manifest.py
  stages/

application/translation_reuse/
  candidate.py
  resolver.py
  mutation_policy.py

ports/
  archive.py
  plugin_io.py
  tm_repository.py
  translator.py
  artifact_publisher.py
```

现有模块作为 adapters 保留：

- `fileops` → Archive/Diff/Policy adapter
- `PluginParser/PluginWriter` → PluginIO adapter
- `TranslationMemoryManager` → TM repository adapter
- `AutoTranslator` → Translation adapter
- PyQt FomodPanel → application service 的 UI adapter

### 7.3 条目写入不变量

禁止各模块直接散落地写 `entry.translation`。由统一 mutation policy 处理：

```text
EXACT key/text accepted  → translation=候选译文, stage=1, provenance=...
STALE key               → 不写 translation, review_required=true
conflict unresolved     → 不发布/保持待决，或用户明确接受后 stage=1/2
AI success              → translation=结果, stage=1, provenance=ai...
locked/hidden           → 永不修改
```

如果项目希望 TM 命中后仍需人工校对，可以将其设为 stage=2；关键是以一份明确策略替代当前“有译文但 stage=0”。

## 9. 验收与测试门禁

### 9.1 最小端到端 fixture

至少准备一组可合法提交仓库的微型 fixture：

- 新归档有一层 wrapper，旧归档没有 wrapper。
- 1 个 inline ESP、1 个 localised/ESL fixture（如真实二进制难提交，可用受控 adapter fixture 加一个发行前真实样本门禁）。
- 条目包含：EXACT、STALE、FormID 漂移但文本命中、完全新增、TM 冲突、AI 失败。
- ModuleConfig 包含 moduleName 文本、step/group/plugin `name` 属性、description、UTF-16LE BOM、namespace/注释/占位符。
- `fomod` 目录有 PNG/JPG，textures 目录有同扩展名侵权贴图。
- 一次正常发布、一次中途取消、一次 writer 失败、一次损坏归档。

### 9.2 必须满足的业务断言

1. wrapper 不同仍能配对同名插件和 XML。
2. EXACT 继承并设正确 Stage；STALE 不写译文且进入 review。
3. TM 只查询当前目标语言和允许的 project/global 范围。
4. 冲突必须在发布前解决，报告包含所有候选与最终选择。
5. AI/Writer/XML 任一 fatal 失败时不产生最终归档。
6. 取消后状态为 CANCELLED，不产生/不覆盖最终归档，临时目录按策略清理。
7. FOMOD 图片保留，textures 图片剔除；未知扩展名出现在预览并按策略处理。
8. 输出归档可再次解包；XML 可解析且保持要求的编码；插件可再次解析并核验译文数量。
9. 结果摘要精确展示 extracted、diff、inherited、stale、TM、conflict、AI、failed、pending、kept、stripped。
10. zip 与 7z 在干净安装环境通过；RAR 在捆绑 unrar 的发行物中通过。

### 9.3 安全门禁

- ZIP/7z/RAR 均拒绝绝对路径、`..`、盘符/UNC、越界符号链接。
- 可配置限制成员数、总展开大小、单文件大小和压缩比。
- 解包/打包只在专用 staging 目录工作。
- 最终输出通过同目录临时文件 + 原子替换发布。
- 不允许错误被空 `except` 吞掉；所有错误必须进入 StageResult 和最终报告。

### 9.4 性能门禁

- 为当前实现先记录基线，再给 V2 设预算。
- 至少覆盖：同名 mod 命中、跨 100 本词典文本命中、10 万总词条批量套用、冲突高发场景。
- 查询复杂度不应为“每条词句 × 全部词典线性扫描”；应通过合并索引接近按候选数增长。
- 大归档阶段提供真实字节/文件进度，取消响应时间应有明确上限。

## 12. 最终建议

### ParaTranz JSON 身份补充

TM 的主键与来源仲裁必须使用用户稳定 `key`，不能把 ParaTranz 数值 `id` 写入 TM key。ParaTranz id 只允许作为带 project/file scope 的来源证据；同一词条在平台重新生成 id 后，仍应命中同一 TM 记录。离线 ParaTranz JSON 导入与在线拉取应先转换成同一 Candidate/ChangeSet，再进入 TM 仲裁。详细合同见 [ParaTranz JSON 双 ID 兼容性调整](paratranz-json-compatibility-adjustment.md)。

FR15 不需要推倒现有底层能力。PluginParser、PluginWriter、AutoTranslator、基础 TM 模型、ZIP/fileops、migrator、UTF-16 读写都可以保留。真正需要重构的是它们之上的“执行与决策层”：

- 用 staged orchestrator 取代单体 `run()`；
- 用 candidate resolver + mutation policy 取代各模块直接写译文；
- 用 locale/project-aware TM V2 取代当前只按 mod/scope 标签的查询；
- 用 preview manifest + atomic publish 取代“边处理边修改、最后无条件打包”；
- 用真实 E2E/发行门禁取代“函数存在即完成”。

建议迭代优先级为：**P0 止血 → TM/候选契约 → 事务流水线 → XML/过滤预览 → GUI → 性能与批量化**。这条路径既能尽快避免产出错误成品，又能保留已有投资，并为后续 Agent、CLI、批量 FOMOD 和项目自动化提供稳定的应用服务边界。
