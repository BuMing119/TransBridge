# FR7 纵向需求—架构—方案—代码审查

> 审查日期：2026-08-18  
> 审查方式：独立纵向只读审查（需求 → ADR → Plan/Story → Changelog → 真实入口代码 → Tests）  
> 范围：FR7.1～FR7.17，重点为工作台、智能助手与 FR7.13 Agent 框架；同时追踪直接相关的 session-controller、session-manager、task-monitor 方案  
> 限制：未修改任何业务代码、需求、ADR 或 Plan；仅新增本审查报告

## 1. 结论先行

FR7 目前不是“整体已实现”，而是三种状态混在一起：

1. **工作台基础 UI 基本可用**：主窗口、工作台/ParaTranz 双 Tab、文件菜单中的解析/上传/下载/写回、Step2 筛选/搜索/行内编辑、自定义标签、AI 翻译窗口等都有真实入口。
2. **智能助手的聊天外壳和大量组件已存在**：流式输出、Tool/Plan 卡片、会话列表、任务监控、工具注册、护栏、Graph、观测、MCP 等均能在代码中找到相应模块。
3. **FR7.13 的“Agent 产品闭环”没有完成**：多 Agent 调度核心文件当前不存在；知识文件不能被 LLM 检索或引用其内容；长期记忆在真实 UI 中被显式禁用落盘；Graph 的暂停、条件路由和 checkpoint 恢复存在实质错误；MCP 启动入口会因未导入 `ToolRegistry` 且无 `AppContext` 而失效；工作台 UI 与 Agent 工具维护两套筛选/标签状态，助手调用成功也不能可靠反映到主表。

因此，建议把 FR7 拆成：

- **可交付**：FR7.3～7.6、7.8 的主体、7.14/7.16 的大部分视觉能力、7.17。
- **部分完成**：FR7.7、7.9、7.11、7.12、7.13.1～7.13.4、7.13.7～7.13.9、7.15。
- **当前不可宣称完成**：FR7.13.5 MCP 产品入口、FR7.13.6 多 Agent 协作，以及 FR7.13 所宣称的端到端项目隔离与完整 Agent 成功链。

### 2.1 工作台真实入口

真实启动路径为：

`ui/app.py:38 main()` → `MainWindow()` → `MainWindow._init_central()` → `WorkbenchWidget(AppContext)` / `ParaTranzWidget(AppContext)`。

这部分与 FR7.7/7.8 的方向大体一致。

### 2.2 智能助手真实入口

`MainWindow._get_assistant_panel()` → `SmartAssistantPanel` → `ChatWidget`，随后 ChatWidget 在四个延迟阶段内创建：

- `ConversationManager`
- `ToolExecutionHandler`
- `ConversationOrchestrator`
- `SessionController`
- `MemoryStore/MemoryRetriever`
- `ObservabilityCollector`
- `TaskManager` 延迟监听

用户发送消息后的当前主链为：

`ChatWidget._on_send()` → 记忆检索 → `SessionController.handle_user_message()` → `ConversationOrchestrator.start_round()` → `ChatWorker` → `on_response_parsed` → `SessionController.handle_llm_response()` → ToolCard/PlanCard 或自动执行 → `ToolExecutionHandler` / `ExecutionEngine(GraphExecutor)`。

该链路“组件齐全”，但在状态、线程、长任务与工作台同步处发生断裂，详见下文。

## 4. 关键发现与优先级

## P0 — 必须在继续宣称 FR7.13 完成前处理

### P0-1 多 Agent 核心实现当前缺失

证据：

- ADR-008 `:158-159` 明确规定 `agents/orchestrator.py` 与 `agents/agent_worker.py`。
- `plans/agent-upgrade/stories/story-07-agent-orchestration.md:215-218` 规定创建两文件并接入 ExecutionEngine/ChatWidget。
- Changelog `2026-05-10-008-Phase2全部7Story编码实现.md:17-27` 宣称二者已创建并导出。
- 当前 `src/transbridge/smart_assistant/agents/` 只有 `agent_spec.py`、`agent_registry.py`、`__init__.py`。
- 全库只有测试引用 AgentRegistry，没有实际 Orchestrator/AgentWorker 产品调用。

影响：FR7.13.6.2～7.13.6.6 的任务分解、并行、通信、汇总、隔离都不存在；“预置 7 Agent”只是一组元数据，不是运行时 Agent。

建议：需求状态立即改为“部分实现”；重新打开 agent-upgrade S07。不要继续在 ChatWidget 中直接补 if/else，应建立独立 `AgentRuntime/Coordinator`，以项目作用域、工具能力集合和 JobRuntime 为依赖。

### P0-2 Agent 注册顺序导致预置 Agent 工具集为空

`ui/app.py:45-49` 先 `AgentRegistry.init_presets()`，后 `register_all_tools()`。但 `AgentRegistry.register()` 会在注册时立即把 `namespace:*` 展开；此时 ToolRegistry 尚无工具，所以 translator/proofreader/parser/editor/paratranz/writer 的通配工具集为空。

此外，orchestrator 的显式工具名使用 `editor:get_visible_entries` 形式，而 ToolRegistry 的 `ToolSpec.name` 是非限定名，当前没有统一的 `ToolId(namespace, name)` 类型契约。

验收要求：启动后断言每个 enabled Agent 的工具集非空、每个工具均能在限定 namespace 中解析；注册顺序与模块导入顺序无关。

### P0-3 工作台与 Agent 是两套状态，工具“成功”不等于产品可见成功

`AppContext` 有 `_filter_state/_label_library/_entry_labels` 及信号；`Step2PreviewWidget` 又维护同名的三套私有状态。全库没有任何 `filter_changed.connect` 或 `label_data_changed.connect` 到 Step2。

结果：

- Agent `set_filters/manage_entry_labels` 修改 AppContext；
- 主表读取 Step2 私有状态；
- AITranslatorWindow也直接读取 Step2 私有字段；
- Agent 工具返回成功，但用户主表可能无任何变化；
- UI 标签变化也不会同步给 Agent 查询；
- VariantStore 保存从 Step2 采集，但加载只 `apply_to()` 译文，没有恢复标签到 Step2 或 AppContext。

这是 FR7.9/7.11 与 FR7.13/FR9 之间最核心的纵向断层。

建议：引入唯一 `ProjectWorkspaceState`（collection/filter/labels/selection/variant），UI、Agent、MCP 只通过 command/query API 使用它；Step2 变成 presenter，不再拥有第二份业务状态。

### P0-4 文件上传没有知识注入

`ChatWidget._on_upload_file()` 能解析文件，但 `ContextBuilder:56-62` 只写入文件名、格式和字符数。全库没有“查询上传文档内容”的工具，`raw_text` 没有进入向量索引或检索上下文。

因此典型场景“上传纠错表/风格指南，Agent 翻译时引用”实际不可用。

建议：实现 per-project `KnowledgeStore`：异步解析 → 分块 → 索引 → `search_knowledge(query, filters)` 工具；LLM 只能通过检索获得小片段及来源，不直接拼接整文件。上传完成前显示 indexing 状态，失败可重试。

### P0-5 MCP 启动链不可用

`ui/app.py:60` 引用未导入的 `ToolRegistry`，启用 MCP 时会 NameError。即使补 import，server 在 MainWindow/AppContext 创建前启动，MCPAdapter ctx 为空，所有 call 返回“app_context 为 None”。`mcp_auth_token` 也没有放入 mcp_config。

建议不要把 stdio MCP 塞进 GUI 的后台线程。建立独立 `transbridge-mcp` entry point：

- composition root 完成工具和 service 注册；
- 通过明确的 `project_id/session_id` 获得 ApplicationService；
- stdio 进程由 MCP client 启动；
- GUI 若要提供服务，使用具备生命周期和认证的本地 IPC/HTTP，而不是占用 GUI stdin/stdout。

### P0-6 长任务状态机未接 `is_long_running`

SessionController 定义 AWAITING_TASK 与 `handle_task_started()`，但全库没有调用 `handle_task_started()`。ToolSpec 虽有 `is_long_running`，ToolExecutionHandler 不读取它。

实际流程是：启动翻译工具立即返回 task_id → Controller 当普通工具执行完成并继续下一轮；任务真正完成后 `ChatWidget._on_task_completed()` 调 `handle_task_completed()`，此时状态不是 AWAITING_TASK，触发 assert，回调被 TaskManager 的 safe callback 吞掉。

影响：FR7.15.2 的“异步任务完成后自动通知 LLM”不可靠，长任务可能永远无法进入正确下一轮。

验收要求：用真实 `start_translation` fake backend 做端到端状态测试，必须观察 `EXECUTING → AWAITING_TASK → THINKING/IDLE`，失败和取消同样覆盖。

## P1 — 下一迭代主线

### P1-1 记忆、会话、观测没有项目隔离

- MemoryStore：`persist_to_disk=False`，且目录为全局 data/memory。
- SessionManager：使用全局 data/sessions，虽然记录 project_name，但列表和恢复不按项目过滤。
- ObservabilityCollector：使用全局 data/observability。
- 项目切换时不重建这些对象。

这既违反 FR7.13.3/7.13.9，也可能造成 A 项目的上下文在 B 项目出现。

目标路径建议：`projects/{project_id}/{variant_id}/assistant/{sessions,memory,knowledge,observability,checkpoints}`，并由 `ProjectScope` 生命周期统一创建、切换和关闭。

### P1-2 Reflexion 在主 ReAct 链不工作

ToolExecutionHandler 使用无 LLM 的 `RetryHandler()`；`analyze_and_adjust()` 在 `_llm is None` 时直接返回 None。现在最多只是“判断可重试”，没有需求所说的 LLM 原因分析和参数调整。

应把 `RetryPolicy/ReflexionService` 作为 composition root 依赖注入 ToolHandler 和 GraphRuntime，禁止各执行器自行构造不同 RetryHandler。

### P1-3 Graph 实现与 ADR-011 语义不一致

主要问题：

1. `pause()` 设置 Event，但执行循环在 Event 已 set 时调用 `wait()`，会立即返回，暂停无效。
2. checkpoint 加载只取得 completed key，没有把结果恢复进 results，也没有从 current_node 恢复；保存时 current node 永远写 graph.entry_node。
3. ConditionNode 自己递归执行 true/false 节点；随后 BFS 又按 graph.edges 遍历，不区分条件分支，可能执行非选中分支或重复节点。
4. HumanConfirmNode 的 `timeout_seconds` 字段未被使用，执行器固定使用类级 300 秒。
5. `edge_type=conditional` 没有条件表达式字段，也没有真正条件判断。
6. `execute_graph()` 没有从 Chat/LLM 响应协议接入；真实 UI 主要只把普通 steps 转成简化 DAG。

建议把 GraphRuntime 明确为确定性状态机：`GraphState(current, completed, variables, loop_counters, status)`；节点只产出结果和 route，不递归执行下游；scheduler 统一选择 next frontier；checkpoint 保存完整 state 并用 schema version 恢复。

### P1-4 HITL 主线程桥接存在死锁风险

ChatWidget 在 ThreadPoolExecutor 回调中使用静态 `QTimer.singleShot(0, _on_main)`，随后 `threading.Event.wait()`。没有 receiver 的 singleShot 可能投递到调用线程，而该线程没有 Qt event loop，导致确认对话框永不出现且 worker 永久等待。

应使用专门 QObject signal 或 `QMetaObject.invokeMethod` 投递到 GUI thread；后端 Runtime 只发 `DecisionRequested` 事件并异步等待 Future，不直接知道 QMessageBox。

### P1-5 任务暂停语义是“按钮状态”，不总是真暂停

TaskManager pause 只 clear pause_event 并改 status。postprocess 会消费 pause_event，但 translation 的主执行仅传 stop_event，没有消费 TaskHandle.pause_event。任务监控对所有 running 任务都显示暂停，用户会看到 paused，但翻译仍可能继续。

建议 ToolSpec 声明 `capabilities={cancel,pause,resume}`，UI 只显示任务真正支持的操作；所有长任务统一接受 CancellationToken/PauseToken。

### P1-6 工作台标签持久化和导航有可复现缺陷

- VariantStore.load 能加载 labels/label_library，但 `apply_to()` 只恢复 translation。
- `_switch_to_variant()` 没有把标签注回 Step2/AppContext。
- `locate_entry()` 使用不存在的 `_search_original/_search_translation`，实际字段为 `_search_orig/_search_trans`。
- 标签/筛选修改未统一触发 `ctx.mark_dirty()`。

建议纳入统一 WorkspaceState Story，一次性修复，而不是再做字段级补丁。

## P2 — 结构与体验优化

### P2-1 ChatWidget 仍是 God Object

llm-chat Story-09 目标把 ChatWidget 精简到约 400 行；session-controller Story-02 目标约 600 行。当前实际为 1239 行，仍承担 UI 构建、流式、记忆、观测、上传、Engine、HITL、TaskManager、会话保存/命名等职责。

建议拆分为：

- `ChatPresenter/ViewModel`：将 runtime events 转成 view state；
- `ChatView`：纯控件和渲染；
- `AssistantSessionService`：会话/轮次状态；
- `KnowledgeUploadController`；
- `TaskMonitorPresenter`；
- `DecisionDialogAdapter`。

### P2-2 MainWindow 仍是 God Object

`ui/main_window.py` 约 1522 行，解析、迁移、项目、版本、菜单、窗口、持久化、任务创建混合。FR7 后续迭代会继续把所有功能堆进 MainWindow。

应按 use case 提取 `ProjectController`、`ParseController`、`VariantController`、`OperationController`，MainWindow 只组合 action 和 presenter。

### P2-3 筛选标签计数不满足动态交集

`_build_category_tags()` 和 `_build_stage_tags()` 都直接遍历全部 `_entries`，没有先应用其他维度，因此 FR7.9.1 所要求的“随其他标签选中状态联动更新交集数量”没有实现。

## 6. 三种优化路线与取舍

### 方案 A：在现有 callback 架构上局部补丁

做法：补 ToolRegistry import/注册顺序、桥接 Step2/AppContext、修 Graph pause/checkpoint、恢复标签、补 AgentWorker/Orchestrator 文件。

优点：改动小、短期快。  
缺点：ChatWidget/MainWindow/全局单例继续膨胀；GUI、Agent、MCP 三入口仍会不断分叉；下一轮很可能再次出现“单元组件都在、产品链不通”。  
适用：只为短期发布止血，不适合作为 2～3 个迭代后的目标架构。

### 方案 B：统一 Application Service + ProjectScope（推荐）

做法：保留 PyQt UI、现有 parser/writer/translator 实现和大部分工具定义；新增统一应用层：

```text
GUI Adapter ─┐
Agent Tool ──┼─> Application Services ─> ProjectWorkspaceState / Domain
MCP Adapter ─┘            │
                          ├─ JobRuntime + EventStream
                          ├─ AgentRuntime + GraphRuntime
                          └─ Project-scoped Persistence
```

所有入口调用同一个 command/query；UI 订阅事件更新，不维护第二份业务状态。ProjectScope 统一 memory/session/knowledge/observability/checkpoint 生命周期。

优点：最大程度复用现有代码，同时根治双轨状态、入口分叉和项目隔离问题；适合渐进迁移。  
缺点：需要新增一层接口和契约测试，前两个 Story 的用户可见功能不多。  
适用：当前项目最平衡、风险最低的迭代方案。

### 方案 C：完整 Actor/Event-Sourced Agent Runtime 重写

做法：所有会话、任务、工具、Graph、项目切换都建模为 actor/event log，GUI 只是投影。

优点：多 Agent、恢复、观测、审计非常统一。  
缺点：对当前桌面应用过重，迁移成本高，容易在业务价值验证前陷入基础设施重写。  
适用：未来确实要做远程多用户/分布式 Agent 时再评估；当前不推荐。

## 7. 推荐目标架构

### 7.1 核心对象

- `ProjectScope(project_id, variant_id)`：所有项目级服务与生命周期容器。
- `ProjectWorkspaceState`：collection、filter、facets、labels、selection、dirty/version 的唯一真相源。
- `WorkbenchService`：parse/import/migrate/filter/edit/label/write command/query。
- `AssistantSessionService`：会话状态机与 LLM round，不依赖 QWidget。
- `KnowledgeService`：上传、解析、分块、索引、检索、来源追踪。
- `MemoryService`：偏好/术语决策/纠错历史，按项目持久化。
- `AgentRuntime`：AgentSpec 解析、实例创建、任务分解、能力授权、结果汇总。
- `GraphRuntime`：确定性状态机与 checkpoint；只发布 RuntimeEvent。
- `JobRuntime`：长任务的 cancel/pause/progress/result；Qt adapter 转 signal。
- `ObservabilitySink`：统一接收 LLM、tool、guard、job、graph 事件。
- `MCPApplicationAdapter`：只面向 Application Service，不持有 MainWindow/AppContext。

### 7.2 关键契约

- `ToolId(namespace, name)`，禁止混用 `editor:foo` 字符串和裸 `foo`。
- `CommandResult(data, warnings, error, events)`，GUI/Agent/MCP 共用。
- `CapabilitySet(read/write/admin + allowed_paths + project_id)`，替代“拒绝所有绝对路径”。
- `RuntimeEvent`：RoundStarted、DecisionRequested、ToolStarted、ToolFinished、JobStarted、JobFinished、StateChanged。
- `CancellationToken/PauseToken`：只有实际消费 token 的 job 才声明支持 pause。

## 10. 最终判定

FR7 的主要问题不是“少几个模块”，而是**实现按组件横向铺开后，没有用同一业务状态和同一运行时把它们纵向串成产品成功链**。继续新增工具、面板或 Agent 类型只会扩大双轨实现。

最值得做的下一步不是大规模重写，也不是逐个补 if，而是采用方案 B：

> 先建立 ProjectScope + Application Service + 唯一 WorkspaceState，把 GUI、Agent、MCP 统一到同一命令/查询和事件流；随后修复 AgentRuntime/GraphRuntime，再做项目知识与 UI 瘦身。

在以下 5 个门禁通过前，不建议把 FR7.13 标为“全部完成”：

1. 真实多 Agent 分解/并行/失败隔离/汇总 E2E；
2. 上传文件正文可被检索并带来源用于回答；
3. Agent 修改筛选/标签后主表立即可见且重启不丢；
4. Graph pause/resume/checkpoint/HITL 语义测试通过；
5. MCP enabled 在 Windows composition root 下启动并成功调用一个 project-scoped read tool。
