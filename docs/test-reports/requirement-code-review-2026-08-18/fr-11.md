# FR11 工具提示词分层加载机制：需求—架构—Plan—Story—代码纵向审查

> 审查日期：2026-08-18  
> 审查方式：独立纵向审查，不读取其他 Agent 结论  
> 审查范围：`requirements.md` FR11 → ADR-005/008/009/012 → `plans/tool-prompt-layering/` 全部 Story → changelog / 历史 QA → ToolRegistry / 工具描述 / Prompt 组装 / Agent 注册与实际执行链 → tests

## 1. 结论摘要

FR11 的基础设施代码已经存在，但**不能判定为需求验收通过**。建议把当前状态从“已实现”调整为：

> **主体已编码，但核心运行态验收失败；存在 P0 阻断，需先修复后再继续架构升级。**

核心判断如下：

1. `ToolSpec.summary`、工具目录、`build_tool_help()`、`get_tool_help`、路由表和两个预加载工具均已落地，28 个 FR11 单元测试全部通过。
2. 真实执行链中，`get_tool_help(namespace=...)` 的完整帮助会被 `ToolResult.to_observation()` 的通用大数据摘要逻辑截断。实测 editor namespace 原始帮助为 **4,180 字符**，传给下一轮 LLM 的 observation 仅 **150 字符**，其中 help 正文约保留前 **100 字符**，参数表完全消失。这直接破坏 FR11 的核心机制。
3. 仓库已有 LLM 回归结果 `tests/smart_assistant/test_data/result.json`：15 条仅 2 条命中，工具选择准确率 **13%**。历史 QA 报告只摘录“跳过率 0%”并宣布通过，没有披露 13% 的核心失败指标。
4. 回归脚本虽构建了 old/full prompt，却只运行 new/directory prompt，未实际完成“full schema vs directory”A/B 对比；只跑 15 条、仅覆盖 default/editor，未满足 50+ prompts、7 namespace、所有工具和跨领域任务验收。
5. 当前运行态已有 **49 个活跃工具、8 个 namespace**；FR11 路由表仍固定为 7 个 namespace，新增 `archive` namespace 出现在目录中但没有路由入口。
6. 应用启动顺序先初始化 Agent、后注册工具；`namespace:*` 在空 ToolRegistry 上被一次性展开，导致 translator/parser/editor/paratranz/writer 预置 Agent 的工具列表保持为空。实测启动顺序等价快照：translator=0、parser=0、editor=0、paratranz=0、writer=0。
7. 工具 Schema、描述和真实能力之间已有漂移：例如 `write_back` 描述和实现支持 `output_dir`，但 parameters schema 未声明；`migrate_entries` 被目录宣称为可用能力，实际始终返回 `NOT_AVAILABLE`；parser namespace 的多个工具描述可见但分派实现当前不可用。

因此，FR11 现在的问题不是继续压缩 100—200 tokens，而是**发现协议、工具契约、Agent 可见性和真实能力没有形成一个可验证的闭环**。

## 5. 发现项（P0—P3）

## P0-01：完整工具帮助在真实执行链中被截成约 100 字符

证据链：

1. `tool_default.py:165-171` 把完整帮助放在 `ToolResult.data["help"]`。
2. `tool_execution_handler.py:250` 调用 `tr.to_observation(tool_name)`。
3. `tools/types.py:40` 默认总预算 2,000 字符；第 58 行只给 data 60% 预算。
4. 当完整 JSON 超预算，`tools/types.py:115-120` 会把长字符串值截到 100 字符。
5. `conversation_manager.py:17` 又将 observation 总上限固定为 2,000 字符。

运行态实测：

- `build_tool_help(namespace="editor")`：4,180 字符。
- 转为 observation：150 字符。
- 参数表：丢失。
- namespace 内除最前端描述片段外的工具定义：丢失。

影响：

- LLM 不能获得“完整 Schema”，FR11 的按需加载协议在真实应用中失效。
- LLM 会重复调用 get_tool_help、猜参数或停在发现阶段。
- 工具越多、namespace 越大，问题越严重。

即时修复建议：

- 为 `ToolResult` 增加明确的 `observation_content` / `content_kind="tool_schema"`，禁止通用 data 摘要器改写 schema。
- `get_tool_help` 不应把帮助塞进普通 `data` 字段；应返回专用结果类型或专用 observation。
- namespace 帮助若超模型预算，应按工具分页/游标返回，而不是静默截断。
- 为真实链路增加端到端测试，断言最后一个工具和完整 required parameters 仍出现在下一轮 messages 中。

## P0-02：LLM 回归真实准确率为 13%，却被历史 QA 判为通过

仓库证据：

- `tests/.../result.json:3-5`：total=15、correct=2、accuracy=13%。
- `tool-prompt-layering-qa-2026-05-25.md:103-108` 只报告跳过率 0%，并称机制“工作正常”。
- `tool-prompt-layering-qa-2026-08-05.md:68` 又称行为数据缺失，`第82行`仍宣布全部验收合格。

影响：

- 核心业务指标“工具选择准确率不降”没有通过。
- QA 结论和原始数据冲突，后续团队可能在错误基线之上继续调优。

整改建议：

- FR11 状态回退到“验收失败/整改中”。
- 历史报告保持 append-only，但新增纠偏报告，不覆盖原始证据。
- CI/发布门禁读取机器可读 eval 结果，准确率不达标直接失败，不能靠人工摘要选择性通过。

## P0-03：应用启动顺序使大部分预置 Agent 工具列表为空

证据：

- `ui/app.py:46` 先 `AgentRegistry.init_presets()`。
- `ui/app.py:49` 才 `register_all_tools()`。
- `agent_registry.py:24-31` 在 Agent 注册时一次性把 `namespace:*` 展开为当时 ToolRegistry 中的工具。
- 注册表为空时 wildcard 展开得到空列表，后续工具注册不会回填 AgentSpec。

实测启动等价快照：

- tools 注册前：translator=0、parser=0、editor=0、paratranz=0、writer=0；proofreader=2、orchestrator=7 只是因为保留了显式字符串。
- tools 注册后，已有 AgentSpec 不会自动更新，以上数量仍为 0。

影响：

- namespace 和 Agent 可见性契约失效。
- FR11 即使正确生成目录，也无法保证 Agent 真正被授权相应工具。

修复建议：

- 最小修复：先注册工具，再初始化 Agent。
- 正式方案：AgentSpec 保留 `CapabilitySelector(namespace="translator", include="*")`，不要在注册时静态展开；每次执行/构建 Prompt 时动态解析，并缓存版本号。

`archive` 已进入目录，但路由表和 Agent 预置没有它；token 报告仍记录 42 / 7。

## P1-02：Story 04 并未完成需求要求的 A/B 行为回归

证据：

- `run_llm_regression.py:124` 构建 old prompt。
- 实际执行在第 151 行只调用 `call_llm_two_rounds(new_prompt, ...)`。
- `call_llm()` 和 old prompt 从未参与评分。
- 第 134 行只取前 15 条且排除 cross。
- 15 条仅覆盖 default/editor，而非 7 namespace。
- 数据集恰好 50 条，不满足“50+”。

建议：建立可复现的离线/在线 eval harness，输出每个 provider/model 的 A/B 指标、置信区间和失败样本。

## P1-03：Schema、描述和实际能力并非单一事实源

代表性证据：

- `write_back` 描述和实现支持 `output_dir`（`tool_writer.py:124,156`），parameters schema 没有该字段（`141-147`）。
- `migrate_entries` 目录/帮助将其描述为可执行迁移工具，但实现固定返回 `NOT_AVAILABLE`。
- parser 工具的“可用能力”与实际分派实现不一致；相关 parser 类/方法映射当前不能完成真实解析。
- 自定义 schema 类型使用 `str/int/list`，不是标准 JSON Schema 的 `string/integer/array`；MCP/provider 适配必须重复转换，容易漂移。
- `_format_tool_schema()` 不展示统一的 permission/effect/idempotency/cancellation/output schema；只在 `require_confirmation=True` 时增加提示。

影响：LLM 即使拿到完整 help，也可能调用不存在、不可用或参数不完整的能力。

建议：引入 canonical `ToolContract`，执行校验、Prompt 文本、MCP Schema、provider-native tools 和文档都由它生成。

## P1-04：工具发现协议没有显式的“已加载能力状态”

当前 get_tool_help 结果只是普通 user observation：

- 没有 `LoadedCapabilityState`。
- 没有 namespace/version/tool-set 哈希。
- 没有防止重复加载。
- 对话裁剪后没有恢复已加载 namespace 摘要。
- 跨领域顺序完全交给 LLM 记忆文本规则。

这正对应 FR11 风险表中“schema 压缩时丢失”的缓解项，但代码没有实现该缓解。

建议：会话状态显式记录 `loaded_namespaces: {name: registry_version}`，每轮 Prompt 由 assembler 决定需要补入或刷新哪些 schema。

## P1-05：安全提示不足以承担工具执行策略

当前 49 工具中：read 22、write 26、admin 1；大量 write 工具未声明 `require_confirmation`。`_format_tool_schema()` 只展示长运行/显式确认，不展示统一权限和副作用等级。

建议在 canonical contract 中增加：

- `effect`: none / context_mutation / file_read / file_write / network_read / network_write
- `permission`
- `confirmation_policy`
- `idempotent`
- `long_running`
- `cancellable`
- `path_policy`
- `output_schema`
- `availability(ctx)`

Prompt 只负责告诉模型，真正安全性继续由执行层 guardrails 强制，不依赖提示词。

## P2-01：Plan / Story 状态与实际不一致

- Plan 顶部写“全部完成”。
- Story 02—04 的验收项在 Plan 中仍是 `[ ]`。
- 五个 Story 文件头均为“已确认”，不是“已完成”。
- Story 05 前置条件称 Story 04 已完成并提供准确率/跳过率/参数填充率，实际没有。

建议：不篡改历史记录；新增纠偏 changelog，Plan 标记“主体编码完成、验收失败、S06+整改中”。

## P2-02：token 目标和测量对象已漂移

- FR11 需求仍写约 1,040 tokens / 节省 92.5%。
- 历史实测约 3,435 / 节省 62.6%。
- 现在又新增 7 个工具和 1 个 namespace，历史结果已不是当前基线。
- `scripts/measure_tokens.py` 仍手工导入七个工具模块，遗漏 archive/migrator，无法准确测当前注册表。

建议：测量脚本调用唯一 composition root 的 `register_all()`，生成带 registry fingerprint 的报告，并在 CI 中对总量/每 namespace 设预算。

## P2-03：namespace 参数是死接口

`build_system_prompt(context, namespace=None)` 保留 namespace，但实现完全忽略。对于专职 Agent，这是本来可以显著减小目录、提高准确率和落实能力隔离的入口。

建议：短期实现 namespace / capability selector 过滤；长期由 `PromptAssemblyContext` 代替裸字符串参数。

## P3-01：测试命名和断言过宽

- “截断 80”测试只断言 <=80，无法验证现行 50。
- 路由表测试只查字符串，不检查 ToolRegistry namespace 全覆盖。
- 预加载测试只查名字，不检查完整 schema。
- 没有工具注册版本、重复命名、route manifest 或 schema round-trip 快照。

## 6. 方案比较

### 方案 A：保留现有文本元工具，只修复截断和路由

做法：

- get_tool_help 使用专用 observation，不被通用摘要器截断。
- namespace 超长时分页。
- 路由表从 manifest 生成。
- 修复启动顺序。
- 补齐 A/B eval。

优点：

- 改动小，最快恢复可用。
- 不依赖所有 provider 支持 function calling。
- 可复用现有 Prompt / ToolRegistry。

缺点：

- 工具调用仍依赖模型生成 JSON 文本并由本地解析。
- 多一轮发现调用，跨领域轮次累积。
- Schema 仍以自然语言文本传输，结构完整性和参数约束较弱。

适用：P0 热修复和兼容 fallback。

### 方案 B：静态注入全部 provider-native tools

做法：把 49 个 canonical schema 一次性转换为 OpenAI/Anthropic function calling tools。

优点：

- 参数结构由 provider 协议约束。
- 不需要 get_tool_help 轮次。
- 工具调用解析比文本 JSON 更可靠。

缺点：

- token 成本重新升高。
- 每个 Agent 会看到过多无权/无关工具。
- 工具数继续增长后选择准确率可能下降。

适用：工具少或上下文窗口非常充裕的模型；不推荐作为默认长期方案。

### 方案 C：动态能力解析 + provider-native tool binding（推荐）

流程：

1. `ToolCatalog` 持有 canonical ToolContract 和 namespace manifest。
2. `CapabilityResolver` 根据 Agent selector、用户意图、当前 AppContext availability 选出 1—2 个 namespace。
3. `PromptAssembler` 只注入小型目录/路由提示；provider adapter 将已选工具以原生 schema 绑定到当前 LLM 请求。
4. 会话记录 `LoadedCapabilityState`，跨轮复用并在 registry version 变化时刷新。
5. 不支持 function calling 的 provider 回退到方案 A 的专用 help observation。

优点：

- 兼得较低 token、结构化参数、能力隔离和跨 provider 兼容。
- 路由、Agent 可见性、MCP 和 Prompt 都基于同一 canonical schema。
- 可以基于当前上下文隐藏不可用工具，避免宣传假能力。

缺点：

- 需要新增 provider adapter、能力状态和 eval 基础设施。
- 迁移涉及 ConversationOrchestrator / LLM client 请求模型。

适用：TransBridge 当前已进入 49 工具、8 namespace、多 Agent、多入口阶段，最符合后续迭代方向。

### 方案 D：纯代码规则路由，不让 LLM参与发现

优点：快、便宜、确定性强。

缺点：自然语言歧义、跨领域和新工具扩展维护成本高；难覆盖所有表达。

建议：作为方案 C 的一级候选生成器，而不是唯一决策器。规则高置信度直接路由，低置信度再由小模型/主模型选择。

## 7. 推荐目标架构

建议新增 ADR-016：**Agent Capability Catalog 与动态工具绑定**。

核心组件：

```text
Tool implementations
        │
        ▼
Canonical ToolContract ───────────────┐
        │                              │
        ├─ ToolCatalog / namespace manifest
        ├─ Runtime argument validator
        ├─ Prompt help renderer
        ├─ MCP schema adapter
        └─ Provider tool schema adapter
                                       │
User intent + Agent selector + AppContext availability
        │                              │
        ▼                              │
CapabilityResolver ──► LoadedCapabilityState
        │                              │
        ▼                              ▼
PromptAssembler + provider-native tools
        │
        ▼
LLM tool call ──► Guardrails ──► Tool executor
```

### Canonical ToolContract 建议字段

```python
@dataclass(frozen=True)
class ToolContract:
    name: str
    namespace: str
    summary: str
    description: str
    input_schema: dict          # 标准 JSON Schema
    output_schema: dict | None
    permission: Permission
    effect: ToolEffect
    confirmation_policy: ConfirmationPolicy
    idempotent: bool
    long_running: bool
    cancellable: bool
    tags: frozenset[str]
    route_terms: tuple[str, ...]
    available_when: Callable[[ExecutionContext], Availability]
    execute: Callable
```

约束：

- description 不再承担参数事实源职责。
- Prompt 表格、MCP inputSchema、provider tools、运行时校验和文档都从 input_schema 生成。
- `available_when` 为不可用工具提供结构化原因；目录可隐藏或标记 unavailable。
- registry 有单调递增 version/fingerprint，Agent selector 和 session state 依据版本解析。

## 8. ADR 修改建议

### 新增 ADR-016

主题：Capability Catalog、动态 selector、provider-native tool binding、fallback text help、session-loaded capability state。

必须明确：

- canonical schema 的唯一事实源。
- namespace manifest 的所有者。
- Agent 权限采用动态 selector，不静态展开。
- Prompt/MCP/provider adapter 的依赖方向。
- 工具可用性和执行权限的边界。
- 兼容不支持 function calling 的模型。

### 更新 ADR-005

- 保留 TOML + 自建 PromptBuilder 决策。
- 补充：结构化工具调用由 provider adapter 处理，不等于引入 LangChain。
- Prompt 文本和 tool schema 分开管理。

### 更新 ADR-008

- ToolRegistry 不再同时承担注册、帮助渲染、路由目录和 provider schema 的全部职责。
- 明确 ToolCatalog / renderer / resolver / adapter 分层。
- composition root 的注册顺序固定为：实现注册 → catalog freeze → Agent 注册 → UI/MCP 启动。

### 更新 ADR-009

- AgentSpec 的 `tools` 从注册时展开列表改为动态 `CapabilitySelector`。
- 定义 Agent namespace、跨 namespace allow-list 和 registry version 刷新策略。

### 更新 ADR-012

- MCP 与 LLM provider 都从 canonical ToolContract 转换 schema。
- permission/effect/confirmation 不由 Prompt 保证，执行层强制。

## 10. 验收标准建议

### P0 修复验收

1. `get_tool_help(namespace="editor")` 经完整执行链进入下一轮 messages 后，至少包含 namespace 内每个工具名、每个 required 参数和最后一个工具的 Schema。
2. 不允许无提示静默截断；超预算必须返回分页信息或明确错误。
3. 按 app.py 实际启动顺序，7/8 个预置 Agent 的动态 selector 均能解析出非空授权工具；工具新增后不需重建 AgentSpec。
4. route manifest namespace 集合与 ToolCatalog namespace 集合完全一致。

### 行为验收

1. 数据集数量 `>= 60`，且每个活跃工具至少 2 个正例；关键写工具至少 3 个正例 + 2 个拒绝/确认例。
2. 7/8 namespace 全覆盖，跨领域任务不少于 10 条。
3. full schema vs layered/dynamic 使用相同模型、相同温度、相同样本、至少 3 次重复。
4. 最终工具准确率不得低于 full baseline 2 个百分点，且绝对准确率建议 `>= 90%`。
5. required 参数准确率 `>= 95%`。
6. get_tool_help 重复调用率 `< 5%`；非预加载直接猜参数率 `< 5%`。
7. 所有 write/admin 工具必须通过执行层权限测试；Prompt 是否提示不影响安全门禁。

### Token/性能验收

1. 报告基于当前 registry fingerprint。
2. 基础 system prompt、目录、每 namespace schema、每 provider schema 分别计量。
3. 动态方案首轮输入 token 相比 full baseline 至少节省 50%。
4. 统计额外发现轮次带来的 latency/cost，不能只统计首轮 prompt。

## 13. 最终建议

优先顺序：

1. **先处理 P0-01、P0-02、P0-03，不要继续以当前 FR11 为已验收基线。**
2. 用方案 A 完成一个最小可靠热修复，恢复真实按需帮助链。
3. 随即启动方案 C：canonical ToolContract + CapabilityResolver + 动态 provider-native tool binding。
4. 由同一 registry manifest 生成目录、路由、Agent 权限、MCP/provider schema、测试矩阵和 token 报告。
5. 将 Story 04 的行为 Eval 变为机器门禁，避免再次出现原始准确率 13% 但 QA 结论仍为通过的情况。

FR11 的设计方向“不要一次性塞入所有工具”是正确的；真正需要迭代的是：从“Prompt 中约定模型先查帮助”升级为“运行时管理可见能力，并用同一契约驱动发现、绑定、校验和执行”。
