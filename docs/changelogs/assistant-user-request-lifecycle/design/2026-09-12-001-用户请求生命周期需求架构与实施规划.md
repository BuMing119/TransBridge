## 背景与用户选择

长会话中的目标可能跨越多次回答、确认和后台任务；新消息还可能同时追问、补充约束、取消旧目标或提出新问题。原有前台轮次状态与最近 20 轮消息不足以表达目标归属、完成证据和恢复位置，因此设计独立的用户请求层。

用户已明确选择：旧请求后台任务完成时先记录结果，当前新问题回答结束后继续推进旧请求，需要确认时等待用户。换题本身不等于取消；生命周期快照记录恢复阶段和引用，不表示翻译项目内容快照，也不承诺回滚已发生的业务副作用。

本记录合并归档此前的设计初稿及补充复核，不将设计接口表述为已实现能力。

### 新增：`docs/adr/040-assistant-user-request-lifecycle.md`

- 决策 1～2：区分 Session、UserRequest、RequestItem、Turn、ExecutionAttempt 和 JobRef；分离请求修订、存储修订和执行身份，定义状态迁移、终态收敛及完成证据。
- 决策 3：输入先可靠接纳，再通过独立控制协议路由；支持同句多操作、逐指令消费、重试去重与纠正。拟新增 `submit_request_routing` 和 `report_answer_coverage`，控制解析与业务执行分离；截断或被中断的回答不能完成验收项。
- 决策 4～5：一个有效前台轮次管理多个请求，新输入优先、旧请求随后继续；按请求项就绪状态调度，确认绑定操作和版本，后台结果写回原请求。补充多窗口 TurnLease、跨会话资源协调、主动停止与技术中断的区别。
- 决策 6：副作用接纳、任务关联保存、执行激活和正式提交分阶段核验；父计划与叶子副作用使用不同身份，未知结果先核对，不自动重放。
- 决策 7：完整 Transcript、模型上下文和派生摘要分离；消息、工具定义和输出预留联合预算，大结果以可回查引用保存，保留原生工具协议完整性。
- 决策 8～9：复用 JSON repository，以原子 Session manifest 和不可变附件保存状态；提出共享条件保存、schema 3→4 迁移、恢复核对、旧任务兼容及关闭/删除规则。生命周期恢复继续调用业务 recovery/checkpoint 能力。
- 明确应用、模型适配、持久化和 UI 边界，记录备选方案、风险与待定项；未修改已有已接受 ADR。
