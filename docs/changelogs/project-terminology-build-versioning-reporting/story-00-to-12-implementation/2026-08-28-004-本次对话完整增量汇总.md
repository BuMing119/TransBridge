## 对话级最终结果

本次对话从“建立项目级术语库”推进到完整的生产能力：以当前 Project 登记来源和 Variant 为权威输入，构建可追溯术语候选，处理不同译法和人工决定，保存草稿，发布不可变版本，提供历史比较、恢复、质量报告与更新日志，并让已发布术语进入后续翻译、向量检索、校对、润色和质量检查链路。

用户随后基于实际运行截图指出：把内部构建、检查、调整、发布、历史和报告直接表现为编号步骤，不符合现代桌面软件的任务逻辑。对话据此把交互模型从“六步流程向导”改为“概览 / 术语 / 版本 / 报告”四个稳定业务对象页面，隐藏底层环节，并保留用户认可的浅色、克制、卡片化视觉语言。第一次现代化实现仍使用左侧竖向导航，与横版参考稿明显不一致；在用户反馈后，该版本被继续返工为顶部项目上下文加横向导航的最终结构。

最后，实际页面暴露出“创建术语库暂不可用”：安装版把发布候选的性能、迁移、稳定性证据当成了用户运行时门禁，未执行检查会产生一长串 `not-run` 并禁用按钮。对话确认这些检查只应服务 CI 和发行决策，因此移除了这条运行时阻塞，并审计了其他 disabled/default-off 分支。正式性能证据仍可判定发布候选不合格，但不会再阻止本地用户创建、更新、调整、发布、比较、恢复或导出术语库。

## 对话中的需求与设计决策

1. **隐藏内部流程**：构建、归并、冲突检查、草稿和发布仍由后台阶段执行，但不作为长期导航，也不要求用户按编号理解实现原理。
2. **保持横版**：术语工作台面向桌面宽屏；拒绝左侧竖栏和纵向长页面方案，采用顶部品牌/项目区、横向四区导航和单一主内容区。
3. **明确主动作**：尚无已发布版本时显示“创建术语库”，已有版本时显示“更新术语库”；按钮位于当前页面可见的主操作区域，而不是藏在某个流程步骤中。
4. **按业务对象归位**：不同译法和人工调整属于“术语”，当前版本、发布、比较和恢复属于“版本”，质量报告和更新日志属于“报告”，项目状态、数量和需要关注事项属于“概览”。
5. **真实数据优先**：参考图只定义结构、层级和交互，不把 Skyrim、4,826 条、v8 等示例内容硬编码进产品；空状态和禁用原因由实际 Project、Variant、来源、草稿与版本资产决定。
6. **发布验证不支配产品运行**：release evidence、benchmark、迁移演练和 crash recovery 结果仅用于 CI/发行验收；运行时只允许真实业务前置条件阻止操作。
7. **保留必要保护**：部分构建禁止发布、草稿陈旧、冲突未解决、提交修订不匹配、仓储只读/损坏和缺少已发布版本等保护继续生效。

## 返工与问题闭环

- 初始六步界面能表达实现流程，但信息架构以系统为中心、空白区过大、内部状态泄露、主动作不明确，被用户判定不符合现代软件使用逻辑。
- 第一轮重设计引入左侧“概览 / 术语 / 版本 / 报告”竖向导航，只解决了流程命名，没有满足用户明确要求的横版，也与四张参考图的顶部上下文和横向导航差异明显；该实现被后续横向结构取代。
- 最终横版实现按参考图复现信息层级和交互关系，同时继续使用真实 Qt 控件和生产 service，不复制参考图中的演示数据。
- “创建术语库暂不可用”并非项目缺少来源，而是 release-candidate evidence 的 `not-run` 被错误接入运行时能力判断。该耦合已从 UI service、presenter、commands、runner、composition、publisher 和 effective adapter 全链移除。
- 同类扫描确认生产路径中不再存在“发布测试未跑/未通过就禁用用户功能”；留下的不可用状态均对应实际产品条件或用户主动关闭的可选能力。
