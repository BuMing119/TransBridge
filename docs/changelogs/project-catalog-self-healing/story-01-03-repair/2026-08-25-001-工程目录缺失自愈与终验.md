# 工程目录缺失自愈与终验

- **日期**：2026-08-25
- **归属**：`project-catalog-self-healing`
- **Stories**：S01～S03
- **类型**：持久化兼容、自愈与故障防护
- **需求/决策**：FR19.8、ADR-024

## 问题

`project-catalog.json` 是本地工程的派生目录索引。用户误删该文件后，canonical V2 Project 本体仍然存在，但开始中心只能通过活动工程兜底恢复一个条目，其他合法工程会被隐藏。已有损坏 catalog 又不能直接用扫描结果覆盖，否则可能破坏现场或把未来格式降级。

## 真实变更

- 新增严格的 schema-1 catalog 文档合同，统一修复、目录查询和工程创建事务对名称、`name_key`、Project ID 与重复名称的验证。
- 文件系统端口新增稳定、非递归的直接文件枚举；候选路径仍经 canonical root 边界校验。
- 从 lifecycle 抽出共享 `AtomicDocumentStore`，保留 staging、字节复读、原子 replace 与尽力清理；清理故障不会覆盖原始发布异常。
- 新增 `ProjectCatalogRepairService`：只在 catalog 整体缺失时扫描 `projects/*.json`，严格验证当前 V2 Project、canonical 路径与显示名称，稳定生成并复读 schema-1 catalog。
- catalog 合法存在时不扫描；存在但损坏或未来版本时保留原字节并报告阻塞；普通坏候选只跳过，合法候选名称冲突则阻止整次发布。
- 启动组合在首次暴露 query/lifecycle 前执行一次修复，仅向 runtime 暴露不可变 repair report，不暴露可重复调用的修复服务。
- lifecycle 后续新建工程复用同一严格 catalog 合同，因此不会把修复器已判定为损坏的目录悄悄覆盖。
- 失败报告包含可重试诊断；目录越界、枚举、stage read/write、replace、复读验证等故障均不修改 Project、Variant 或 active pointer。

## 用户可见结果

- 误删 `project-catalog.json` 后，重新启动 TransBridge 即可自动恢复全部安全可识别的本地工程。
- 本机真实忽略目录已重新生成 catalog，恢复“蕾米尔”“艺术馆”两个工程索引；工程本体和活动指针未改动。
- 若 catalog 文件仍在但内容损坏，程序不会擅自覆盖，仍保留现场并输出诊断。
- 全新安装或没有合法 Project 时不会创建无意义的空 catalog。

## 兼容性与边界

- catalog schema 未升级，旧版本代码仍可读取自动生成的 schema-1 文件，无需数据迁移。
- 自动修复只处理“catalog 文件完全缺失”；对存在但不完整的合法 catalog 不做隐式全量重扫。
- 当前仍采用单进程桌面写入假设，不提供多个进程同时 provisioning/repair 的强一致性保证。
- 未执行 Git commit 或 push。
