# ADR-050：应用层预检与可选来源参考路径

- 状态：提议；桌面与 AI 助手范围已本地实现、相关验证及清理完成，验证边界见计划与增量 003。
- 日期：2026-10-28；最终更新：2026-10-29
- 对应需求：FR8.3、FR8.4、FR19.10、FR26.8、FR29.5。
- 计划：[application-preflight](../../plans/application-preflight/plan.md)。
- 局部取代：[ADR-038](038-rebuildable-history-search-projection.md) 的外部来源实时解析前提，以及 [ADR-049](049-task-result-lifecycle.md) 中缺引用时自动解析外部路径、按路径重定位成果的约束；其余内容身份、原子提交及成果完整性契约保持。

## 背景与约束

工程已持久保存解析成果与原始输入闭包，但部分模型、归档、UI slot 绑定、历史搜索、术语和 AI 启动仍把原始路径当作身份或读取已保存内容的条件。`ui/operations/mappers.py` 也拥有输入、输出、覆盖、备份与条目状态检查，使展示层承载业务判断。

S01～S04 搬迁或委托已有检查，未新增校验规则。后续用户明确要求补齐按需输入交互：来源内容缺失不再导致整个工程只读，已有译文可正常打开、编辑和保存，只有实际需要缺失内容的操作请求文件。此修订取代首轮“缺真实内容进入整工程只读恢复”的实现边界，首轮事实仍保留于增量 001。用户主动选择新输入、实际输出目标和项目自身完整性的现有规则继续执行，不增加检查规则、索引或通用校验平台。

## 决策与关键契约

1. `application/preflight/operation.py` 按具体用例承载现有 facts、service、Kind 与结果类型，`ai.py` 承担 AI 既有预检。复用现有 `PreflightCheckState`、`OperationPreflightResult`、状态及 `repair_intent` 语义，均不依赖 Qt。UI 负责收集选择、后台调度、展示诊断和将稳定 repair intent 映射到现有动作，不根据文案或自行读文件决定可执行性。
2. 既有 diagnostic code、阻断/警告级别、检查顺序及修复动作保持，只有本 ADR 明确的来源参考语义改变。既有用例服务仍分别承担规则，不通过一个巨大 Controller 重新集中全部领域逻辑。
3. 原始来源 `location` 是可空参考。`application/preflight/sources.py` 统一存在性策略；启动、打开、导入只检查该参考是否存在，确认缺失即清空，权限等原因导致存在性未知时保留参考，不读取其内容、计算 hash、比较指纹或因此阻断。重复/空参考不影响稳定来源身份；UI slot、来源关系和持久成果使用 `source_id`、完整条目身份及成果引用。
4. 操作优先使用项目保存的原文、定位、依赖与版本状态。缺失来源内容是对应来源的输入可用性状态，不是工程只读状态。合法 Project/Variant 正常激活；无来源内容的已保存译文、Stage、标签、引用及完整 EntryKey 仍进入权威编辑/保存流程，其他有完整输入的来源继续工作。不在启动、打开或普通浏览时选择文件、解析外部参考或阻断整个工程。
5. 参考路径清空或重定位不改变成果内容身份。归档内部成员定位由包内引用和稳定来源身份决定，不依赖原始路径或原文件名推导。纯 legacy 记录不读取外部来源或 SST magic；只要工程/版本记录自身合法，其已保存译文正常打开编辑，未知原文按第 8 条展示。旧 portable 包自带的 sources 在导入边界作为明确输入解析保存成果，location 仍保留可选参考语义，不改写为内部存储路径。包内容完整性、路径穿越及实际输出的原有保护保持，不扩展规则；输出位置由用户独立选择。
6. 显式添加/更新来源继续解析用户选定的新文件并保存成果。新增来源 ID 基于已捕获内容 namespace 生成，不迁移已保存 ID；同一参考地址换成不同内容可独立加入，既有内容重复保护保留。更新旧内容仅读取保存成果，确实缺失时沿用未验证旧内容的译文保留警告，不重读参考路径。原始路径清空后再设置参考不等同于更新来源；更新原文仍走现有来源更新用例。
7. 术语构建通过当前 `BuildWorkloadRequest` 传递完整冻结输入；`ProductionState` 和运行记录只保留轻量证据，执行结束可释放完整输入，不新增长期全量缓存、不改变 fingerprint。已折叠迁移来源保留各自捕获证据，搜索只使用权威基线来源恢复原文。动态词库界面入口复用既有 `source_terminology_path` 合同。
8. 缺少原文不等于原文为空。展示可用占位提示，但不得把提示或猜测文本写成业务原文。`EntryKey.original` 若实际保存则可显示其真实值；若未保存，保持未知。不得用译文、local_key、文件名或任意空字符串构造“已验证” SourceBaseline、SourceSnapshot、指纹或可供 AI/输出使用的来源成果。加载与保存须保留缺基线 namespace 的实际已存条目，不把它们当成已删来源丢弃。
9. 实际操作缺少必需原文/模板/依赖时，application 返回指向原 Project/Variant/source_id 的补输入意图；UI 展示所需来源及原因并让用户选择文件。用户明确对应关系后，后台复用现有解析、来源准备、成果保存和项目提交边界；选择文件只对该目标提供输入，不自动猜配其他来源，不改变完整来源的已保存内容。不将补缺解释为升级整个来源并删除未匹配译文；不能可靠对齐的已保存条目继续保留，不伪造已对齐状态。
10. 补齐成功后重新准备发起操作，复用其原范围和参数以及现有许可/目标保护，不要求用户从功能入口重新开始。取消选文件只取消当前操作，不关闭工程、不撤销已保存编辑、不影响其他来源；补齐失败显示可操作原因并保留原有状态。切换工程/版本或关闭窗口后，旧请求不得自动执行到新目标。文件选择及补齐不是新的校验门禁，沿用现有输入、身份和提交规则。
11. 助手和桌面使用相同输入事实及补齐用例。助手工具通过结构化 `source_input_repair` 返回缺原文或模板的既有前提，GUI 主线程提供可执行动作，worker 不调用 Qt。真实失败回执继续保留；仅专用缺输入失败使原事项等待 `source_input_required`，不把整个请求伪报成功，也不吞掉其他失败。补齐后只解除原事项该原因，重新获得 admission 并重新准备/确认原工具范围，不沿用已消费许可、不重跑成功事项、不通过自然语言重提整个请求代替恢复。
12. 已保存原文和未知 context 是不同证据。缺 artifact 的文字操作可使用真实 `EntryKey.original`；捕获、成果保存和合入须保留 context 是否已知，只有 saved-only 明确证据标记未知，真实来源解析得到的空 context 仍是已知空值；不能将未知 `None` 序列化为空字符串后伪造已知 context。旧成果没有新证据时继续原保护，显式 context、locator 与内容身份保护不放宽。助手动态词库与 GUI 共用稳定定位，报告传递冻结轻量来源身份，不重新持有来源 bytes。原始参考清空后，写回默认目标不得退回快照 URI；明确输出目录可使用保存文件名。

当前落点：`application/projects/source_inputs.py` 的 `MissingProjectSourceInput` 描述来源可用性，`persistence/project_source_inputs.py` 只读已存成果并逐来源汇总。正常版本和历史恢复以已存状态为主，与确实可用且身份一致的基线作无损并集，补入真实缺省条目但不丢缺基线行、不复活 tombstone；显式保存的空译文、阶段、标签及引用保持。`ProjectSourceSupplementService` 提供 prepare/remap/commit/discard，条目对应预览独立于实际发布；`source_input_publication.py` 从来源更新抽取原原子发布，由两用例共用。部分来源仍有可用成果时保留其已知原文，新输入不替换已有成果。历史搜索及文字型读模型可使用 `EntryKey.original` 中真实保存的原文，缺失时仍不猜测，也不据此构造二进制模板或来源快照。

实现覆盖边界：上述文件选择与自动继续已接桌面入口和助手工具链；S09 通过独立成果合入、请求等待/映射/新许可及真实 offscreen 助手窗口验证。助手 GUI 覆盖取消、忙状态、确认保存前后失败与关闭清理；模型任务启动和外部交互用测试替身，未执行真实 LLM、网络或人工桌面验收。详见[增量 003](../changelogs/application-preflight/story-09/2026-10-29-003-assistant-source-inputs.md)。

## 备选方案

- 仅关闭 UI 提示：仍有模型、归档和下游路径门禁，无法实现保存内容可独立使用。
- 仅将原函数移到公共工具模块：业务规则缺乏所有者，UI 仍可能自行判断。采用应用层按用例迁移与窄契约。
- 新建通用校验/自动修复总管：扩大规则和状态面，超过本次需求；不采用。

## 影响与风险

可选路径放宽需要覆盖模型校验、序列化、归档、UI 绑定和消费者，不能只改变单个入口。旧工程缺少成果时，系统保留已有版本并在实际需要缺失输入的操作上解释原因，不自动从外部文件猜测原文。来源内容摘要仍是成果完整性证据；不能把停止读取参考路径 hash 扩展为停止校验工程成果。

实施前 `VariantMaterializer` 会跳过没有 baseline 的 namespace，UI 安装又只消费 hydration；本轮使用未就绪来源的权威状态和展示修复，不能只删除只读弹窗。补缺与显式更新来源的责任不同：后者现有迁移会删除不在新版中的词条，不能直接把该行为用于修复缺输入。项目/版本记录损坏仍走原有保护，正常工程的来源输入缺失不得被升级为全局失败。

动态词库仍采用既有 reference-or-stable-key 本机缓存定位。参考清空后，不自动将原先按文件 stem 命名的本机缓存迁移到 stable-key 缓存；这项迁移未实施，工程正式术语和保存原文不受影响，也不承诺本机缓存随工程包迁移。

超大现有模块只做本地接线，新增责任放入完整且可独立测试的应用切片。历史文档中的原实现背景保留，但当前需求、关键决策和索引指向本契约。

## 迁移与回退

允许空参考并复用既有成果格式，不改依赖、不批量重写用户数据。UI 旧导入路径如需兼容，仅重导出应用契约，不保留第二份检查。回退代码时保留已存成果和空参考，不通过恢复“路径必填”规则使已正常保存的工程无法读取。
