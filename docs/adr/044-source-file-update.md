# ADR-044：源文件更新与多版本迁移

- 状态：提议（实现已按用户授权推进）
- 日期：2026-10-01
- 需求：[FR19.14](../requirements.md#fr19-source-update)；ParaTranz 顺序衔接遵守 [FR22.9～FR22.11](../requirements.md#fr22-context-order)。
- 关联：ADR-018、[实现计划](../../plans/source-file-update/plan.md)

## 背景与约束

来源指纹不匹配时，既有工程进入只读恢复；来源管理仅有新增和移除。正式 Variant 不保存原文与源顺序，不能靠比较翻译版本还原插件升级差异。一个工程的多个 Variant 共用来源登记，单独迁移当前版本会让其余版本无法正常加载。

## 决策

使用独立“更新源文件…”用例，保持来源登记 ID，解析相同格式的新版文件，按同一来源唯一 local_key 迁移全部版本，更新内容 namespace、指纹与路径。正常工作台与恢复窗口共用 prepare/commit 服务，Qt 只负责后台调度及确认。

预览令牌绑定 owner、生命周期 generation、工程与全部版本原始文件哈希。确认时重新解析新版，核验整个解析结果及源文件指纹；原文变化与来源变化不隐式覆盖用户预览后的编辑。来源更新本身不访问 ParaTranz。

原文可验证且内容相同的条目保留状态；原文/上下文变化或旧原文无法验证时保留译文并标为待复核；新增沿用新基线；删除保留在完整旧工程/旧版本备份中。旧快照保持历史原样，不承诺跨来源修订直接恢复。

## 持久化与故障恢复

独立 store 在共享 repository mutation lock 内校验全套前像，先写入持久备份与事务日志，再发布全部 Variant、最后发布 Project。异常按精确前像回滚；进程重启处理未完成事务，拒绝覆盖事务之外的修改。成功提交的日志有持久完成状态，后续版本保存不应被误认为事务冲突。

活动工程使用既有 lifecycle 内容提交边界，持久化成功后同步内存及已保存 revision；非活动工程提交不改变当前工作台，并使过期的待激活计划失效。初始运行时装配须在打开工程前恢复更新事务。

## 备选与影响

- 先删除再新增：会丢失条目状态、破坏多版本关系，拒绝采用。
- 忽略指纹直接打开：不能区分旧译文与新原文，也没有可审阅的影响预览，拒绝采用。
- 只更新当前翻译版本：工程级来源登记会与其他版本冲突，拒绝采用。
- 全量保存历史源文件：能提高覆盖更新后的原文比对质量，但改变工程资产容量与历史管理；本轮不引入，明确采用无法验证时待复核的规则。

现有工程无需 schema 升级。源文件本身不会被此功能改写；生成的备份保存在工程备份目录。旧文件已覆盖/丢失时可从恢复窗口继续更新。本地化插件的配套 Strings 旧指纹目前不在工程登记中独立保存，因此这类旧原文采用无法验证策略。
