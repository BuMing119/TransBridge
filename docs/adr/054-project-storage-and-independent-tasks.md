# ADR-054：翻译数据项目库与独立任务存储

- 状态：已采用；2026-11-09 本地实现与相关验证完成，限制见实施记录。
- 需求：[FR32](../requirements/project-storage-redesign.md)，已由用户确认。
- 计划：[project-storage-redesign](../../plans/project-storage-redesign/plan.md)。
- 决策边界：取代 ADR-051 的来源完整闭包、旧工程自动升级；局部取代 ADR-018 的 Project/Variant JSON 全量持久化、ADR-035 的跨 Project/Variant 文件 journal、ADR-049 的项目绑定任务与旧包升级、ADR-050 的可选来源参考路径。保留这些文档的历史理由；Session 存储、条目身份、应用层权威变更、三方合入及输出发布保护继续适用。
- 用户后续已授权按计划实施，指定 Sol/high 子 Agent 负责编码和单元测试，主会话负责总体验证；不迁移、清理真实用户数据，不顺带修改依赖或安装器。

## 背景与仓库事实

改造前 `bootstrap/persistence.py::build_persistence_v2_services` 装配 Project/Variant JSON repository、来源 artifact、缺内容自动恢复和跨文档 journal。`source_artifact_codec.py` 保存完整 PreparedProjectSource 对象图。`VariantSnapshot.to_dto` 同时输出 entries 与 translations/labels 映射；只给 JSON 换个容器不能消除这些成本。

`GuiProjectCommandFacade.task_result_directory` 要求活动项目存在并返回项目记录父目录。TaskHistoryStore 持久化整份报告，RecoveryStorage 保存带 prepared_source 等字段的输入世代；任务结果、历史和恢复分属多个保存路径。改目录不能实现生命周期独立。

`EntryKey` 的 namespace、local_key、original（包括 None 与空字符串之别）共同定义身份。现有身份、Stage、显式清空、来源顺序和领域冲突规则可复用，不能因改存储降为仅 local_key 匹配。

仓库已在术语与历史搜索使用标准库 sqlite3；本轮只读环境核验为 Python 3.12.12 / SQLite 3.50.4。工作台已有 QTableView 和后台打开协调器，但权威聚合、投影、部分 AI/术语/搜索消费者仍要求全量 Snapshot/hydration。

## 真实候选与选择

1. 压缩现有 JSON：能减小部分占用，但仍全量解码、全量保存，且保留对象图、插件闭包和任务耦合，不采用。
2. 按来源分片 JSON 加增量日志：可部分读取，但需自行维护条目索引、跨片事务、日志合并与恢复；复杂性集中到本次最敏感的保存路径，不作为首选。
3. 规范化 SQLite 项目库与独立任务库：以条目查询和事务更新表达权威状态，复用标准库及仓库已有使用经验；推荐。收益须通过同口径测量验证，不把“使用 SQLite”当性能验收。

## 一、存储归属与新格式

以下为本轮实现采用的归属与格式；实际接口定义见 `application/projects/storage_contracts.py`、`application/tasks/storage_contracts.py`，SQL 定义见各存储包的 `schema.py`。

- 项目根：`data/project-store-v1/<ProjectId.encoded>/project.sqlite3`。一个项目包含多个版本，Project、来源、条目、Variant 状态、命名快照和合入凭据在同一事务数据库内。
- 项目附属业务资产：同一项目自有目录下的 `terminology/` 等明确列举的业务存储。复用术语库的格式和查询能力，修改路径注入，不能继续写入旧 `data/projects`。项目中只保留选择所需的稳定 profile/version 引用；选择引用与译文提交同事务，不能同时在术语库维护另一份可写 selection。具体适配纳入 S03/S09。
- 任务根：`data/task-store-v1/tasks.sqlite3`。运行、输入条目、候选、处理决定、报告和续跑状态以 Run ID 管理。任务日志/报告文件如确需外置，位于该根的 run 自有目录，使用白名单类型与相对引用；不复制插件，不指向项目自有文件作为必要依赖。
- 工作区偏好与会话存储保持独立。项目列表索引为可重建轻量投影，采用新根内的索引；活动项目偏好使用新格式标识和项目 ID，不复用旧 active-project 指针触发自动恢复。
- 项目数据库由 application_id `0x54425031`、user_version `1` 和内部格式/实体元信息共同识别，不能只认 `.sqlite3` 后缀。当前版本之外明确拒绝，不自动迁移。
- 便携扩展名沿用 `.transbridge` 以复用入口，容器仍为 ZIP；采用新的必需 manifest：逻辑格式 `transbridge.translation-project`、版本 1，并包含明确列举的数据库/附属业务成员。旧包即使扩展名相同也拒绝，不能回退旧 reader。

项目打开、保存及目录列举不查询任务库。任务查询不要求项目存在；目标可用性按需要查询项目目录，列表中失效关联显示“原项目已删除”，不在每次打开项目时反向修补全部任务。

## 二、项目数据模型与字段边界

项目数据按责任划分为以下记录，实际表与索引以 `persistence/project_store/schema.py` 为准：

- 项目/版本：稳定身份、显示名、创建信息、revision、有效版本及业务配置；无绝对来源路径。
- 来源与来源修订：来源 ID、namespace、显示名称、FormatId、影响解释的解析选项、内容修订、插件作用域和来源关系。复用已有必要来源指纹作为身份事实，不为每次读写新增整库哈希。
- 来源条目：完整 EntryKey、真实原文、必要上下文、记录/字段类型、解析顺序及最小定位信息。稳定来源信息按来源保存，不逐行重复 namespace 对象和插件描述。
- 版本状态：以 variant_id 和条目身份关联，保存译文、Stage、标签、provenance、entry revision、tombstone、外部业务引用。空字符串是明确值，未加载不是空，未提供字段不是清空。默认未翻译状态可缺省表达；不得据默认值遗漏真实业务字段。
- 格式字段：按格式白名单保存 EET/SST/XML/JSON 的原生翻译字段、物理记录次序、重复定位、编码等必要保真信息。不得通过通用 metadata/bytes 入口把 SourceSnapshot、插件树或路径嵌套存入。
- 项目历史：用户命名快照或来源更新前恢复点保存必要翻译状态及所引用的来源修订。只在这些显式事件创建，不在每次保存、结果批次或任务回执时复制整个项目。
- 合入凭据：operation_id、Run ID、不可变成果修订、目标、处理决定和提交 revision/结果摘要。只证明已提交业务行为，不保存任务日志或完整任务输入，不使项目依赖任务库才能打开。

逻辑条目身份必须区分 original=None 和 original=""；SQLite NULL 的唯一性不能替代领域唯一性。采用原值与显式存在标记或等价可逆结构，保留大小写与重复定位语义；不得以文件名、行号或新内容哈希取代 EntryKey。数据库内部代理键仅为关联优化，不对外替换业务身份。

不保存 baseline 和 hydration 两份完整条目；二者改为按用途从权威数据构建的短期读模型。Project/Variant 不再保存重复 translations/labels 全表。必要的小字段 JSON 采用显式版本与白名单，不允许任意 dataclass codec。

## 三、来源提取与按需写回

导入链为：本次用户输入 → 现有格式识别与解析 → 翻译字段提取器 → 校验过的项目事务。完整插件及其解析对象只在操作作用域存在；成功、失败、取消都释放，不交给任务持久化和跨操作缓存。来源路径只存在本次操作参数与即时错误定位中，持久化来源身份、诊断摘要、UI 历史和恢复载荷不携带可用来重找源插件的路径。

插件字段白名单必须覆盖现有使用者所需的 FormID/EditorID、记录/字段类型、重复定位区分、String 表类型与 ID、对话/人物/任务关联、原文及顺序；保存必要语义关系，不保存整棵插件对象树。Strings 仅保留提取的翻译内容与必要定位，不保留完整写回表和原始片段。

EET/SST 等是翻译文件，不是插件。其重复物理记录与原生翻译字段仍须保真；以格式专用的有界记录表示保存，导出时重建短期文档交给既有 writer，不能默认直接丢弃未知字段、缓存字段或重复行。S02/S07 必须用真实格式夹具证明 round-trip；若发现字段模型不足，补齐明确格式字段并复验，不退回完整通用来源对象存储。需求不授权削弱既有格式保真或把“不存插件”扩成“不支持翻译文件”。

写回插件单独创建本次操作的输入绑定：用户重新选择插件与必要 Strings → 校验条目映射、解析选项及输出策略 → 沿现有 publish/fidelity 路径生成用户输出 → 释放输入。不同内容插件不得只因名称相同被接受；普通严格写回与明确目标插件迁移的规则保持分离。成功也不发布新的永久 source artifact。不要求原插件存在才能显示项目“已保存”。

## 四、读取、工作副本与保存

ProjectReadPort 提供项目概况、来源目录、按来源/范围读取条目、按完整身份批量取值、计数/筛选/排序及版本读令牌。结果为只读页或有限批次，不把整个 VariantSnapshot 当唯一公开读取方式。

ProjectWorkingCopy 持有 project/variant generation、基准 revision 与稀疏 dirty patch；UI 的当前来源驻留投影单独管理。编辑从权威命令进入 patch；UI collection 只作投影，不再反向序列化 UI 保存。字段明确提供与清空分别表达。修改的行不会随前台投影释放而消失，dirty patch 与前台驻留内容分开计量。

打开先准备目录、当前版本及当前来源首屏，随后自动在后台完整读取当前来源并安装驻留投影，不依赖滚动触发后续读取。驻留完成后的滚动直接访问内存，筛选和排序复用完整投影；其他来源仍按需打开，来源切换或关闭释放旧投影。后台结果核对项目/版本/generation 和读 revision，不能覆盖新编辑或切换后的页面。全局搜索、批量选择和导出须使用全范围查询或一致读取会话，不得只处理首屏；“全选”保存范围谓词与版本证据，不能等同已加载行。首次可用时间、完整驻留时间与内存成本分别测量。

保存捕获当前 patch 及 generation，在项目数据库事务内验证 expected revision，按变化更新必要行、Project/Variant revision 和本批合入凭据，再一次提交。提交完成只清除本次捕获且未被后续编辑替换的 patch；编辑期间新增修改仍为 dirty。无变化不建立写事务、不增加 revision 或快照。冲突返回结构化原因，保留 patch；不通过全库 hash 验证每次保存。

新建、来源增加/移除、更新源文件、版本复制与快照恢复可以触及整个受影响范围，其原子性不能为了小事务而拆成用户可见半完成状态。大型操作先后台准备，再一次发布，取消只在提交前生效；提交后报告实际结果，不伪装已回滚。

## 五、SQLite 生命周期与并发策略

首版使用标准库 sqlite3、显式事务、foreign_keys 校验、同步持久化配置，**默认 rollback journal（DELETE），不启用 WAL**。每个连接由单一 worker/线程持有；不以 check_same_thread=False 代替同步。跨进程同库写入用短事务、revision CAS 和有界 busy 等待，多窗口间不共享可变 DTO。

这个选择基于当前环境而非性能结论：SQLite 官方记录 WAL-reset 竞态涉及受影响版本的多个连接并发写/检查点，本地 3.50.4 不在已修复版本之列。修复版本包含 3.50.7、3.51.3 及后续版本。首版不为本次存储重做顺带改依赖或内置运行时；若后续基准证明需要 WAL，应另行评估并验证修复后的发行运行时。[SQLite 官方 WAL 文档](https://www.sqlite.org/wal.html#walresetbug)

rollback journal 允许一致事务，但长读会影响写入。普通页面读使用短事务；任务固定输入通过短批读取并核对开始/结束 revision，有限次数重试后明确“输入正在变化”，不得拼出跨版本内容。固定后释放连接再调用外部服务。大型导出、命名快照或来源变更可以持有明确的项目操作租约，等待/取消在后台处理，不能把整个 AI 运行期变成数据库读事务。[SQLite 官方隔离说明](https://www.sqlite.org/isolation.html)

备份与项目导出使用数据库提供的一致复制能力或受控事务导出，不能复制正在写入的主文件来假装完整快照；导出的副本关闭连接、验证身份与引用后再发布。Python sqlite3 提供 backup 接口，具体异常与事务边界按标准库文档实现。[SQLite Backup API](https://www.sqlite.org/backup.html)、[Python 3.12 sqlite3](https://docs.python.org/3.12/library/sqlite3.html)

连接关闭、忙、磁盘满、只读、取消、损坏须变成可定位诊断。内容删除后的文件压缩作为受控维护，不在每次保存执行全库整理。支持本机存储，跨机器共享网络数据库不在本期保证内；不修改术语等既有数据库的 journal 配置。

## 六、独立任务与跨库合入

TaskStore 接收明确 Run ID、Owner 和目标关联，无 active project 参数前置。TaskRuntime 的运行状态仍是执行权威，任务库是其持久记录及成果存储，不另造调度器。任务输入是实际任务范围的必要翻译数据，不复制无关版本、整个项目、来源插件或任意 prepared_source。

候选按不可变成果修订和条目身份保存；进度、逐条结果、报告视图共同引用这份记录，不在 history/recovery/report 三处反复写同一大载荷。终态任务与可恢复能力分别表达；缺插件时只能重新选择，不能显示可无条件继续。

项目库和任务库不构成一个隐式分布式事务，不依赖跨库 ATTACH 原子性。合入协议如下：

1. 任务库先持久保存不可变成果与处理请求，分配 operation_id，固定候选修订、目标、选择及策略。
2. 使用现有相关字段三方比较，读取目标权威状态，生成稀疏 patch；目标不存在或身份不符时保持成果，禁止自动重定向。
3. 普通 working-copy 合入只标“已应用、待保存”，不把任务标为已持久合入；相应凭据随 patch 待提交。显式保存型合入走同一项目事务。
4. 项目保存同时提交实际 patch 和对应 operation_id 凭据。这是持久合入的唯一证据。
5. 成功后更新任务的处理状态。若此更新失败，显示“项目已保存，任务状态待同步”；下次仅在任务恢复/查询时按 operation_id 对账，不重跑模型、不重放项目写入。
6. 同 operation_id 只能对应同一不可变请求；相同重试读取已有凭据，变更选择生成新请求。删除、来源变化及新的用户编辑仍按现有冲突规则处理，不以幂等为由覆盖。

如果用户在首次保存前撤销或改写合入字段，对应待提交凭据必须按实际存活的 patch 更新/拆分，不得把未持久的候选标为已合入。任务库失败不能回滚已经成功保存的项目；项目库失败不能删去任务候选。详细故障矩阵见 S06 Story。

删除任务只删除任务根内的材料，不触及项目及合入凭据；删除项目在停止该项目写入、释放连接和处理未保存内容后标记不可用，再清理自有目录，不遍历任务库级联删除。列表索引不是真相，残留删除阶段可以重试；任务仍能报告失效目标。运行中任务可继续形成独立成果，但不能向删除目标提交。

中间材料回收入口仅处理已终态、无未处理候选、无执行租约且可重建/已被替代的材料；本轮不启动定时自动清理，也不按未经确认的天数删除正式成果和历史。未完成或未合并任务受到删除保护，运行租约阻止并发清理。任务删除发布 cleanup_pending 状态后回收本任务目录，失败可重试；不把旧目录纳入回收。空间测量分别记录项目与任务，当前不新增容量管理界面。

## 七、术语、搜索、会话与工程包

历史搜索、术语构建、命名方案、AI 输入和 ParaTranz 使用 ProjectReadPort 的用途查询；不得为兼容旧消费者提前 hydrate 全项目。会话可以保留指向旧项目的历史文字和关联，但只读浏览不激活旧工程；执行时目标不可用则明确拒绝/要求选择新的受支持目标，不自动迁移。

术语库仍独立管理不可变 profile/version 数据。项目提交只切换稳定选择引用；写入新术语版本须先成功发布，随后项目事务引用，失败留下可回收但未引用的新术语版本，不能留下指向未发布数据的正式项目。旧跨库 selection journal 不继续用于新项目。删除仍被项目引用的版本须受引用保护。

便携包导出先保存或明确选择已保存 revision，并冻结本次项目及所引用不可变附属版本；导出副本只保留选择的快照/必要来源修订与业务资产，剔除运行合入凭据、删除暂存、缓存和任务记录。不可直接递归打包项目目录或裸拷整库后宣称已剔除历史。

包导入先检验新 manifest、路径、重复成员、体积限制、数据库格式/允许对象和引用关系，再在新根 staging 发布。对不可信 SQLite 文件禁用扩展和非必要 schema 执行，先按预期表结构验证；不能将包中任意数据库当可执行配置打开。失败保留原包和原项目，清理本次 staging；身份冲突由显式副本/重命名处理。副本生成新 Project ID，规范内部引用，不携带原任务凭据；业务 namespace 不因新目录而变化。

## 八、兼容、退役与回退

不提供旧 Project/Variant/schema 迁移器、新旧双写、legacy 包转换或旧 artifact 恢复。新 composition 不调用旧项目 journal recovery、catalog repair 和 source content repair；它们不得在版本识别前修改用户旧数据。Session 仍需要的旧 persistence 基础设施按实际引用保留，不能整包删除 `persistence/v2`。

新项目上线前旧项目处理链从所有入口断开，旧数据原样留存。开发分阶段可以保留尚未切换的实现供基线验证，但最终产品不提供旧格式开关或长期 adapter。若需回退代码，旧程序不读取/降级新项目，新数据保留；不把旧磁盘空间已释放作为上线结果。

## 风险与验收

主要风险是最小字段遗漏、未加载数据被当成空、全量消费者旁路、跨库合入双写误判、历史修订无限增长和旧启动恢复仍可达。S02/S03/S06 分别形成可交接细化；依赖图、入口矩阵和性能预算在计划维护。

本轮字段保真、故障注入、保存期间编辑、无插件持久化、旧格式零改写、真实 Qt 和同输入性能对照的证据见[实施记录](../changelogs/project-storage-redesign/story-01-to-10/2026-11-09-001-translation-project-store.md)。没有宣称清空系统缓存后的冷开、所有机器的性能或全库测试全绿；三个既有失败及其他验证限制保留。
