# /bm-council — 技术议会

> **DSH 子代理工具映射**：本 skill 的「并行 spawn N 个专家 Agent」在 DeepSeek Harness 下用 `subagent` 工具实现——R1 阶段在同一条消息内并行发起 N 个独立 `subagent`（`run_in_background: true`，每个 prompt 独立、互不知晓彼此），全部发起后用 `list_agents` / `job_output` 收齐 R1 产出；R2 阶段再并行发起 N 个**新** `subagent`（非 continue，即不 `send_message` 续用旧会话），把匿名化的 R1 汇总注入其 prompt。「非 continue」在 DSH 下 = 为 R2 重新调用 `subagent`（不复用 R1 的子代理会话）。

## 参数

- `/bm-council <问题描述>` — 传入问题或议题，召集专家议会进行多轮辩论
- `/bm-council` — 无参数，提示用户输入议题

## 触发时机

- 面临技术选型需要多视角权衡
- 方案完成后需要多角色把关
- 遇到复杂 bug 需要诊断思路
- 架构决策需要多方意见
- 任何"拿不准"的技术问题

## 配置前置检查

启动时若 `.dsh/bm_config/paths.json` 不存在或内容为空，则**自动调用 `/bm-init`** 进行交互式初始化，等待初始化完成后再继续执行本 skill 的后续步骤。

## 配置文件

启动时读取 `.dsh/bm_config/paths.json`，使用以下目录配置：

| 配置键 | 默认值 | 本 skill 用途 |
|--------|--------|--------------|
| `docs_dir` | `docs` | 读取需求文档、ADR、索引以获取项目上下文 |
| `plans_dir` | `plans` | 读取相关 plan 了解方案背景 |
| `adr_dir` | `docs/adr` | 读取架构决策作为分析依据 |

子路径命名由各 skill 自行约定，不从配置读取。

## 职责

1. **议题分析**：理解用户问题，识别涉及的技术领域
2. **议会召集**：按领域自动匹配专家组（3-5 人），即刻启动辩论
3. **主持辩论**：组织两轮专家辩论（独立分析 → 交叉辩论）
4. **汇总建议**：综合所有专家意见，输出结构化建议

## 禁止事项

- **不写文档文件**：所有讨论过程和结论均在对话中呈现，不产生文件
- **不做最终决策**：提供建议和风险分析，最终决策权归用户
- **不替代其他 skill**：议会建议后，用户自行决定是否调用 bm-plan/bm-arch/bm-dev 等执行
- **不因确认而中断**：议会组成自动匹配，不通过 ask_user_question 打断用户。用户可在辩论进行中随时调整专家组成

## 专家角色池

### 核心角色（默认 3 人）

| 角色 | 代号 | 分析框架 | 关注点 |
|------|------|---------|--------|
| 系统架构师 | architect | ADR、模块边界、技术栈匹配度、接口契约 | 系统耦合、扩展性、技术债务、架构一致性 |
| 开发工程师 | developer | 实现可行性、代码影响面、重构成本、现有模式 | 文件改动量、模式复用、开发效率、可维护性 |
| 质量专家 | quality | 测试策略、边界条件、回归风险、数据完整性 | 测试覆盖、异常路径、边界输入、回归范围 |

### 扩展角色（按议题领域关键词自动匹配）

| 角色 | 代号 | 匹配关键词 | 关注点 |
|------|------|-----------|--------|
| 安全专家 | security | 安全、auth、token、注入、权限、敏感数据、加密、encrypt、XSS、SQL注入、越权 | OWASP、威胁建模、合规、数据保护、认证授权 |
| 性能专家 | performance | 性能、慢、卡顿、内存、并发、QPS、O(n)、瓶颈、吞吐、延迟 | 时间复杂度、内存泄漏、I/O 瓶颈、缓存策略、连接池 |
| 产品/UX | product | 用户、交互、UI、体验、流程、易用性、界面、操作 | 需求合理性、用户体验、操作流程、信息架构 |
| 数据专家 | data | 数据库、迁移、schema、存储、索引、查询、SQL、表结构 | 数据模型、迁移策略、存储方案、查询优化、一致性 |

### 议会规模规则

- **简单决策**（单一领域，2 个以下关注维度）→ 3 人核心组
- **标准决策**（跨 2-3 个领域）→ 核心组 + 1-2 个扩展角色
- **复杂决策**（全系统影响、安全关键、性能敏感）→ 核心组 + 3-4 个扩展角色，**上限 5 人**

## 工作流

### 步骤 1：议题接收与领域分析

1. 解析用户输入，提取议题核心问题
2. 判定议题类型：技术选型 / 方案评审 / 问题诊断 / 架构决策 / 综合
3. 扫描议题关键词，匹配扩展角色
4. 读取相关上下文（若议题涉及已有 plan/ADR，读取对应文件以提供背景信息）

### 步骤 2：议会组成自动匹配（直接启动，不中断）

**根据议题自动匹配专家组，向用户简要展示后立即启动 R1。**

展示格式（简短通告，不等待用户回复）：

```
🏛 技术议会 — 自动召集

议题：<一句话摘要> | 类型：<类型> | 复杂度：<简单/标准/复杂>

议会组成（N 人）：
  🏗 系统架构师  💻 开发工程师  ✅ 质量专家  ⚡ 性能专家

预计 2 轮 × N 人 = 2N 次 Agent 调用。即刻启动，可随时说"调整议会"增减成员。
```

**议会规模自动判定**：
- **简单**（单一领域，2 个以下维度）→ 核心 3 人
- **标准**（跨 2-3 个领域）→ 核心 3 + 1-2 扩展
- **复杂**（全系统影响、安全关键、性能敏感）→ 核心 3 + 2-4 扩展，上限 5 人

**议员可在 R1 进行中调整**：用户说"去掉XX角色"或"加上YY专家"时，动态调整后续流程。

**仅在以下情况使用 ask_user_question**：
- 议题领域模糊，无法判断匹配哪些扩展角色（如议题同时涉及安全+性能+数据，可能超出 5 人上限）
- 用户明确要求"让我选专家"

### 步骤 3：Round 1 — 独立分析（并行 spawn）

并行 spawn N 个 Agent，每个 Agent 使用其角色专属的 R1 prompt。

**关键约束**：
- 每个专家只知道自己的角色和议题，**不知道议会中还有哪些其他成员**
- prompt 中不提及"其他专家"或"多轮辩论"，确保分析的独立性
- 所有专家使用相同的输出格式

**R1 通用 Prompt 结构**：

```
## 角色：{角色名}（{代号}）

你是 TransBridge 项目技术议会的一名**{角色名}**。
你的职责是从{专业领域}的视角，对议题进行独立、深入的分析。

## 项目背景

TransBridge 是一个 SSE mod 本地化工具，将翻译条目在 ESP 插件、EET/XT XML 和 ParaTranz 之间转换/上传/同步。技术栈：Python 3 + PyQt6，src/transbridge/ 下按功能分包。

## 议题

{用户原始问题}

{相关上下文 —— 如涉及已有 plan/ADR，摘录关键段落}

## 分析框架

作为{角色名}，请从以下维度分析此议题：
{角色特定的分析维度列表，见下方各角色定义}

## 约束

1. **独立分析**：基于你的专业视角独立判断，不要猜测其他领域的考量
2. **基于事实**：所有判断必须基于议题中提供的信息，不确定的地方请标注"需确认：..."
3. **具体而非抽象**：给出具体的风险、建议、替代方案，而非泛泛而谈
4. **承认边界**：明确说明哪些超出了你的专业范围，标注"建议咨询：[领域]专家"
5. **关注 TransBridge 实际场景**：这是一个 mod 翻译工具，非通用 Web 服务

## 输出格式

### {角色名}分析报告

**核心判断**：[1-2 句话，你的总体立场和建议]

**关键发现**：
- 发现 1：...
- 发现 2：...

**风险识别**：
| 风险 | 严重程度 | 缓解建议 |
|------|---------|---------|
| ... | Blocker/Critical/Major/Minor | ... |

**建议与替代方案**：
- 首选方案：...（理由：...）
- 替代方案：...（权衡：...）

**需其他领域关注的问题**：
- [需确认] ...

**建议咨询的领域**：
- ...（如本议题超出你的专业范围的部分）
```

#### 各角色 R1 分析维度

**系统架构师 (architect)**：
- 架构影响：此议题对现有模块边界、接口契约、数据流的影响
- 技术匹配度：候选方案与现有技术栈（Python/PyQt6）的契合度
- 耦合风险：方案是否引入新的模块耦合或循环依赖
- 扩展性：方案对未来类似需求的支持能力
- 架构一致性：是否符合现有 ADR 决策方向

**开发工程师 (developer)**：
- 实现可行性：方案的技术可行性和工作量估算
- 代码影响面：预估涉及的文件和模块数量、改动行数
- 现有模式复用：项目中是否已有可复用的代码模式或工具函数
- 开发效率：不同方案的实现成本和维护成本对比
- 风险点：实现过程中可能遇到的技术难点

**质量专家 (quality)**：
- 测试策略：需要哪些类型的测试（单元/集成/E2E）
- 边界条件：异常输入、空数据、大文件、并发操作等边界场景
- 回归风险：改动对现有功能的潜在影响范围
- 数据完整性：翻译条目、配置文件的数据一致性保障
- 验收标准：如何验证方案的正确性和完整性

**安全专家 (security)**：
- 输入安全：用户输入、文件导入的注入风险和路径遍历
- 认证授权：API key、token 的存储和传输安全
- 数据保护：翻译数据、配置文件的敏感信息处理
- 依赖安全：新引入依赖的已知漏洞检查
- 合规风险：开源协议兼容性

**性能专家 (performance)**：
- 时间复杂度：核心路径的算法复杂度分析
- 内存占用：大数据量（万级翻译条目）下的内存消耗
- I/O 瓶颈：文件读写、网络请求的性能影响
- UI 响应：PyQt6 主线程阻塞风险
- 缓存策略：可复用的计算结果和缓存机会

**产品/UX (product)**：
- 需求合理性：议题是否解决了真正的用户问题
- 用户体验：对操作流程、等待时间、错误提示的影响
- 信息架构：功能在 UI 中的位置和导航路径
- 用户心智模型：功能是否符合 mod 作者的预期行为

**数据专家 (data)**：
- 数据模型：涉及的 TranslationEntry/Collection 结构变化
- 存储方案：JSON/INI/二进制文件的读写策略
- 迁移兼容：数据格式变更的前向/后向兼容
- 查询效率：大量条目下的查找/过滤/排序性能
- 一致性：多数据源（ESP/EET/XT/ParaTranz）之间的同步

### 步骤 4：Round 2 — 交叉辩论（并行 spawn）

所有 R1 Agent 返回后，并行 spawn N 个新 Agent（新一轮，非 continue），进行交叉辩论。

**设计决策**：使用新 Agent 而非 continue，确保每个专家能客观审视所有观点。R1 的观点被匿名化为"观点 A/B/C"，专家不知道哪个观点来自哪个角色（包括自己的）。

**R2 通用 Prompt**：

```
## 角色：{角色名}（{代号}）

你是 TransBridge 项目技术议会的一名**{角色名}**。

## 议题

{用户原始问题}

## 第一轮专家意见汇总

{逐一列出 N 个匿名化观点，每个观点的完整 R1 分析}
格式：
### 观点 A
{完整 R1 分析内容}

### 观点 B
{完整 R1 分析内容}

...

## 输出格式

### {角色名}交叉辩论报告
```

## 汇总策略指南

主席汇总时，遵循以下原则：

### 共识判定标准

| 级别 | 标准 |
|------|------|
| **强共识** | 所有专家明确同意，R2 中无人反对 |
| **弱共识** | 多数专家同意，R2 中有保留意见但未明确反对 |
| **无共识** | R2 中仍有明确对立立场 |

### 分歧处理

- **技术事实分歧**（如"会不会导致循环导入"）→ 议长基于代码结构判断，给出倾向性建议
- **价值判断分歧**（如"要不要引入新依赖"）→ 列出双方理由，标记为需用户决策
- **风险偏好分歧**（如"性能优化是否值得增加复杂度"）→ 给出不同风险偏好下的建议

### 建议优先级定义

| 优先级 | 定义 |
|--------|------|
| **P0** | 强共识 + 低风险 + 高收益 → 强烈建议立即执行 |
| **P1** | 强共识或弱共识 + 中风险 → 建议执行但需注意风险 |
| **P2** | 弱共识或分歧 + 高风险 → 可选，需用户权衡后决定 |

## 规则

- **议会组成自动匹配**：步骤 2 根据议题关键词自动匹配专家组，简短通告后直接启动 R1，不打断用户。仅在议题跨领域过多（可能超 5 人上限）或用户明确要求时才使用 ask_user_question
- **R1 必须保证独立性**：各专家的 R1 prompt 不得提及"其他专家"或暗示多轮辩论的存在
- **R2 观点必须匿名化**：用"观点 A/B/C"代替角色名，确保专家客观审阅（包括对自己 R1 观点的审阅）
- **不写文档文件**：所有讨论和结论在对话中完成，不产生文件产出
- **最终决策权归用户**：议会提供建议和分析，不做最终决策
- **议会规模上限 5 人**：控制 Agent 调用成本，复杂议题 5 人、标准 4 人、简单 3 人
- **汇总由主会话完成**：步骤 5 不再 spawn Agent，减少成本
- **所有文件路径引用必须从 `.dsh/bm_config/paths.json` 读取，不得硬编码**
