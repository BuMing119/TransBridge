# /bm-dev-serial — 代码开发者（串行版）

> **DSH 子代理工具映射**：本 skill 中的「spawn 子 Agent」在 DeepSeek Harness 下用 `subagent` 工具实现。串行版 = 每次 `subagent` 用 `run_in_background: false`（同步等待结果）或 `run_in_background: true` + `job_output` 逐个子代理收结果后再派下一个；「并行 spawn N 个」见 `bm-dev`（并行版）。`general-purpose` 类型即不带产品 provider 的普通 `subagent`。prompt 模板中的「前序 Agent 变更摘要」通过 `send_message` 传给后续子代理。

## 参数

- `/bm-dev-serial <feature>` — 指定 plan 文件名（不含 .md），进入**严格执行模式**
- `/bm-dev-serial 我要实现 xxx` / `/bm-dev-serial 修复 xxx` — 描述形式，进入**灵活开发模式**

## 配置前置检查

启动时若 `.dsh/bm_config/paths.json` 不存在或内容为空，则**自动调用 `/bm-init`** 进行交互式初始化，等待初始化完成后再继续执行本 skill 的后续步骤。

## 配置文件

启动时读取 `.dsh/bm_config/paths.json`，使用以下目录配置：

| 配置键 | 默认值 | 本 skill 用途 |
|--------|--------|--------------|
| `plans_dir` | `plans` | 方案 `{plans_dir}/{feature}/plan.md`，Story `{plans_dir}/{feature}/stories/` |
| `docs_dir` | `docs` | 文档索引 `{docs_dir}/INDEX.md` |
| `tests_dir` | `tests` | 测试代码 `{tests_dir}/{module}/test_{file}.py` |

子路径命名由各 skill 自行约定，不从配置读取。

## 与 bm-dev 的区别

本 skill 是 bm-dev 的**串行变体**，核心差异：

| 维度 | bm-dev（并行版） | bm-dev-serial（串行版） |
|------|-----------------|----------------------|
| 多实例执行 | 同一条消息并行 spawn N 个 Agent | 逐个 spawn，等前一个完成再启动下一个 |
| 接口契约 | 必须冻结契约以防止并行冲突 | 无需冻结，后续 Agent 直接使用前序 Agent 的产出 |
| 上下文传递 | 每个 Agent 独立，互不知晓 | 后续 Agent 接收前序 Agent 变更摘要作为上下文 |
| 合并步骤 | 需要冲突检测、术语一致性检查 | 无并行冲突，合并简化 |

**适用场景**：使用 DeepSeek 等有并发限流的模型时，或希望 Agent 间有明确先后依赖关系时。

## 职责

1. 读取并理解 plan（严格执行模式）或理解用户需求（灵活模式）
2. **规模判定**：自动判定任务规模，决定单实例自行完成或多实例串行调度
3. **多实例模式下**：拆分任务 → 串行逐个 spawn 子 Agent → 合并结果 → 运行集成测试
4. **单实例模式下**：自行编码、运行测试、验证
5. 确保编码产出与 plan 一致，测试覆盖完整

## 禁止事项

- **不调用任何其他 skill**（包括 `/bm-plan`、`/bm-arch`、`/bm-qa`、`/bm-chronicle` 等）
- **不写 changelog、不更新索引**（留给 `/bm-chronicle` 或编排器统一处理）
- **不做复杂度判定或流程编排**（复杂度判定仅限于编码任务本身的规模，以决定单/多实例）
- **不替代 Analyst / Planner / Architect / Chronicler / QA 的角色**
- **多实例模式下，子 Agent 不直接修改 plan、不写 changelog**

## 通用前置步骤：规模判定（30 秒内）

**此步骤在两种模式的编码阶段前强制执行。**

### 判定依据

1. **提取文件清单**：
   - 严格执行模式：从 plan/story 中提取"涉及文件"列表
   - 灵活开发模式：根据用户描述，用 Glob/Grep 快速定位相关文件
2. **依赖分析**：检查文件间的导入/调用关系，判断哪些是独立可拆分的
3. **判定规则**：

| 判定结果 | 条件 | 下一步 |
|---------|------|--------|
| **单实例模式** | ≤2 个文件且无跨文件强依赖 | 进入单实例编码流程 |
| **多实例串行模式** | 3+ 个文件，或跨模块，或文件间有明确边界 | 进入多实例串行调度流程 |

**防御性降级**：若文件间耦合过强（大量循环导入、共享全局状态）且无法冻结接口契约 → **降级为单实例**，但向用户说明原因。

## 模式一：严格执行模式（有 plan）

触发条件：用户传入 `<feature>` 参数，且 `plans/<feature>/plan.md` 存在。

### 步骤 1：读取输入

1. 读取 `plans/<feature>/plan.md`
2. 读取 `docs/INDEX.md`（了解项目模块上下文）
3. 扫描 `plans/<feature>/stories/story-*.md`，若存在已确认的 Story 详细文档，将其作为编码的优先参考
4. 若 plan 不存在 → 终止，告知用户"plan 不存在，请以描述形式调用本角色进行灵活开发"

### 步骤 2：检查 plan 状态

| plan 状态 | 处理方式 |
|-----------|---------|
| **已确认** | 直接进入步骤 3 |
| **草稿 / 待确认** | 通过 `ask_user_question` 询问用户："plan 尚未确认，是否继续编码？" 提供选项："继续编码" / "终止，先去确认 plan" |
| **已实现** | 询问用户是否覆盖或追加功能 |

### 步骤 3：规模判定与路由

执行**通用前置步骤：规模判定**。

- **单实例** → 进入「步骤 3A：单实例编码」
- **多实例串行** → 进入「步骤 3B：多实例串行编码」

---

### 步骤 3A：单实例编码

适用场景：规模判定为单实例（≤2 个文件，无强耦合）。

1. **按 Story 顺序编码**：
   - 提取 plan 中的 Story 清单、验收标准、涉及文件
   - 对每个 Story，检查 `plans/<feature>/stories/story-<NN>-<slug>.md` 是否存在：
     - **存在且已确认** → 优先按 story 文档中的详细指导（数据流、伪代码、边界条件）实现
     - **不存在** → 按 plan 中的实现步骤编码
   - 读取涉及文件的当前内容，按实现步骤修改代码
   - 保持与现有代码风格一致

2. **编码纪律**：
   - 只做 plan 描述的事，不额外优化、不重构无关代码
   - 若发现 plan 遗漏 → 记录并告知用户，不得擅自修改未列出文件
   - 若发现 plan 有明显错误 → 暂停编码，向用户说明问题

3. **运行测试**：
   - 运行 plan 中涉及模块的现有测试
   - 补充单元测试覆盖新增逻辑（测试文件遵循 ADR-002 镜像结构）
   - 测试失败 → 修复至通过

4. **汇报**：
   - 已完成的 Story 列表
   - 修改的文件列表
   - 是否有因 plan 边界限制而未实现的内容
   - 提醒用户：编码完成后**必须**调用 `/bm-chronicle` 做规范化记录

---

### 步骤 3B：多实例串行编码

适用场景：规模判定为多实例（3+ 个文件，或跨模块）。

**核心理念**：`bm-dev-serial` 主会话不直接写代码，而是作为**任务拆分器 + 串行调度器 + 合并验证器**。子 Agent 逐个执行，每个完成后主会话检查结果，再启动下一个。

#### 子步骤 1：任务拆分

1. **提取完整文件清单**：
   - 从 plan/story 中提取所有涉及文件路径
   - 包含新增文件、修改文件、删除文件

2. **依赖分析**：
   - 读取各文件的 import/依赖关系
   - 标记文件间的耦合强度和先后依赖顺序

3. **边界分组**（按文件边界拆分）：
   - 每个子任务负责 **1-2 个独立文件** 的修改
   - 若一个 Story 涉及 3+ 个文件但逻辑紧密相关 → 可合并为一个子任务，但上限为 3 个文件

4. **确定串行执行顺序**：
   - 按依赖关系排序：被依赖的文件（基础模块/接口/数据模型）先执行
   - 无依赖关系的子任务按逻辑顺序排列（如：先 parser 后 writer）
   - 同一文件只能由一个 Agent 负责，若多个子任务需改同一文件 → 合并为单一子任务

5. **向用户呈现串行执行计划**（简要），通过 `ask_user_question` 确认或调整：
   - 列出子任务序号、负责文件、预计依赖关系
   - 说明串行执行顺序及理由

#### 子步骤 2：串行逐个 Spawn 子 Agent

**逐个执行**（不是并行），每个子任务流程：

1. **准备 prompt**：包含子任务描述 + **前序 Agent 的变更摘要**（首个 Agent 无此前缀）
2. **spawn 单个 general-purpose 类型 Agent**
3. **等待 Agent 完成**并返回结果
4. **检查结果**：
   - 通过 → 记录该 Agent 的变更摘要，进入下一个子任务
   - 失败 → 暂停，向用户说明失败原因，询问"重试 / 跳过 / 终止"
5. 重复直到所有子任务完成

每个子 Agent 的 prompt 必须包含：

```
## 子任务描述
你是第 <N>/<总数> 个执行的 Agent。
你负责修改以下文件：
- <文件路径 1>（操作：修改/新建/删除）
- <文件路径 2>（操作：修改/新建/删除）

## 边界约束（严禁越界）
- 禁止修改以下文件：<列出不在本 Agent 职责内的文件>
- 禁止做本任务描述范围之外的重构或优化

## 输入上下文
### Plan 片段
<从 plan/story 中提取的与本任务相关的实现步骤>

### 前序 Agent 变更摘要（仅供了解，无需重复实现）
<前面已完成的 Agent 修改了哪些文件、做了什么关键变更>
<若这是第一个 Agent，写"无">

### 需要修改的文件的当前内容
<文件 1 的当前内容>
<文件 2 的当前内容>

## 编码要求
- 保持与现有代码风格一致
- 只做本任务描述的事，不额外优化
- 若发现明显问题 → 记录问题摘要并汇报，不擅自修改范围外内容
- 前序 Agent 已完成的变更已生效，你读取的文件内容是最新的，无需重复前序工作

## 测试要求（强制）
- **必须**为修改/新增的代码编写或更新单元测试
- 测试文件放置在 `tests/` 目录，遵循 ADR-002 镜像结构
  - 如修改 `server/app/xxx.py` → 测试放在 `server/tests/test_xxx.py`
- **必须**运行你负责的测试并确保通过
- 测试未通过不得汇报完成

## 输出格式
完成后向主会话汇报：
1. 修改的文件列表及每处关键变更摘要
2. 新增/更新的测试文件列表
3. 测试运行结果（通过/失败）
4. 发现的任何问题或建议
```

#### 子步骤 3：结果合并

所有子 Agent 完成后，主会话执行合并：

1. **变更汇总**：
   - 按执行顺序列出所有 Agent 的变更
   - 确认没有遗漏的文件或 Story

2. **接口一致性检查**：
   - 跨子任务的函数签名、数据结构是否匹配
   - 如发现不匹配 → 分析原因并 spawn 一个修复 Agent 或自行修复

3. **完整性检查**：
   - 对照 plan/story 验收标准，确认所有需求已覆盖
   - 如有遗漏 → spawn 补充 Agent 处理

#### 子步骤 4：集成测试

1. 运行项目完整测试套件（包括所有子 Agent 负责的单元测试）
2. 验证各子 Agent 修改后的代码协同工作
3. 如有失败 → 分析原因：
   - **单个 Agent 的测试在其范围内通过，但集成时失败** → 主会话自行修复集成问题，或 spawn 汇总 Agent 裁定
   - **单个 Agent 的测试本身有遗漏** → 反馈给对应 Agent 修复
4. 集成测试通过后，方可进入汇报

#### 子步骤 5：汇报

向用户输出：
- 子任务串行执行清单（每个 Agent 负责的文件、执行顺序、执行结果）
- 各子 Agent 完成状态（成功/失败/需要重试）
- 修改的文件总列表（汇总）
- 集成测试结果
- 是否有因 plan 边界限制而未实现的内容
- 发现的任何问题或建议
- 提醒用户：编码完成后**必须**调用 `/bm-chronicle` 做规范化记录和状态更新，**未记录不得进入下一 Story/阶段**

## 模式二：灵活开发模式（无 plan）

触发条件：用户以描述形式调用，无对应 plan 文件。

适用场景：修 bug、改配置、更新依赖、小功能迭代、探索原型、plan 未覆盖的补丁。

### 步骤 1：理解需求

1. 读取 `docs/INDEX.md` 和 `docs/changelogs/INDEX.md`（了解最近变更上下文）
2. 根据用户描述，使用 Glob/Grep/Read 定位相关代码
3. 向用户呈现初步理解（2-3 句话），确认方向正确

### 步骤 2：规模判定

执行**通用前置步骤：规模判定**：
- 用户描述的修改涉及 ≤2 个文件 → 进入「步骤 3A：单实例灵活开发」
- 涉及 3+ 个文件 → 进入「步骤 3B：多实例串行灵活开发」

### 步骤 3A：单实例灵活开发

1. **口头确认修改点**：通过 `ask_user_question` 向用户呈现计划修改的文件列表、每处修改的简要说明、预计影响范围
2. 用户确认后方可编码
3. 读取相关文件，按确认的范围修改
4. 如涉及配置/依赖变更，同步更新相关文件
5. 运行受影响模块的测试，如有失败则修复
6. 简要汇报变更摘要，提醒调用 `/bm-chronicle`

### 步骤 3B：多实例串行灵活开发

1. **自行分析文件边界**：根据用户描述和代码扫描结果，列出所有涉及文件
2. **执行多实例拆分**：按「模式一 步骤 3B」的子步骤 1-5 执行
   - 子任务按文件边界拆分，每个 Agent 负责 1-2 个文件
   - 确定串行执行顺序（按依赖关系排列）
3. 向用户呈现串行执行计划（简要），通过 `ask_user_question` 确认或调整
4. 串行逐个 spawn 子 Agent（按「模式一 步骤 3B」子步骤 2 的 prompt 模板）
5. 合并结果（子步骤 3）
6. 运行集成测试（子步骤 4）
7. 汇报（子步骤 5）

---

## 禁止场景

以下场景**不得**使用多实例串行：

1. **子任务间存在强耦合且无法冻结接口契约** → 降级为单实例
2. **子任务需要修改同一文件的不同部分** → 合并为单一子任务，若合并后仍过大则降级为单实例
3. **用户明确要求简化流程**（极简模式）→ 直接单实例
4. **涉及配置文件的单行变更**（如改版本号、开关配置）→ 单实例
5. **子任务数超过 6 个** → 串行耗时过长，建议拆分为多个 `/bm-dev-serial` 调用分阶段执行，或考虑使用 `/bm-dev` 并行版

## 统一规则

- **规模判定是强制步骤**：任何编码任务开始前必须先判定单/多实例
- **多实例模式下主会话不直接写代码**：只做拆分、串行调度、合并、验证
- **子 Agent 严格边界化**：每个子 Agent 只改分配的文件，禁止越界
- **禁止同文件多 Agent**：同一文件只能由一个 Agent 负责
- **测试是每个子 Agent 的强制职责**：子 Agent 必须写测试并确保通过
- **集成测试是主会话的强制职责**：所有子 Agent 完成后必须运行集成测试
- **不修改 plan 中未列出的文件**（严格执行模式）
- **不新增 plan 中未预见的文件**（严格执行模式）
- **append-only，永不删改既有 changelog 内容**
- **保持与现有代码风格一致**
- **测试文件位置遵循 ADR-002**：新建测试文件放置在 `tests/` 镜像源码子包结构，共享夹具提取到 `conftest.py`
- **所有文件路径引用必须从 `.dsh/bm_config/paths.json` 读取，不得硬编码。**
- **任何文件修改都必须记录**：编码完成后**必须**调用 `/bm-chronicle` 记录本次所有文件变更（增/改/删/移），未记录不得进入下一 Story 或下一阶段
