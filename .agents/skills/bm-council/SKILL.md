# BM 技术议会

## 目标

获得少量、独立、证据驱动的专家意见，并把分歧压缩成用户可行动的决策建议。

## Codex 协作模型

- 议会本身即明确授权使用子 Agent。遵守当前 Codex 的协作槽位：主会话之外最多同时运行 3 个子 Agent。
- 默认选择 2–3 个与议题直接相关的角色，不固定凑齐架构、开发、QA。安全、性能、UX、数据等角色只在确实相关时加入。
- Round 1 使用 spawn_agent 创建独立子 Agent 并行分析，再用 wait_agent 等待结果。使用最少的任务上下文，传递原始问题和必要文件，不泄露主会话的预设结论。
- 默认不再为每个角色启动第二轮新 Agent。主会话比较 Round 1 结果；只有存在关键事实冲突且一次定向复核能解决时，才用 followup_task 给相关 Agent 定向复核。
- 子 Agent 只做只读分析，不修改共享文件。主会话负责事实核验和最终综合。

## 工作流

1. 把议题压缩成一个可回答的问题，读取相关代码、plan、ADR、测试或日志。
2. 按风险选择角色，并在 commentary 中简短告知议会组成和关注面，不等待无必要确认。
3. 为每个角色创建有界任务，要求输出：核心判断、证据、主要风险、推荐、仍需核验的事实。
4. 等待所有结果。对文件位置、API 行为、测试结果等可验证事实，由主会话亲自核验；不要用多数投票代替证据。
5. 若意见冲突，区分事实冲突、目标权衡和风险偏好。必要时做一次定向追问，不进行固定两轮表演式辩论。
6. 输出简洁结论：推荐、共识、关键分歧、风险/缓解措施和下一步。

## 输出要求

- 先给出议长建议和置信度，再给证据。
- 清楚标注哪些是仓库事实、哪些是专家判断、哪些仍未知。
- 对价值取舍给出推荐但保留用户决策权；对可核验技术事实给出明确结论。
- 不展示冗长的逐专家原文，除非用户要求。

## 边界

- 默认不写文件、不改代码、不创建 ADR。
- 不为简单问题启动议会；直接由主会话回答更高效。
- 不超过可用协作槽位，不让多个 Agent 修改同一文件，不启动没有独立产出的子任务。
- 协作工具不可用时，由主会话按相同角色框架完成分析，并明确说明未进行独立 Agent 评议。
