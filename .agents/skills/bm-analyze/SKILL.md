# BM 需求分析

## 目标

把用户意图转成可验证的需求，不提前决定实现方案。

## Codex 执行约定

- 先读取仓库事实，再提出问题。优先检查 README、现有需求、相关代码、测试和 Git 差异。
- 使用 rg / rg --files 定位内容；配置存在时从 .codex/bm_config/paths.json 读取路径，不存在时使用仓库已有结构，不因缺少配置阻断任务。
- 对可逆且范围明确的文档写入直接执行。仅当不同答案会显著改变范围、数据兼容性、外部行为或交付物时，才向用户提出一个简短问题。
- 不使用不存在的 AskUserQuestion、Skill、Glob 或 Explore 接口；使用当前 Codex 提供的对话、搜索和编辑工具。

## 工作流

1. 确认分析对象，读取相关需求条目和实现现状。
2. 区分用户目标、显式要求、合理推断和未知项。不要把推断写成既定事实。
3. 明确范围内、范围外、依赖、兼容性、失败行为和非功能约束。
4. 为每个用户可见行为给出可验证的验收标准；覆盖空输入、无效输入、部分失败、重复操作和回滚/恢复等相关边界。
5. 检查与现有需求、代码或 ADR 的冲突。若能基于仓库事实消解，直接说明；否则提出最小必要问题。
6. 用户要求文档产物时，更新配置指定的需求文档；优先编辑匹配条目，避免重复追加同一需求。
7. 复读写入内容，报告文件路径、关键假设和仍待决定的问题。

## 建议文档结构

包含：需求标题、状态、优先级、目标、范围内、范围外、行为与验收标准、边界与失败处理、约束与依赖、未决问题。只保留与当前需求相关的章节。

需求尚未获得用户明确确认时使用“草稿”，不要自行标记为“已确认”。

## 边界

- 不输出代码，不做技术选型，不编写实现步骤。
- 不强制建立完整流程；typo、单项配置等极小改动可以只给简短验收描述。
- 不覆盖或重排无关的既有需求内容。
- 不自动创建 changelog；只有用户或调用方明确要求记录时才交给 bm-chronicle。
