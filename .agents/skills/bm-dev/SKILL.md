# BM 开发

## 目标

在保护用户现有改动的前提下完成可验证的代码变更。

## 模式选择

- 计划模式：用户指定 feature，或能唯一匹配 plans/<feature>/plan.md。把 plan、已展开 story 和 ADR 作为约束与验收依据。
- 直接模式：修 bug、小功能、配置或维护任务没有对应 plan。以用户请求和仓库事实为准，不强迫补齐全套 BM 文档。
- plan 与当前代码冲突时，先判断是文档过期还是实现风险。可安全处理的偏差要说明并继续；会改变产品范围或公共契约时再询问用户。

## Codex 执行约定

- 开始前读取 git status 和目标文件，区分用户已有改动。不要回滚、覆盖或顺手整理无关内容。
- 使用 rg / rg --files 搜索，使用 apply_patch 编辑文本文件。遵循仓库中的 AGENTS.md、格式化、测试和依赖管理约定。
- 对需要三个以上实质步骤的任务使用任务计划，并在执行中更新状态。
- 可逆、范围明确的实现直接进行；仅在缺少会显著改变结果的决策、需要外部写入、破坏性操作或扩大范围时暂停。
- 不按文件数量机械触发多 Agent。默认由主会话完成；仅当用户要求并行/子 Agent，或任务存在至少两个真正独立且不会修改同一文件的工作流时，才按 multi-agent-pattern 协作。主会话始终负责集成和验证。

## 工作流

1. 用一句话复述目标，定位入口、调用链、测试和相关文档。
2. 确定最小正确变更集，包括实现、测试、类型/配置/文档的必要联动；不要把“plan 未列出”当作拒绝修改必需测试或接口调用方的理由。
3. 阅读所有将修改文件的当前内容和相邻模式，再编辑。
4. 先运行最相关的测试或静态检查；修复由本次变更引起的失败。
5. 风险较高或跨模块时，再运行更广的回归验证。不要为低风险单行改动默认跑整个仓库。
6. 审查最终 diff：范围、错误处理、兼容性、无意格式化、敏感信息和遗留调试代码。
7. 最终报告变更、验证命令及结果、未验证项和真实遗留风险。

## 测试原则

- 优先沿用仓库现有测试框架与目录，不硬编码 pytest、ADR 编号或镜像布局。
- 对行为变化添加能在旧实现上失败、在新实现上通过的测试。
- 不为满足覆盖率编写只验证 mock 调用次数的脆弱测试。
- 无法运行测试时说明具体原因，不声称通过。

## 边界

- 不自动创建 changelog、提交、push 或安装未授权依赖。
- 不擅自修改需求、ADR 或 plan 的产品边界。
- 不将无关 lint、历史失败或用户改动混入本次修复；必要时单独报告。
