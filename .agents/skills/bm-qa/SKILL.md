# BM 质量验证

## 目标

用可复现证据判断变更是否正确，并优先报告会影响用户或维护者的问题。

## 意图与写入权限

- “审查/找问题/诊断”默认只读：检查代码并运行非破坏性验证，不修改业务代码。
- “补测试/完善测试”允许编辑测试文件，但不自动修复生产代码。
- “修复并验证”明确包含修复时，按 bm-dev 的开发纪律修改后复验。
- 只有用户或调用方要求报告文件时才写入 test-reports；普通审查直接在对话中交付。

## Codex 执行约定

- 先读取 Git diff、相关 plan/story/ADR、项目测试配置和受影响调用链。
- 沿用仓库现有测试框架、fixture 和目录；不强制 pytest、400 行限制、ADR-002 或特定导入写法。
- 先运行最小相关测试，再根据风险扩展到模块或全套验证。记录精确命令、退出码和关键失败。
- 宽范围且维度真正独立时，只有用户要求子 Agent/并行评审，或调用方明确授权时，才按 multi-agent-pattern 分派只读审查；主会话统一核验事实。
- 代码审查先给 findings，按严重程度排序并引用精确文件与行号。没有问题时明确说“未发现问题”，同时说明测试覆盖盲区。

## 检查顺序

1. 需求/plan 一致性：用户可见行为和验收标准是否满足。
2. 正确性：状态转换、错误处理、边界输入、资源释放、并发和幂等。
3. 回归：公共接口、序列化、配置、持久化和兼容性。
4. 安全：仅检查与攻击面相关的输入、路径、命令、凭据和权限。
5. 性能：仅检查热路径、主线程阻塞、大数据规模和明显复杂度风险。
6. 可维护性：重复、命名、不可达逻辑和测试脆弱性；不要把纯偏好升级成高严重度。

## 严重度

- Blocker：数据损坏、可利用安全漏洞、主流程不可用或无法构建/启动。
- Critical：核心行为错误、重大兼容风险或高概率严重回归。
- Major：特定条件下的错误、重要测试缺口或明显维护风险。
- Minor：低影响一致性、可读性或优化建议。

严重度基于影响和可达性，不基于个人风格。

## 报告

每个 finding 包含：标题、严重度、证据位置、触发条件、影响和最小修复方向。报告验证命令及结果、未运行项及原因。若创建文件，使用配置指定的 test_reports_dir 和仓库既有命名格式，不强制新建并行片段目录。

## 边界

- 不把测试失败自动归咎于当前变更；对比基线或检查差异。
- 不声称静态阅读等同于运行验证。
- 不因发现 Major/Minor 自动改业务代码。
- 不更新 plan 为“已实现”或写 changelog，除非用户明确要求该状态变更。
