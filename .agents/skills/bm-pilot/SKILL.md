# BM 自动驾驶

## 目标

在当前 Codex 任务中从现状持续执行到可交付结果，减少不必要的停顿和重复确认。

## Codex 原生编排

Codex 没有通用的 Skill(...) 调用工具。不要输出伪调用，也不要要求用户逐个重新输入命令。需要进入某阶段时：

1. 在 commentary 中说明正在应用哪个 BM skill 及原因。
2. 完整读取同级目录下该 skill 的 SKILL.md。
3. 在当前主会话中直接执行其工作流。
4. 用任务计划记录阶段状态；阶段完成后依据产物和验证结果继续。

若上下文被压缩，依据当前任务计划、Git diff 和已生成产物继续，不从头重复已完成工作。

## 启动

1. 读取 .codex/bm_config/paths.json 和 pilot.json（若存在），并检查 AGENTS.md、Git 状态和相关 BM 产物。
2. 识别用户目标和当前阶段。无参数调用时，从未提交变更、plan/story 状态和测试证据推断最可能的活动工作线；存在多个候选且选择会改变写入目标时询问用户。
3. 按影响选择路线：
   - 直接：bm-dev → 验证。
   - 规划：按需 bm-analyze → bm-plan → bm-dev → bm-qa。
   - 架构：按需 bm-analyze → bm-arch → bm-plan → bm-dev → bm-qa。
4. 使用 pilot.json 的 dev_skill 选择 bm-dev 或 bm-dev-serial；值无效时回退 bm-dev。
5. 用 update_plan 建立当前任务的阶段计划并开始执行。路线是可调整的，不因最初分类阻止必要的相邻工作。

## 自动推进规则

- 用户已授权端到端执行，因此对可逆、范围内的本地读取、编辑和测试直接继续。
- 仅在以下情况暂停：缺少会显著改变产品行为的选择；需要外部写入/发布；破坏性操作；权限审批；Blocker 无安全替代；用户现有改动与目标不可区分。
- 下游 skill 中若存在比本 skill 更保守的例行确认，以本节的最少暂停规则为准。
- 某阶段已有充分、匹配且可信的产物时跳过，不重新生成。
- 架构和 plan 文档状态未经用户明确接受时保持“提议/草稿”，但若实现目标已清楚，不必仅为状态标签停止编码。
- Story 细化只用于复杂交接或高风险数据流，不默认给每个 Story 生成文档。
- bm-chronicle 只在用户、仓库规则或明确流程配置要求审计记录时加入；不把 changelog 当作每阶段门禁。
- bm-council 只在用户要求专家评议，或高风险决策确实需要独立意见时加入。

## 阶段完成标准

- 分析：目标、范围和验收行为足以指导下一阶段。
- 架构：影响长期结构的关键契约和迁移策略已明确。
- 计划：变更边界、步骤、文件落点和验收方式可执行。
- 开发：代码与必要测试已完成，diff 已审查。
- QA：相关检查已运行，失败已修复或明确报告。
- 记录：仅在被要求时，增量文件与实际 diff 一致。

不要用“文件存在”替代上述内容判断。

## 失败与恢复

- 测试失败：先判断是否由本次变更引起；在授权范围内修复并重跑。
- plan/代码冲突：优先核验当前事实，安全时更新计划或实现并说明；产品边界冲突时暂停。
- 连续遇到同一外部阻塞时，尝试安全替代并清楚报告，不进行无效循环。
- 用户中途追加要求时，把它并入当前目标并更新计划；若明确替换原目标，停止旧路线。

## 收尾

运行与风险相称的最终验证，审查 git diff，并把计划全部更新为 completed。最终报告交付结果、修改文件、验证命令和结果、未完成项及原因；不要只报告“已调用哪些 skill”。
