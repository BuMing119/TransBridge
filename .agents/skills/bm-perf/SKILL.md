# BM 性能验证

## 目标

用仓库认可的代表性场景，比较改动前后的耗时、吞吐量和峰值内存；结论必须能由他人复现。

## 意图与写入权限

- “性能分析/定位变慢/性能验证”默认只读：运行基准、检查代码和报告结果，不修改业务代码、性能阈值或基线。
- “优化性能”允许按 `bm-dev` 的纪律修改代码，并在改动后复验。
- 只有用户明确要求持久化结果时，才在 `docs/performance/` 下新增或更新基准记录；不要把临时结果写入仓库。

## 执行约定

1. 先读取 [代表性场景](references/benchmark-scenarios.md)、相关 Git diff 与受影响的调用链。
2. 明确性能问题的用户可见指标：单次耗时、批量吞吐量、峰值内存、UI 响应性或启动时延。不要把无关指标混入结论。
3. 优先复用已有测试 fixture 和无网络、无 LLM API 的输入；若输入会改写数据，使用临时目录并在报告中说明。
4. 对可通过命令行运行的场景，使用 `scripts/benchmark_command.py` 重复执行；UI 场景使用现有测试/分析工具或人工测量，不虚构精确数据。
5. 比较前后版本时保持 Python 版本、依赖、硬件负载、输入样本和运行命令一致。至少运行 5 次，报告中位数及范围。
6. 先报告基线、结果和证据，再提出优化方向。没有可比较基线时，明确这是初始测量而非“无回归”的证明。

## 分析顺序

1. 复现：确认慢的是哪个用户路径和输入规模。
2. 测量：隔离 I/O、网络、模型加载等外部波动，并保留原始结果。
3. 定位：检查热路径、重复解析/序列化、集合复杂度、缓存命中、主线程阻塞及不必要的模型加载。
4. 验证：修复后使用相同场景复测，并运行最小相关功能测试。

## 报告

报告应包含：环境、提交/工作区状态、输入样本、测量命令、次数、原始或汇总结果、与基线的差异、结论、覆盖盲区和下一步建议。

将回归等级按实际用户影响说明；不要设定未获确认的全局百分比阈值。若性能下降来自网络、LLM 服务或首次模型下载，应单独标出，不能归因为本地代码回归。

## 边界

- 不运行需要真实 API 密钥的 LLM 测试，除非用户明确授权并提供安全的测试方式。
- 不因一次测量波动就断言回归；复测或说明不确定性。
- 不自动改变全局缓存、并发度、模型配置或发布设置。
