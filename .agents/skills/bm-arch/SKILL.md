# BM 架构设计

## 目标

基于真实仓库约束形成可执行、可追溯的系统级决策。

## Codex 执行约定

- 先检查 README、依赖清单、入口、模块边界、相关需求、现有 ADR 和测试；不要套用其他项目的目录或技术栈。
- 从 .codex/bm_config/paths.json 读取可用路径；缺失时按仓库实际结构工作。
- 对可能近期变化的框架能力、版本兼容或安全建议，使用官方文档核验；在 ADR 中区分事实与推断。
- 不为写 ADR 强制多轮确认。信息充分时直接给出推荐并将状态设为“提议”；只有用户明确接受后才标记“已接受”。
- 只有存在多个真正独立的架构研究面且并行能显著提高质量时才委派；同一 ADR 由主会话统一写入。

## 工作流

1. 定义待决策问题、约束、成功标准和不在本次处理范围内的内容。
2. 搜索现有 ADR。相同决策域优先更新原 ADR；若新结论取代旧结论，明确 supersedes/superseded-by 关系，不静默改写历史理由。
3. 检查当前代码中的依赖方向、数据流、公共接口和迁移风险。
4. 比较切实可行的方案。只列真实候选，说明成本、风险、可逆性和与现有系统的匹配度。
5. 给出一个推荐，记录关键契约：模块责任、输入输出、错误语义、兼容策略、迁移与回退方式。
6. 用户要求落盘时，在 ADR 目录创建新文件或编辑匹配 ADR。编号通过扫描现有文件确定，避免冲突。
7. 验证 ADR 中引用的路径和接口确实存在或被明确标为计划新增。

## ADR 最小结构

包含：标题、状态、日期、背景与约束、决策、关键契约、备选方案、影响与风险、迁移与回退。

## 边界

- 不把实现清单伪装成架构决策；细节交给 bm-plan 或 bm-story。
- 不硬编码项目专属测试布局、Web/Server 目录或特定框架。
- 不引入依赖、修改业务代码或执行迁移，除非用户同时明确要求实施。
- 不要求每个小改动都新建 ADR；只有影响长期结构或跨模块契约时才记录。
