# BM 实现计划

## 目标

把已明确的需求和架构约束转成开发者可直接执行、可验证的计划。

## Codex 执行约定

- 先读取相关需求、ADR、现有 plan、代码入口、测试和 Git 状态。计划必须描述当前仓库，而不是想象中的目录。
- 从 .codex/bm_config/paths.json 读取目录；缺失时使用仓库实际的 plans/docs 布局。
- 不要求写前和写后双重确认。用户请求计划即授权创建或更新计划；只有范围选择会产生实质不同方案时才提问。
- 不默认多 Agent。独立研究面很多且用户要求并行时可委派只读调研，主会话统一编写 plan。
- 技术选型已有 ADR 时遵守 ADR；没有 ADR 但只是局部实现选择时可在计划中记录合理假设。只有长期公共契约未定时才建议 bm-arch。

## 工作流

1. 定义 feature slug、目标、范围内/外和验收结果。
2. 搜索现有 plan，按需求语义和真实代码归属判断是更新现有 Epic 还是创建新 Epic。不要仅凭路径前缀硬匹配。
3. 追踪调用链和测试入口，列出必要文件及操作类型。计划新增文件时说明为何现有位置不合适。
4. 按可独立验收的行为拆分 Story。一个 Story 可以跨多个内聚文件；不要按文件机械拆 Story。
5. 为每个 Story 写验收标准、实施步骤、相关文件、依赖、边界条件和验证方式。步骤保持实现级但避免逐行伪代码。
6. 标明迁移、兼容、回退和风险；没有则省略，不填模板废话。
7. 创建或最小更新 plans/<feature>/plan.md；保留用户已有内容和已完成 Story，不重排无关章节。
8. 按仓库现有格式最小更新 plans/INDEX.md（若存在），复读链接和状态。

## Plan 最小内容

- 标题、状态、对应需求/ADR。
- 目标与非目标。
- 当前实现事实和关键约束。
- Story 列表。
- 每个 Story 的验收标准、文件落点、实现步骤、测试策略。
- 依赖顺序、风险与回退。
- 未决问题和明确假设。

新计划默认状态为“草稿”。用户已经明确批准具体方案时可标记“已确认”；不要把创建计划本身当作批准。

## Story 粒度

- 以独立用户价值或可验证工程能力为边界。
- 避免把“改模型、改服务、改 UI”拆成无法单独验收的横向 Story。
- 复杂数据流或跨团队交接才建议继续使用 bm-story；简单 Story 直接交给 bm-dev。

## 边界

- 不修改业务代码，不安装依赖，不执行迁移。
- 不把未知接口写成已存在事实。
- 不强制为小修复创建 plan。
- 不自动创建 changelog；按用户或项目规则决定是否记录。
