# BM 增量记录

## 目标

用仓库证据记录“改了什么、为什么、如何验证”，不把模型猜测写入历史。

## Codex 执行约定

- 先运行只读 Git 检查：git status --short、目标文件的 git diff / git diff --cached，并读取相关 plan、story 和现有 changelog。
- 工作区可能包含用户的既有改动。仅记录能与当前任务可靠关联的文件；不要把所有未提交内容都归到本次任务。
- 从 .codex/bm_config/paths.json 读取目录；缺失时使用 docs/changelogs、plans 和 docs 的现有结构。
- 既有增量文件保持 append-only：不修改、不重命名、不删除。索引文件可以为新增记录做最小更新。

## 工作流

1. 确定当前增量的文件集合、目的和验证证据。若无法区分当前任务与用户已有修改，停止写入并询问归属。
2. 按以下优先级确定 Epic/Story：用户指定；当前 story/plan；路径与 plan 的明确匹配；最后使用 maintenance/<topic> 或 unplanned/<topic>，不要凭空制造业务归属。
3. 扫描目标 Story 目录中的现有编号，使用下一个三位编号；同日同编号冲突时重新扫描。
4. 创建 YYYY-MM-DD-NNN-<slug>.md，逐文件记录符号/段落级变化、动机和测试结果。删除或移动也要明确说明来源与目标。
5. 只更新 changelog 索引及直接受影响的 plan/docs 索引条目。不要每次全库重算并改写无关状态。
6. 复读新文件和链接，确认路径可解析、编号唯一、没有记录未发生的变更。

## 增量文件内容

记录标题、日期、Epic/Story 关联、逐文件的操作类型/具体变化/原因、实际执行的验证命令与结果，以及真实遗留项。没有遗留项时写“无”。

## 边界

- 不修改业务代码，不提交 Git，不把未运行的测试写成通过。
- 不以文件时间戳替代 Git 差异和任务上下文。
- 不因缺少 plan 阻断维护、修复或文档类任务；使用明确的非计划归属。
- 若本次没有可记录的实际变更，直接说明，不创建空日志。
