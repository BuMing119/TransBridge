# Codex 多 Agent 协作模式

## 使用前提

同时满足以下条件才协作：

- 用户明确要求子 Agent/并行，或当前已加载 skill 明确授权。
- 至少有两个具体、有界、可独立推进的子任务。
- 子任务不需要同时修改同一文件或共享可变外部状态。
- 委派带来的并行收益大于协调和复核成本。

简单搜索、单文件修改、强依赖链和单次工具调用由主会话完成。

## Codex 约束

- 当前主会话占一个槽位；最多同时用 spawn_agent 创建 3 个子 Agent。
- 所有 Agent 共享工作区，变更立即可见。按文件或模块建立互斥所有权。
- 子 Agent 可以继续 spawn，因此任务中明确禁止继续委派，除非主会话特意授权。
- 主会话始终拥有最终决策、文件集成、测试和用户沟通责任。

## 工作流

1. 主会话先读取 Git 状态、任务规则和目标文件，保留用户现有改动。
2. 把任务拆成 2–3 个结果可独立验证的子任务。不要按角色名或文件数量机械拆分。
3. 为每个任务写明：目标、只读或可写、允许文件/模块、禁止范围、验收证据、是否允许测试，以及“不要再 spawn”。
4. 优先使用最小上下文 fork。让 Agent 从共享工作区读取原始文件，不粘贴主会话结论或预期答案。
5. 同时用 spawn_agent 创建可并行任务；依赖任务使用 followup_task，或在前序完成后再启动。
6. 等待期间主会话继续处理不冲突的集成准备、事实核验或测试设计。
7. 收到结果后检查实际文件、diff 和命令输出，不只相信摘要。
8. 对遗漏使用 followup_task 定向补充；对错误方向及时使用 interrupt_agent，避免无效继续。
9. 主会话统一解决术语/接口冲突，运行集成验证并汇报整体结果。

## 只读评议

对 council、代码审查或研究任务，子 Agent 默认只读。传递原始问题和必要文件，避免泄露主会话的倾向；主会话对可验证事实亲自复核。

## 写入协作

- 每个文件只分配给一个写入 Agent。
- 公共接口由主会话先冻结，或先串行完成基础契约再并行消费者。
- 不让子 Agent 执行 commit、push、发布、删除、迁移或外部写入。
- 发生重叠修改时停止并行，由主会话整合；不要让两个 Agent相互覆盖。

## 失败处理

- Agent 失败不等于任务失败。主会话先检查已产生的安全结果，再决定 follow-up、自行完成或缩小范围。
- 不无限重试同一阻塞。两次定向尝试仍无进展时，改用本地方案或向用户报告具体阻塞。
- 任务结束前确认没有仍在运行且可能继续写入的子 Agent。
