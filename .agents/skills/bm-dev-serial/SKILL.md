# BM 串行开发

## 目标

复用 bm-dev 的开发纪律，在确有必要时把大任务拆成依赖有序的串行子任务。

## 必须先读

完整读取 ../bm-dev/SKILL.md，并遵守其中的仓库保护、编辑、测试和汇报规则。本 skill 只覆盖任务调度方式。

## 使用条件

满足以下任一条件才使用串行子 Agent：

- 用户明确要求串行 Agent 或指定 bm-dev-serial。
- 运行环境限制并发。
- 后续工作必须消费前一步产生的接口、迁移或生成物。
- 单个上下文难以可靠处理，但任务能按明确依赖边界分段。

若任务小、强耦合或主要修改同一文件，由主会话直接按 bm-dev 完成，不为了“串行”而制造 Agent。

## 工作流

1. 检查计划、Git 状态和依赖关系，把任务拆成 2–6 个可验收子任务。
2. 按“基础契约/数据模型 → 实现 → 集成 → 测试/文档”排序。每个文件在同一阶段只交给一个 Agent。
3. 在 commentary 中简述顺序和边界。无需为明显合理的拆分额外等待确认。
4. 每次只用 spawn_agent 创建一个子 Agent，并用 wait_agent 等待；让它读取共享工作区中的最新文件，限制修改范围并运行局部验证。
5. 等待结果后，由主会话检查实际 diff 和测试输出。失败时先在当前范围内修复或用 followup_task 让原 Agent 补充；不要把错误上下文传给下一步。
6. 将已验证的变更摘要作为下一子任务的上下文，然后继续。
7. 全部完成后由主会话运行集成验证并审查整体 diff。

## 子任务要求

每个 Agent 任务必须包含：目标、允许修改的文件/模块、禁止范围、上游已完成事实、验收标准和验证命令。不要粘贴可由 Agent 从工作区读取的大段文件内容。

## 边界

- 不并行运行编码 Agent。
- 不让后续 Agent 假设前序工作成功；以主会话核验后的文件和测试为准。
- 不让子 Agent提交 Git、写 changelog、改 plan 或扩大范围。
- 子任务超过 6 个时，优先合并内聚步骤或分批交付，而不是制造长链。
