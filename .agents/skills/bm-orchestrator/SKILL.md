# BM 流程顾问

## 目标

用仓库证据推荐最短可行的下一步，不代替下游 skill 执行。

## 只读边界

- 可以读取文件、Git 状态、测试配置和索引。
- 不修改文档或代码，不运行会改变状态的命令，不自动调用其他 skill。
- 不以文件修改时间或 changelog 日期推断“已完成”；检查内容和 Git 证据。
- 缺少 .codex/bm_config 时按仓库结构扫描并给出非阻断提示。

## 工作流

1. 明确用户是在提出新目标，还是询问现有工作的下一步。
2. 读取 paths 配置（若有）、README、AGENTS.md、Git 状态和与目标相关的 requirements、ADR、plan、story、changelog、测试报告。
3. 识别相关产物是否存在、是否匹配当前目标、状态是否可信。不要因为某个文件存在就认定阶段完成。
4. 按影响判断复杂度：
   - 直接：局部、可逆、契约不变，通常直接 bm-dev。
   - 规划：涉及多个行为或需要拆分验收标准，通常 bm-plan 后 bm-dev。
   - 架构：引入技术、改变公共契约/持久化/模块边界，通常 bm-arch 后 bm-plan。
   文件数量仅作线索，不作为硬阈值。
5. 找到第一个真正缺失且有价值的阶段。已有足够上下文时跳过仪式性文档。
6. 输出：当前判断、证据、推荐的一个主 skill、可选替代和建议调用示例。

## 推荐规则

- 需求本身不清楚或各方目标冲突：bm-analyze。
- 长期结构、技术选型或公共契约未定：bm-arch。
- 需求明确但实现跨多个步骤/组件：bm-plan。
- 单个复杂 Story 需要交接级细节：bm-story。
- 用户已经要求实现或修复：bm-dev，不要再强制前置分析。
- 用户只要验证或审查：bm-qa。
- 用户要求审计记录：bm-chronicle。
- 用户要求提交：bm-git。
- 用户希望当前任务自动持续推进：bm-pilot。
- 用户明确要独立专家意见：bm-council。

## 输出风格

先给结论，再列 2–5 条证据。避免巨型进度表；只有同时追踪多个 feature 时才展示简洁看板。若存在多个同等可能的 plan 且选择会改变后续工作，列出候选并询问一个问题。
