# AI 翻译默认 100 并发与流式处理性能

- 状态：S19～S23 已实现并完成相关本地验证；真实服务和完整主窗口性能边界见交付记录。
- 日期：2026-10-24 规划，2026-10-25 实施。
- 归属：[AI 多插件并发计划](plan.md)，接续 S19～S23；遵守 [ADR-048](../../docs/adr/048-ai-project-concurrency-and-terms.md)。
- 目标：默认允许 100 个在途逻辑模型调用，减少本地流式处理开销，保留逐条展示、结果校验、暂停取消和恢复语义。

## 范围与优先级

完整范围是四项实现和一项验证：统一默认值、优化日志写盘、增量解析 JSON、增量检测重复输出、100 并发回归与基准；本轮五项均已落地。
实施时首先解决已测出的日志写盘瓶颈，再完成两项流式增量处理；新职责提取为独立模块，保持大型翻译主控只做接线。
不重写共享请求预算、Quest 顺序或三轮调度；不把批次 Token 预算改成并发数，不扩充准备线程数，不引入服务商自动调速或异步 HTTP 框架迁移。

## 实施前证据及其边界（2026-10-24）

- `config/llm.py` 的默认值为 3，`custom_workflow_profile.py` 的缺省回退也是 3；`single_task_view.py` 的控件初始值为 20，上限为 50。仅修改配置会被控件截断。
- 同一任务的模型阶段已共享 `AiRequestBudget`；额度覆盖逻辑调用及 SDK 内部重试，不能解释为账号全局连接数。
- 当前日志既写调用通道又写批次通道，100 路会产生约 200 个活跃通道。`WorkflowLogStore` 最多保留 64 个文件句柄，逐片段同步写入并刷新。
- `_run_batch` 的流式回调在每个片段到达时拼接全部文本、从头提取结果并扫描整段重复内容。
- 前一轮在 Windows / Python 3.12.12 / 32 逻辑处理器环境，以 100 个真实在途模拟调用、1000 条合成术语、16 字符/50ms 的流片段测试。每路 20 条、共 2000 条的五次总耗时中位数为 14.48 秒，范围 13.80～34.87 秒；10000 条候选均正确持久化并恢复。每路 1 条的五次中位耗时为 1.40 秒，范围 1.22～1.48 秒。
- 仅在测试实例内将文件池容量设为 256，五次中位耗时为 8.74 秒，范围 7.79～9.68 秒；额外计数对照中日志打开次数由 23307 次降至 200 次。该对照保留双通道日志，并非删除日志取得的收益。
- 数据覆盖真实批次解析、词法术语匹配、流日志、候选持久化和轻量 Qt 窗口；未覆盖真实模型、语义向量检索、完整校对及整个主窗口。测量有明显波动，不能作为固定耗时 SLA。
- 前轮相关 pytest 172 项及 Ruff 检查通过。临时脚本、输入和原始测量文件已清理，上述为会话测量摘要；实施前须建立可复现的正式基准并重新测量，不将摘要当成已保存的基线产物。

## S19：统一默认值和配置入口（已实现）

文件：`src/transbridge/config/llm.py`、`src/transbridge/application/translation/custom_workflow_profile.py`、`src/transbridge/ui/tools/ai_translator/single_task_view.py`、`src/transbridge/ui/settings/ai_service_page.py`；检查 `config_view.py`、任务配置快照和恢复接线；相关配置/UI 测试与 `docs/dev/ai_translator.md`。

实施：

1. 将新配置的默认并发设为 100，并让控件初始值和自定义流程缺省回退使用同一权威默认值，消除 3/20 的重复定义。
2. 界面范围调整为 1～128，与现有自定义流程及工具的显式 `max_concurrent` 范围一致；默认值仍是 100。
3. 保留用户显式保存的并发数及恢复任务的执行快照；只有缺失配置使用新默认。无法区分旧默认 3 和用户手动选择的 3 时，不猜测并覆盖。
4. 说明该值是本任务全流程共享的最大在途逻辑请求数。文档修改原说明，不叠加互相矛盾的新说明。

验收：新配置/缺失字段为 100；保存并重载 100 或 128 不截断；显式 3、20、50 和恢复任务原值不变；切换翻译/润色/混合模式不悄悄重置；已有输入校验和工具兼容别名语义不变。

## S20：消除流日志文件池抖动与逐片段刷新（已实现）

文件：`src/transbridge/ui/tools/ai_translator/workflow_log_store.py`、`workflow_logging_client.py`、`source_execution.py`；按实际调用点覆盖传统 worker 与校对组合入口。若需要独立后台写入组件，新增职责明确的 `workflow_log_writer.py`，仅承接缓冲、排空和文件生命周期。

实施：

1. 让文件池容量覆盖当前任务实际活跃的调用/批次通道，100 请求时至少容纳约 200 个通道，并预留诊断通道。容量仍有硬上限，完成的通道及时释放；不能无限放大整个进程的文件池。
2. 将流片段合并为有界缓冲，按字节阈值或短周期写入和刷新；周期初始候选不超过 500ms，结合实时日志读者验证。阻塞磁盘操作由后台承担，生产者不在全局存储锁内逐片段执行磁盘刷新。
3. 保留调用日志与批次日志现有用途、文件名和内容次序。本次先消除重复开关与小写入，不删除通道、不改变业务内容保真及凭据处理边界。
4. 调用结束、失败、通道关闭、任务结束须排空对应尾部；收尾等待置于后台生命周期。缓冲按总字节数设限，满载时显式背压；磁盘错误保留可见诊断，不静默丢日志、不把有效模型响应改判为翻译失败。
5. 保持实时查看能看到近期内容，必要时提供显式刷新边界给读者/测试。只缓冲诊断日志，候选检查点的可靠刷盘、校验及恢复承诺不变。

验收：100 路、200 通道反复交错写入时，不再随片段数增长而反复打开同一文件；每通道内容完整有序，尾部可读；内存/句柄有界；写盘异常、取消、重复关闭、迟到片段均不死锁，后台写入任务无泄漏。覆盖 `test_workflow_logging_client.py`、`test_live_llm_logs.py`，并为缓冲/文件生命周期新增聚焦测试。

## S21：真正按增量解析流式 JSON（已实现）

文件：新增 `src/transbridge/ai_translator/translation_stream.py`，小范围接入 `translator.py`、`prompt_builder.py`；新增纯 Python 流状态测试，复用 `test_prompt_builder.py`、`test_structured_output_contracts.py`、`test_translator_term_conflicts.py`。

实施：

1. 提取每请求独立的流状态：解析位置、未完成对象/字符串状态、已完成结果、重复 ID 和撤销状态；只解析新收到的文本，完成的条目不在每个片段重新解码。
2. 完整迁移当前逐条展示与重复 ID 撤销逻辑，`translator.py` 仅做接线；该模块已超过大小门槛，不能继续堆叠状态机和新职责。
3. 现有无状态提取接口保留兼容，复用同一解析规则；最终结构化响应校验、候选接纳和截断 salvage 的权威边界不变。

验收：任意片段切分、转义引号/反斜线/换行/Unicode、不完整字段、空结果、重复 ID、额外字段、无效结果和中断的行为与现有规则一致；重复 ID 的迟到出现能撤销先前暂存项。片段展示不等同于候选已持久化。长结果增加片段时，不重复解析全部已完成条目。

## S22：减少重复输出检测的全量扫描（已实现）

文件：新增 `src/transbridge/ai_translator/stream_repetition.py`；`translator.py` 的检测接口兼容接线；若 S21 已实施则通过流状态组件组合，避免两份完整字符串反复拼接。

实施：

1. 将重复检测作为独立可测责任提取；保留原文自适应阈值、单条回显/异常检查和截断位置语义。
2. 维护跨片段的重复状态和必要尾部，避免对整个历史内容重复执行全部正则。必须证明与当前行为等价，不能用固定尾窗或降低检查频率漏掉长重复链。
3. 已完成译文的检查只针对新条目；响应结束或异常修复处保留所需最终验证。暂停/取消和 `_RepetitionDetected` 的恢复行为不变。

验收：1～10 字符重复周期、跨块重复、长原文合法重复、正常长译文、JSON 转义及截断挽救无漏检/误判回归；检测时机不退化为只在响应结束检查；独立统计检测 CPU 时间与 Qt 心跳，不用总 CPU 使用率掩盖单线程热点。

## S23：100 并发的回归与可复现基准（本地验证完成）

文件：新增 `scripts/benchmark_ai_stream_concurrency.py`、`scripts/benchmark_ai_stream_processing.py` 和必要的高并发测试；复用预算、批次执行、候选日志、恢复、流日志及 UI 反馈测试。脚本仅用合成数据和模拟 provider，临时目录自行清理，支持结果输出参数。

实施与验收：

1. 确认真实峰值达到 100，不能只设置线程池 100。覆盖单来源和多来源共享额度、翻译/术语/校对混合、异常释放、暂停恢复、取消收尾；保留同 Quest 顺序和准备额度。
2. 固定输入与片段节奏，至少五轮前后交替运行。基础样本复现 100 路 × 1 条、100 路 × 20 条、1000 条术语、16 字符/50ms；补充长文本、大小片段和多波持续请求，避免只验证一个瞬时批次。
3. 分开报告导入/准备、片段回调、日志、候选保存及收尾；记录总耗时中位数/范围、实际并发峰值、积压延迟、CPU、内存、线程/句柄、文件打开/刷新次数和 Qt 心跳。恢复后的候选数量、身份、译文均须一致。
4. 将完整任务进度窗口、日志查看窗口以及保存/恢复接入独立集成样本；语义向量检索若启用，单独报告冷启动和热缓存，不将缺失能力算作通过。
5. 100 默认值不要求直接增加 HTTP 连接池：当前本地 httpx 默认最大连接数就是 100。须以无网络 mock 或本地测试传输核验初始化、取消后重建与连接释放；若同时承诺 128 可实际跑满或发现隐式瓶颈，再单独调整连接池与相关测试，不能把逻辑请求名额当成连接池配置。
6. 运行相关 pytest，以及 `uv run ruff check src tests`、`uv run ruff format --check src tests`。不默认调用真实 API；真实服务商吞吐、限流和语义质量另行验证。

## 顺序、兼容和回退

先建立 S23 的基线，再完成 S20；随后按长响应证据推进 S22/S21，最后启用 S19 并完成 S23 集成验收。各步骤串行测量，不与其他压测同时争用机器。
最小交付只需 S19 + S20 + S23；流解析与重复检测可独立回退，但不能移除已有异常保护以维持 100 并发。
默认值变化不迁移项目文件或检查点；已保存参数继续生效。日志缓冲可能在进程崩溃时损失尚未刷新的少量诊断尾部，该范围必须有界，不能影响已经确认持久化的翻译候选。正常关闭与取消必须排空尾部。
性能验收首先要求正确、无泄漏、没有反复开关文件的抖动及相关热点下降；耗时目标在同机正式基线建立后确定，不承诺先前临时对照的秒数在所有机器上复现。
