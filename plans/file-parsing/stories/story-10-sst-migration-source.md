# Story 10：SST 译文迁移

- 所属方案：[文件解析](../plan.md)。
- 当前集成：[SST 正式读写与插件导出](../../sst-integration/plan.md)，最终验证证据由该计划汇总。
- 架构：[ADR-052](../../../docs/adr/052-sst-io-integration.md)。
- 状态：2026-11-08 按完整 codec 与真实记录身份完成本地迁移集成，能力实验性。

## 目标与边界

SSU8 和 SSU9 都保存原文、译文。用户可将 SST 作为独立工程来源，或把其中已有译文迁移到已存在插件集合。两条流程的身份不同：独立来源按物理 ordinal 保留所有记录；译文迁移只更新可以唯一证明的现有目标，不新增猜测的插件记录。

格式读取统一使用 `SST_Parser.from_bytes/from_file` 或 `SstDocument.from_bytes`；完整文档由 Story 09 保证。迁移不需要调用 serializer，不能修改 SST 输入文件。

## 匹配契约

迁移候选同时要求：

1. SST 的真实 `form_id` 与目标插件 FormID 相同。
2. `record_type + field_type` 与目标真实记录/字段类型一致。
3. 原文完全一致。
4. 同一映射在来源和目标中均唯一，且目标来源命名空间正确。

不使用旧 `form_id + index` 规则。SST 的 index 是 xTranslator 物理同名字段索引，插件解析器的业务索引可能表示任务阶段或对话响应；在逐类证明对应前不能将它们等价。不同字段、不同原文、重复候选、跨来源或无法定位的情况均诊断而非自动覆盖。

迁移仍遵循已有译文/状态覆盖规则，匹配本身不授权覆盖用户已编辑译文。空源、没有可用译文、非法文件和所选格式与 magic 冲突须明确报告。独立 SST 来源必须保留显式空译文；是否把空译文用于迁移由既有迁移规则决定，不能误当成解析丢失。

## 数据流与责任

文件选择/拖放/助手参数 → 来源识别与快照读取 → 完整 SST 解码 → 按真实身份、字段及原文生成唯一候选草稿 → 展示统计与冲突 → 权威提交。

- `application/io/migration_import.py` 负责准备、唯一匹配与诊断。
- `converter/sst_entries.py` 负责 SST 自身 `sst-v2:{ordinal}` 身份，不把其 key 当作插件目标定位。
- GUI 通过已有 migration coordinator/worker 准备草稿，正式提交前验证活动工程、版本和修订；解析失败、取消、目标变化时保留原集合。
- 助手调用相同 application 用例，不另建一套匹配器。正式 MCP 当前仅 foundation，尚未提供文件解析/写回工具，read/write 为 unavailable。
- 兼容 `TranslationEntry.try_update_from_sst()` 和集合批量入口时也要遵守真实 FormID、record/field 与原文约束，不从字符串 key 猜测 SST 原始布局。

## 旧来源兼容

旧工程保留可打开、可编辑能力。缺少 codec v2 物理 ordinal、记录签名及来源绑定时拒绝 SST 原格式写回，不静默根据旧 key 生成新定位。恢复路径是重新导入真实 SST，再把旧工程中可以唯一匹配的译文迁移到新来源。迁移必须显示冲突，不能自动覆盖旧版本或改写用户原 SST。

## 验收

- 两种 SST 均能生成正确译文候选；完整解析不能漏掉旧扫描曾遗漏的记录。
- 同 FormID 不同字段、同字段不同原文和重复文本的夹具不会串写。
- 多义来源/目标拒绝；未知或非法格式、损坏输入、取消与提交失败不污染当前状态。
- 来源快照保存后移走原文件仍可重开；SST 独立来源重复物理记录不会被去重。
- GUI 与助手的读取/迁移参数、错误码及语义一致；正式 MCP 能力矩阵不能宣称尚不存在的工具可用。
- 真实语料迁移与工程流程回归属于集成计划验收；格式 codec 的通过不能替代迁移验收。

## 与写出的关系

原 SST 写回由 Story 11 与统一发布流程完成。插件新建 SSU9 属于独立输出动作，不会因导入迁移源而自动触发；当前保持实验性，VMAD、非 ASCII master/插件名及未知字段映射暂不支持。
