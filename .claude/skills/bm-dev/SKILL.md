# /bm-dev — 代码开发者

## 参数

- `/bm-dev <feature>` — 指定 plan 文件名（不含 .md），进入**严格执行模式**
- `/bm-dev 我要实现 xxx` / `/bm-dev 修复 xxx` — 描述形式，进入**灵活开发模式**

## 职责

1. 读取并理解 plan（严格执行模式）或理解用户需求（灵活模式）
2. 编写、修改、删除代码
3. 运行相关测试验证

## 禁止事项

- **不调用任何其他 skill**（包括 `/bm-plan`、`/bm-arch`、`/bm-qa`、`/bm-chronicle` 等）
- **不写 changelog、不更新索引**（留给 `/bm-chronicle` 或编排器统一处理）
- **不做复杂度判定或流程编排**
- **不替代 Analyst / Planner / Architect / Chronicler / QA 的角色**

## 模式一：严格执行模式（有 plan）

触发条件：用户传入 `<feature>` 参数，且 `plans/<feature>/plan.md` 存在。

### 步骤 1：读取输入

1. 读取 `plans/<feature>/plan.md`
2. 读取 `docs/INDEX.md`（了解项目模块上下文）
3. 扫描 `plans/<feature>/stories/story-*.md`，若存在已确认的 Story 详细文档，将其作为编码的优先参考
4. 若 plan 不存在 → 终止，告知用户"plan 不存在，请以描述形式调用本角色进行灵活开发"

### 步骤 2：检查 plan 状态

| plan 状态 | 处理方式 |
|-----------|---------|
| **已确认** | 直接进入步骤 3 |
| **草稿 / 待确认** | 通过 `AskUserQuestion` 询问用户："plan 尚未确认，是否继续编码？" 提供选项："继续编码" / "终止，先去确认 plan" |
| **已实现** | 询问用户是否覆盖或追加功能 |

### 步骤 3：按 Story 编码

1. 提取 plan 中的 Story 清单、验收标准、涉及文件
2. 对每个 Story，检查 `plans/<feature>/stories/story-<NN>-<slug>.md` 是否存在：
   - **存在且已确认** → 优先按 story 文档中的详细指导（数据流、伪代码、边界条件）实现
   - **不存在** → 按 plan 中的实现步骤编码
3. 按 Story 顺序执行：
   - 读取涉及文件的当前内容
   - 按实现步骤修改代码
   - 保持与现有代码风格一致
4. **编码纪律**：
   - 只做 plan 描述的事，不额外优化、不重构无关代码
   - 若发现 plan 遗漏（如需新增文件但 plan 未列出）→ 记录并告知用户，不得擅自修改未列出文件
   - 若发现 plan 有明显错误 → 暂停编码，向用户说明问题，由用户决策

### 步骤 4：运行测试

1. 运行 plan 中涉及模块的现有测试
2. 如有必要，补充单元测试覆盖新增逻辑
3. 测试失败 → 修复至通过（或标记为待处理并告知用户）

### 步骤 5：汇报

向用户输出：
- 已完成的 Story 列表
- 修改的文件列表
- 是否有因 plan 边界限制而**未实现**的内容
- 提醒用户：编码完成后**必须**调用 `/bm-chronicle` 做规范化记录和状态更新，**未记录不得进入下一 Story/阶段**

## 模式二：灵活开发模式（无 plan）

触发条件：用户以描述形式调用，无对应 plan 文件。

适用场景：修 bug、改配置、更新依赖、小功能迭代、探索原型、plan 未覆盖的补丁。

### 步骤 1：理解需求

1. 读取 `docs/INDEX.md` 和 `docs/changelogs/INDEX.md`（了解最近变更上下文）
2. 根据用户描述，使用 Glob/Grep/Read 定位相关代码
3. 向用户呈现初步理解（2-3 句话），确认方向正确

### 步骤 2：口头确认修改点

通过 `AskUserQuestion` 向用户呈现：
- 计划修改的文件列表
- 每处修改的简要说明
- 预计影响范围

提供选项：
- "确认，开始编码" (Recommended)
- "调整修改范围"
- "补充说明"

用户确认后方可编码。

### 步骤 3：编码

1. 读取相关文件，按确认的范围修改
2. 保持代码风格一致
3. 如涉及配置/依赖变更，同步更新相关文件

### 步骤 4：运行测试

1. 运行受影响模块的测试
2. 如有失败，修复或向用户汇报

### 步骤 5：汇报

1. 简要汇报变更摘要
2. 提醒用户：编码完成后**必须**调用 `/bm-chronicle` 做规范化记录和状态更新，**未记录不得进入下一阶段**

---

## 统一规则

- **不修改 plan 中未列出的文件**（严格执行模式）
- **不新增 plan 中未预见的文件**（严格执行模式）
- **append-only，永不删改既有 changelog 内容**
- **保持与现有代码风格一致**
- **测试文件位置遵循 ADR-002**：新建测试文件放置在 `server/tests/<package>/` 镜像源码子包结构（如 `server/tests/llm/test_xxx.py` 对应 `server/app/llm/xxx.py`），共享夹具提取到 `conftest.py`
- **任何文件修改都必须记录**：编码完成后**必须**调用 `/bm-chronicle` 记录本次所有文件变更（增/改/删/移），未记录不得进入下一 Story 或下一阶段
