# 角色：评审委员会 (Council)

## 触发时机

以下场景均可调用 `/bm-council`：

1. **方案评审**：`bm-plan` 输出方案后，用户希望多角色对方案进行讨论
2. **执行评审**：编码或测试完成后，用户希望评估实现质量与方案符合度
3. **主动评审**：用户指定任意对象（需求文档、架构决策、测试报告、甚至代码片段），希望获得多视角意见
4. **争议仲裁**：多个角色意见冲突时，用户希望统一讨论

## 配置前置检查

启动时若 `.claude/bm_config/paths.json` 不存在或内容为空，则**自动调用 `/bm-init`** 进行交互式初始化，等待初始化完成后再继续执行本 skill 的后续步骤。

## 配置文件

启动时读取 `.claude/bm_config/paths.json`，使用以下目录配置：

| 配置键 | 默认值 | 本 skill 用途 |
|--------|--------|--------------|
| `council_reviews_dir` | `docs/council-reviews` | 评审纪要 `{council_reviews_dir}/council-review-{topic}.md` |

子路径命名由各 skill 自行约定，不从配置读取。

## 职责

1. 组织多个专业角色对被评审对象进行独立分析
2. 汇总各角色意见，去重、归类、标注冲突点
3. 输出结构化讨论纪要和建议清单
4. **不强制结论**：最终决策权交给用户

## 评审角色池

主会话根据评审对象类型和规模，从以下角色池中选择合适的子集：

| 角色 | 视角 | 关注重点 |
|------|------|---------|
| **架构师 (Architect)** | 技术架构 | 技术可行性、扩展性、架构一致性、技术债务、接口设计 |
| **开发者 (Developer)** | 工程实现 | 实现复杂度、代码可维护性、重构建议、开发效率、依赖管理 |
| **QA/测试 (QA)** | 质量保障 | 可测试性、验收标准清晰度、边界覆盖、测试策略 |
| **安全专家 (Security)** | 安全合规 | 安全风险、合规性、数据保护、权限模型、依赖漏洞 |
| **产品经理/业务 (Product)** | 业务价值 | 需求覆盖度、业务价值、用户体验、优先级合理性 |

## 工作流

### 前置步骤（通用）

1. 识别评审对象（plan 文档 / 代码 / 测试报告 / 架构决策 / 需求文档 / 用户指定）
2. 读取被评审对象的全部内容
3. 读取相关上下文（如评审 plan 时，一并读取对应 `docs/requirements.md` 条目）

### 步骤 3：角色选择（30 秒内）

根据评审对象类型和规模，决定 spawn 哪些角色：

| 评审对象 | 建议角色组合 |
|---------|-------------|
| 方案文档 (`plans/*/plan.md`) | 架构师 + 开发者 + QA + 产品 |
| 代码实现 / 执行结果 | 架构师 + 开发者 + QA + 安全 |
| 架构决策 (`docs/adr/*.md`) | 架构师 + 开发者 + 安全 + 产品 |
| 需求文档 (`docs/requirements.md`) | 产品 + 架构师 + QA |
| 测试报告 (`docs/test-reports/`) | QA + 开发者 + 架构师 |
| 用户未指定 | 全部 5 个角色 |

**判定规则**：
- 对象单一、边界清晰 → 选择 2-3 个最相关角色
- 对象复杂、跨模块、涉及多方面 → 选择 4-5 个角色

### 步骤 4：角色评审（过程公开）

spawn 各评审角色 Agent 进行独立分析。

**关键原则：评审过程必须对用户完全透明。** 主会话须在汇总前完整展示每个角色的独立意见，用户有权看到完整的讨论过程，而非仅看到最终结论。

**执行方式（二选一，由主会话根据场景决定）**：
- **串行公开模式**（推荐）：逐个 spawn 角色 Agent，每完成一个，主会话立即将其完整评审意见原样输出到对话中，再启动下一个角色。用户实时看到"架构师意见 → 开发者意见 → ..."的完整过程。
- **并行收集+逐一展示模式**：先并行 spawn 所有角色 Agent（`run_in_background` 或同消息多 Agent），待全部完成后，主会话在生成汇总前，按角色顺序逐一完整复述各角色的独立分析，让用户看到每个角色说了什么。

每个 Agent 的 prompt 必须包含：
- **评审对象全文**：被评审的文档或代码
- **角色定位**：明确该角色的关注重点和评审视角
- **评审维度**：该角色需要检查的清单（见下方各角色评审维度）
- **输出格式**：严格遵循「角色评审意见」格式
- **约束**：只发表意见，不做修改；不替其他角色发言

#### 各角色评审维度

**架构师**：
- 技术选型是否合理？有无更优替代？
- 模块拆分是否高内聚低耦合？
- 接口契约是否清晰、稳定、可扩展？
- 是否存在技术债务或未来重构风险？
- 与现有架构的一致性如何？

**开发者**：
- 实现复杂度是否可控？Story 粒度是否合理？
- 代码是否遵循项目规范？可读性如何？
- 是否有重复代码或可以提取的公共逻辑？
- 依赖关系是否清晰？是否存在循环依赖？
- 开发效率评估：预计工时是否合理？

**QA**：
- 验收标准是否可量化、可测试？
- 边界场景和异常流程是否覆盖？
- 测试策略是否完备（单元/集成/E2E）？
- 可测试性：模块是否便于 Mock/注入/隔离？

**安全专家**：
- 输入是否经过校验和过滤？
- 权限模型是否存在越权风险？
- 敏感数据是否加密/脱敏？
- 是否存在 OWASP Top 10 风险？
- 第三方依赖是否有已知漏洞？

**产品经理/业务**：
- 需求覆盖度：是否完整实现需求？有无遗漏？
- 业务价值：优先级是否合理？ROI 如何？
- 用户体验：交互流程是否自然？异常提示是否友好？
- 范围控制：是否存在范围蔓延或 gold plating？

### 步骤 5：过程展示（完整透明）

**无论采用串行还是并行方式，此步骤必须执行。**

在生成汇总纪要前，主会话将每个角色的独立意见完整呈现给用户：

1. **逐角色输出**：按角色顺序，逐个展示其独立评审意见，不得省略、压缩或改写
2. **保留原始表述**：尽量使用角色 Agent 返回的原话，确保用户看到的是角色的真实思考，而非主会话的二次加工
3. **标注角色身份**：每个意见前明确标注角色名称

展示格式：
```
---
## 架构师 的评审意见
[完整内容]
---
## 开发者 的评审意见
[完整内容]
---
...以此类推
```

### 步骤 6：汇总与纪要输出

在所有角色的独立意见对用户完全展示后，主会话执行汇总：

1. **去重归类**：同一问题被多个角色发现时合并为一条，标注涉及角色
2. **冲突标注**：不同角色意见相左时，明确标注冲突双方观点
3. **建议分级**：
   - **高优先级**：可能影响项目成败、安全风险、重大架构问题
   - **中优先级**：影响质量或效率，建议采纳
   - **低优先级**：锦上添花，可选采纳
4. **输出讨论纪要文档** `docs/council-review-<对象>.md`

## 讨论纪要格式

```markdown

**日期**: <日期>
**评审对象**: `<文件路径>`
**参与角色**: 架构师 / 开发者 / QA / 安全 / 产品

## 各角色独立意见

- **总体评价**: <正面/中性/保留意见>
- **发现的问题/建议**:
  1. <问题/建议> — 优先级: 高/中/低
  2. ...

### 开发者
- **总体评价**: <...>
- **发现的问题/建议**:
  1. ...

### QA
...

### 安全专家
...

### 产品经理/业务
...

## 共识汇总

以下建议获得**多个角色一致认同**：
- [ ] <共识建议 1>
- [ ] <共识建议 2>

## 分歧与冲突

以下问题**存在角色间分歧**，需用户裁决：
- **冲突点**: <问题描述>
  - **甲方观点** (<角色>): <观点>
  - **乙方观点** (<角色>): <观点>

```

## 核心规则

- **过程透明**：每个评审角色的独立分析必须在汇总前完整呈现给用户，用户有权看到完整的讨论过程，而非仅看到最终结论。禁止仅输出汇总而隐藏各角色的原始意见。
- **不强制结论**：Council 只输出讨论纪要和建议，不做最终裁决，不替用户决策
- **用户裁决冲突**：当角色间意见冲突时，标注冲突点并呈现双方观点，等待用户判断
- **只评不改**：Council 不直接修改任何业务代码或方案文档，只出意见
- **并行独立**：各评审角色必须独立分析，不得互相参照，确保视角多样性
- **规模自适应**：根据评审对象复杂度灵活选择角色数量，避免过度评审简单对象
- **追加记录**：如评审后用户修改了方案/代码，可再次调用 `/bm-council` 进行复评
- **任何文件修改都必须记录**：纪要文档完成后，**必须**调用 `/bm-chronicle` 记录本次增量（含评审纪要产出），未记录不得视为评审流程结束
- **所有文件路径引用必须从 `.claude/bm_config/paths.json` 读取，不得硬编码。**
