# /bm-orchestrator — 开发流程编排器

## 参数

- `/bm-orchestrator 我要实现 xxx` — 传入需求，评估复杂度并推荐起点
- `/bm-orchestrator 我要实现 xxx --auto` — 自动驾驶模式：确认路线后自动按阶段调用各 skill，仅在确认点和门禁处暂停
- `/bm-orchestrator --auto` — 无参数自动驾驶：扫描当前进度，自动推进到下一未完成阶段
- `/bm-orchestrator` — 无参数，扫描当前项目状态，输出进度看板并推荐下一步

## 职责

1. **复杂度评估**：根据用户输入，30 秒内判定极简/标准/复杂
2. **进度推断**：扫描项目文档，自动推断当前需求走到哪一步
3. **路线推荐**：告知用户当前该调用哪个 skill，带上下文摘要
4. **进度看板**：以可视化形式呈现各阶段完成状态
5. **自动驾驶**（`--auto` 模式下）：按阶段顺序自动调用下游 skill，仅在用户确认点和记录门禁处暂停

## 禁止事项

- **不写文档、不改代码、不运行测试**（这些由下游 skill 执行）
- **不做技术决策**（选型、架构判断交给对应 skill）
- **不替代各 skill 的内部确认机制**（预沟通确认、写后确认仍由各 skill 自行处理）
- **非 --auto 模式下不调用其他 skill**（手动模式保持纯顾问角色）

## 调用方式一：传入需求（起点模式）

### 步骤 1：匹配已有方案

1. 读取 `docs/INDEX.md` 和 `plans/INDEX.md`
2. 解析用户输入关键词，匹配已有需求/方案条目
3. 若 `plans/<feature>/plan.md` 已存在且状态为"已确认" → 输出进度看板，直接进入"接续模式"
4. 若无匹配或仅有草稿 → 进入复杂度评估

### 步骤 2：复杂度评估（30 秒内）

| 检查项 | 极简 | 标准 | 复杂 |
|--------|------|------|------|
| 是否修改现有核心业务逻辑 | 否 | 否 | 是 |
| 是否引入新依赖/新技术 | 否 | 否 | 是 |
| 预估文件数 | ≤2 | 3-5 | 5+ 或跨模块 |

**规则**：任意一项达到"复杂"→ 复杂模式；三项都是"极简"→ 极简模式；其余 → 标准模式。

### 步骤 3：推荐路线

通过 `AskUserQuestion` 呈现评估结果和推荐路线：

**极简模式**：
> "复杂度：极简（1-2 文件，无新依赖）。推荐直接调用 `/bm-dev` 进行快速开发，无需经过完整流程。"
> 选项："确认，推荐调用 /bm-dev" / "切换为标准模式" / "补充说明"

**标准模式**：
> "复杂度：标准（常规功能，3-5 文件）。建议路线：分析 → 方案 → 编码 → 记录 → 测试"
> 选项："确认，进入标准路线" / "切换为极简" / "切换为复杂" / "补充说明"

**复杂模式**：
> "复杂度：复杂（跨模块/新技术）。建议路线：分析 → 架构 → 方案 → 编码 → 记录 → 测试"
> 选项："确认，进入复杂路线" / "切换为标准" / "补充说明"

## 调用方式二：无参数（接续模式）

用户在一个 skill 完成后调用 `/bm-orchestrator`，编排器扫描产出物并推荐下一步。

### 扫描逻辑

按以下顺序检测，停在第一个"未完成的必要阶段"：

| 阶段 | 检测信号 | 判断标准 |
|------|---------|---------|
| **分析** | `docs/requirements.md` + `docs/INDEX.md` | 存在匹配的需求条目且内容完整 → 完成 |
| **架构** | `docs/adr/*.md` | 复杂模式下，已有 ADR 覆盖当前需求的所有架构层面 → 完成；需扩展已有 ADR → 待架构补充；全新架构领域 → 待架构 |
| **方案** | `plans/<feature>/plan.md` | 已确认 → 完成；草稿 → 需继续；需追加 Story 到已有 plan → 待方案补充；新 Epic → 待方案 |
| **Story 细化** | `plans/<feature>/stories/story-*.md` | （可选）复杂 Story 存在对应详细文档且状态为"已确认" → 完成；无则跳过 |
| **编码** | 代码文件修改 + `docs/changelogs/INDEX.md` | 存在编码产出 → 完成 |
| **记录** | `docs/changelogs/<epic>/<story>/` 文件 | 存在对应增量文件，且 Story/Epic 状态已更新 → 完成 |
| **测试** | `docs/test-reports/` | 存在对应测试报告 → 完成 |

**防御性检测**：若方案涉及跨模块接口但无对应 ADR（即使当前判定为标准模式），先推荐 `/bm-arch` 补充架构决策，再进入 `/bm-plan`。

### 记录门禁（强制性）

**每次阶段切换前，编排器必须执行记录门禁检查**：

1. **检测最近修改的文件**：扫描以下目录，获取项目最近一次修改时间：
   - 代码目录：`server/`、`web/`
   - 文档目录：`docs/requirements.md`、`docs/adr/*.md`、`plans/*/plan.md`、`docs/INDEX.md`、`plans/INDEX.md`
   - 通过 git diff 或文件系统时间戳确认
2. **检测最新 changelog 增量时间**：读取 `docs/changelogs/INDEX.md`，确认最新增量文件的日期
3. **判定**：
   - 若最近文件修改时间 **晚于** 最新 changelog 增量时间 → **阻断阶段推进**，必须先调用 `/bm-chronicle` 记录
   - 若一致或 changelog 更新 → 放行

4. **索引一致性检查**（门禁放行前强制执行）：
   对比以下三份 INDEX 文件，发现不一致立即修复（不阻断，但必须在放行前完成修复）：
   - `docs/changelogs/INDEX.md` 中各 Epic 的实际 Story/增量条目数 vs `docs/INDEX.md` 修改记录表中的 Story 数/增量文件数
   - `plans/<epic>/plan.md` 中的实际状态 vs `plans/INDEX.md` 中记录的对应条目状态
   - `plans/tavern.md`（主方案）的 Story 总数 vs 各子方案 Story 之和
   - `docs/adr/*.md` 中是否有 `### 更新:` 节但 `docs/INDEX.md` ADR 表中未标注更新日期

5. **门禁提示格式**：
   ```
   ⚠ 记录门禁：检测到未记录的变更（<文件列表>）。请先调用 `/bm-chronicle` 记录本次增量，再继续推进。
   ```

门禁检查在以下场景触发：
- 用户选择"当前阶段已完成，跳到下一阶段"时
- 用户选择"推荐调用 [skill]"进入新阶段时
- 用户表示"全完成"时（最终检查）
- **文档产出阶段完成后自动触发**：bm-analyze、bm-arch、bm-plan 完成后，若产出文件未入 changelog 则阻断

### 输出格式

1. **进度看板**（所有阶段一律展示，已完成标 ✓，未完成标 ○）：

```
进度看板: <需求标题>
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[✓] 需求分析    → docs/requirements.md
[○] 架构设计    → 待调用 /bm-arch（复杂模式必需）
[○] 方案策划    → 
[○] Story 细化  → （可选）
[○] 编码实现    → 
[○] 记录归档    → 
[○] 测试审查    → 

当前阶段: 架构设计
推荐下一步: 调用 `/bm-arch` 进行架构决策
```

2. **上下文摘要**：带上该阶段需要的输入信息（如 plan 文件名、需求条目摘要），减少用户重复描述

3. **AskUserQuestion**：
   - "推荐调用 [skill]" (Recommended)
   - "当前阶段已完成，跳到下一阶段"
   - "回退到上一阶段调整"
   - "补充说明"

## 调用方式三：--auto 自动驾驶模式

当用户传入 `--auto` 标志时，编排器进入自动驾驶模式：**不再只是推荐，而是直接调用下游 skill 执行**。

### 触发条件

- `/bm-orchestrator 我要实现 xxx --auto`：从需求出发，确认路线后自动推进
- `/bm-orchestrator --auto`：从当前进度出发，自动推进到下一阶段

### 自动驾驶流程

```
用户输入需求 + --auto
    │
    ▼
[步骤 1: 复杂度评估 + 路线确认]  ← 唯一一次全程确认（AskUserQuestion）
    │ 用户确认路线后，进入自动循环
    ▼
[步骤 2: 自动循环] ──────────────────────────────────────┐
    │                                                     │
    ├─→ 记录门禁检查（每次阶段切换前强制）                  │
    │   ├─ 未通过 → 自动调用 /bm-chronicle → 回到门禁      │
    │   └─ 通过 → 继续                                     │
    │                                                     │
    ├─→ 自动调用下一阶段 skill（Skill 工具直接 invoke）     │
    │   ├─ 各 skill 内部的 AskUserQuestion 正常触发        │
    │   │   （预沟通确认、写后确认 — 用户正常交互）         │
    │   ├─ bm-qa 发现 Blocker → 暂停，等待用户决策         │
    │   └─ 其他情况 → skill 完成后自动继续                  │
    │                                                     │
    ├─→ 该 stage 所有 Story 完成？                         │
    │   ├─ 否 → 继续同一 skill 下一个 Story                │
    │   └─ 是 → 重新扫描进度 → 进入下一阶段                │
    │                                                     │
    └─→ 所有阶段完成？                                     │
        ├─ 否 → 回到自动循环 ─────────────────────────────┘
        └─ 是 → 最终记录门禁 → 输出汇总 → 结束
```

### 暂停点（必须等待用户交互）

自动驾驶在以下情况**暂停**，等待用户决策后继续：

| 暂停触发 | 场景 | 恢复方式 |
|---------|------|---------|
| **路线确认** | 复杂度评估完成，首次进入前 | 用户选择"确认路线"后自动开始 |
| **预沟通确认** | bm-arch 步骤 4、bm-plan 步骤 4、bm-story 步骤 2 | 各 skill 内部的 AskUserQuestion 正常呈现，用户选择后继续 |
| **写后确认** | bm-arch/bm-plan/bm-story 文档完成后 | 同上，用户确认后 skill 返回，编排器继续 |
| **Blocker/Critical** | bm-qa 发现阻塞级问题 | 用户选择处理方式后继续（修复/接受风险/终止） |
| **记录门禁阻断** | 阶段切换前发现未记录变更 | 自动调 chronicle 后重检；若 chronicle 也需用户确认归属则暂停 |
| **范围变更** | 用户中途改变需求范围 | 重新评估复杂度，确认新路线后继续 |

### 自动跳过（无需用户交互）

以下情况编排器**自动推进**，不询问用户：

- 阶段完成后的门禁检查通过 → 直接进入下一阶段
- Story 完成且该 Epic 下还有未完成 Story → 自动继续下一个 Story
- 极简模式下的快速路径 → 跳过分析/架构/方案，直接调 bm-dev
- bm-dev 完成一个 Story 的编码 → 自动调 bm-chronicle，然后继续下一 Story
- 标准模式下架构阶段不存在 → 自动跳过

### 自动调用 skill 的方式

编排器通过 `Skill` 工具直接 invoke 下游 skill，传入拼接好的参数：

```
Skill(skill="bm-arch", args="<从用户需求和扫描上下文拼接的参数>")
Skill(skill="bm-plan", args="<feature-name>")
Skill(skill="bm-dev", args="<feature>")
Skill(skill="bm-chronicle", args="记录 <epic>/<story> 的增量")
Skill(skill="bm-qa", args="<feature>")
```

每次调用前，编排器将当前进度看板和上下文摘要作为 prompt 的前置信息传递给下游 skill。

### 自动模式下的记录门禁

在自动循环中，记录门禁升级为**自动修复**：

1. 阶段切换前检测到未记录变更
2. 编排器**自动调用** `/bm-chronicle`（Skill 工具 invoke）
3. 若 chronicle 能自动确定归属（从 plan 匹配到文件路径）→ 记录完成后自动继续
4. 若 chronicle 无法确定归属 → **暂停**，让用户指定"本次增量属于哪个 Story？"
5. 记录完成 → 门禁通过 → 继续下一阶段

### --auto 模式终止条件

- 所有阶段完成 + 最终门禁通过 → 输出汇总，结束
- 用户在任何暂停点选择"终止" → 输出当前进度，结束
- bm-qa 发现 Blocker 且用户选择"终止当前方案" → 结束
- 连续 3 次门禁检查失败 → 暂停，询问用户

## 各阶段的推荐指令

| 当前阶段 | 检测信号 | 推荐调用 |
|---------|---------|---------|
| 待分析 | requirements.md 无匹配条目 | `/bm-analyze` |
| 待架构（复杂模式） | 无对应 ADR 覆盖 | `/bm-arch`（将创建新 ADR） |
| 待架构补充 | 已有 ADR 需扩展 | `/bm-arch`（将在已有 ADR 尾部追加 `### 更新:` 节） |
| 待方案（新 Epic） | plan 不存在 | `/bm-plan`（将创建新 plan） |
| 待方案补充 | 已有 plan 需追加 Story | `/bm-plan`（将编辑已有 plan 追加 Story 节） |
| 待 Story 细化 | plan 已确认，存在复杂 Story（5+ 步骤或 4+ 文件） | `/bm-story <plan> <story-id>`（单个）或 `/bm-story-batch <plan>`（批量） |
| 待编码 | 无代码修改产出 | `/bm-dev <feature>` |
| 待记录 | changelog 无五级结构记录 | `/bm-chronicle` |
| 待测试 | 无测试报告 | `/bm-qa` |
| 已完成 | 全部产出物存在 | "所有阶段已完成，如需调整请直接调用对应 skill" |

## 特殊场景处理

### 用户中途改变需求范围
- 重新评估复杂度
- 若降级（复杂→标准）：告知用户可跳过架构阶段
- 若升级（标准→复杂）：告知用户需补架构阶段

### 检测到多份相关文档
- 列出所有匹配项，让用户选择继续哪一条线
- 例如："检测到 2 个相关 plan：login/plan.md / auth-refactor/plan.md，请选择"

### 架构变更属于已有 ADR 覆盖范围
- 检测到新需求涉及已有 ADR 覆盖的领域
- 推荐 `/bm-arch` 时注明"将在 `docs/adr/<已有-adr>` 尾部追加更新节，而非新建 ADR"
- 在进度看板中标注：`[⚠] 架构设计 → <已有-adr> 需扩展`

### Story 追加到已有 Epic plan
- 检测到新需求涉及的代码路径已归入已有 Epic
- 推荐 `/bm-plan` 时注明"将在 `plans/<epic>/plan.md` 中追加 Story 节，而非新建 plan"
- 在进度看板中标注：`[⚠] 方案策划 → <已有-plan> 需追加 Story`

### 产出物存在但明显不完整
- 不自动判定为完成
- 向用户说明检测到的状态，由用户选择"继续当前阶段"或"推进到下一阶段"

## 规则

- **每次调用都重新扫描推断**，不依赖持久状态文件
- **手动模式（无 --auto）**：只推荐，不代劳，所有 skill 由用户手动调用
- **自动模式（--auto）**：编排器直接 invoke 下游 skill，仅在确认点和门禁处暂停；自动模式下门禁失败时自动调 chronicle 修复
- **阶段切换只做一次确认**：不叠加到各 skill 的内部确认之上
- **极简需求不强行套流程**：直接调用 `/bm-dev`
- **编码阶段明确传 feature 名**：调用 `/bm-dev <feature>`，而非模糊的 `/bm-dev`
- **记录门禁是强制性的**：每次阶段切换前必须执行记录门禁检查，手动模式阻断提示用户，自动模式自动调 chronicle 修复
