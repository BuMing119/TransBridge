# 同角色多 Agent 并行编排模式

## 适用场景

当某个 skill 的规模判定建议采用多实例时，主会话按此模式执行。核心思想：**根据任务规模，灵活决定用 1 个还是 N 个同类型 Agent**。

## 模式对比

| 维度 | 单实例模式 | 多实例并行模式 |
|------|-----------|--------------|
| 触发条件 | 小规模（模块少、维度少、边界简单） | 大规模（模块多、维度多、可拆分） |
| Agent 数 | 1 | N（按子任务数） |
| 执行方式 | 串行 | 并行 spawn |
| 产出物 | 1 份文档 | N 份子文档 + 1 份汇总文档 |
| 拆分者 | 该 Agent 自己 | 主会话预先拆分 |

## 标准流程

### 步骤 1：规模判定（30 秒内）

主会话在执行 skill 前，先快速评估：

- **plan**：涉及几个独立模块/子系统？模块间耦合程度？
- **arch**：涉及几个架构层面？各层面是否正交？
- **qa**：需要几个审查维度？各维度是否独立？
- **dev**：有几个独立 Story？文件边界是否重叠？
- **council**：评审对象涉及几个专业视角？需要几个角色参与？

**判定规则**：
- 单模块 / ≤2 个维度 / 文件边界重叠 → **单实例**
- 多模块低耦合 / 3+ 正交维度 / 无文件重叠 → **多实例并行**
- 多模块高耦合 → **先解耦**（建议先 arch 再 plan/dev）

### 步骤 2：任务分解（主会话执行）

多实例模式下，主会话**必须先拆分**，再并行 spawn。拆分产物：

1. **子任务清单**：每个子任务的名称、边界、输入上下文
2. **接口契约**：子任务之间的交互约定（字段名、接口签名、数据结构）
3. **依赖关系**：哪些子任务可以并行，哪些必须串行

**拆分原则**：
- 每个子任务产出独立文档或代码文件
- 子任务之间尽量不共享可变状态
- 必须共享的部分（如接口契约）在拆分阶段冻结

### 步骤 3：并行执行

在同一条消息中并行 spawn N 个同角色 Agent。每个 Agent 的 prompt 必须包含：

- **子任务描述**：该 Agent 负责的具体范围
- **边界约束**：明确说明哪些内容不在本 Agent 职责内
- **输入上下文**：需求摘录、相关 plan 片段、接口契约
- **输出格式**：严格遵循 skill 定义的产出格式
- **一致性要求**：与兄弟 Agent 的术语统一约定

### 步骤 4：结果汇总

所有子 Agent 完成后，主会话执行汇总：

1. **术语一致性检查**：同一概念在不同子产出中名称是否统一
2. **接口契约检查**：跨子任务的接口定义是否匹配
3. **完整性检查**：是否有遗漏的子任务或边界场景
4. **冲突解决**：发现冲突时，spawn 1 个汇总 Agent 或主会话自己裁定

**汇总产出**：
- 1 份汇总文档（主产出，符合原 skill 的产出格式）
- N 份子文档（在汇总中引用，不重复内容）

### 步骤 5：索引同步

汇总完成后，统一更新索引文件：
- `plans/INDEX.md`：汇总文档 + 各子文档条目
- `docs/INDEX.md`：对应需求状态更新

## 各 Skill 的多实例拆分维度

| Skill | 拆分维度 | 单实例阈值 | 多实例触发条件 |
|-------|---------|-----------|--------------|
| `/analyze` | 需求维度（功能/安全/性能/合规） | ≤3 个维度 | 4+ 个维度 |
| `/plan` | 模块/子系统 | ≤2 个模块 | 3+ 个低耦合模块 |
| `/arch` | 架构层面（数据/API/部署/安全） | ≤2 个层面 | 3+ 个正交层面 |
| `Developer` | Story（按文件边界） | ≤2 个独立 Story | 3+ 个无重叠 Story |
| `/qa` | 审查维度（功能/安全/性能/质量） | 标准审查 | 需要专项并行审查 |
| `/council` | 评审角色（架构/开发/QA/安全/产品） | 2-3 个角色 | 4-5 个角色 |

## 禁止场景

以下场景**不得**使用多实例并行：

1. `/chronicle`：append-only 单文件日志，并行写入会冲突
2. 子任务间存在强耦合且无法冻结接口契约
3. 子任务需要修改同一文件的不同部分（代码冲突风险）
4. 用户明确要求简化流程（极简模式）
